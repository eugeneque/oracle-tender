# Часть 1. Как работает оценка сейчас

Оценка идёт тремя независимыми слоями.

```
закупка → профили релевантности (текст + ОКПД2) → LLM «наша ли закупка?»
        → требования ТЗ × каталог продукции → процент и verdict матрицы
        → профиль компании + матрица + история → Task / Competencies / History → overall
        → заключение (fit) → вердикт ИДТИ / ИДТИ С ОГОВОРКАМИ / НЕ ИДТИ
```

## 1. Профили релевантности (отбор закупок)

Слой работает без LLM. Модель — `RelevanceProfile` (`app/models/relevance_profile.py`).

Поля профиля:
- `keywords`, `exclusion_keywords`;
- `okpd2_codes` (префиксы: `26.51` включает вложенные);
- `match_mode` (`any|all`), `okpd2_mode` (`narrow|either`);
- `source_keys` (площадки; пусто значит все);
- `is_default` (общий профиль), `is_active`.

Сид общих профилей Миртек: `app/seed/search_profile_data.py`, 9 групп в `KEYWORD_GROUPS` (АСКУЭ, бренд и каналы связи, счётчики, замена, монтаж, поверка, обслуживание, комплексные услуги). Коды ОКПД2 — `ELECTRIC_METER_CODES = ("26.51.63.130", "26.51.63.131", "26.51.63.139")` (`app/services/okpd2_service.py:56`). Исключения: вода, газ, тепло, медицина, охрана, видеонаблюдение.

Алгоритм (`app/services/relevance_service.py`):
1. Текст закупки = `title + заказчик + способ закупки`. Документы и описание не используются.
2. Токенизация в нижнем регистре.
3. Правила слов:
   - `слово*` — префикс;
   - слово без звёздочки — точное совпадение или совпадение по первым 5 буквам (`_STEM_PREFIX = 5`), слово текста не длиннее ключа более чем на 3 буквы (`_MAX_ENDING = 3`);
   - `(a* b*)~N` — все термины в окне до N слов;
   - многословная фраза — слова подряд.
4. Порядок `match_profile`:
   1. исключения, любое совпадение отсеивает закупку;
   2. слова (`all` — все ключи, `any` — хотя бы один);
   3. код ОКПД2 (`okpd2_service.covers`);
   4. режим: `narrow` требует и слова, и код; `either` достаточно одного.
5. Достаточно одного активного профиля. Результат пишется в `tenders.passed_relevance_filter` и `matched_profile_id`. Отсеянная закупка не удаляется, а только помечается (`None` = «не проверяли», показывается).
6. Профили фильтруются по `source_keys` площадки. Если на площадку не действует ни один общий профиль, закупка считается прошедшей.

Личные профили кэшируются в `relevance_profile_matches` и пересчитываются по `rules_version` (`relevance_profile_service.py`). Фразы для сбора с площадок хранятся отдельно в `CollectionTerm`.

LLM-доочистка (`ai_relevance_service.py`):
- запускается только для закупок, прошедших текстовый фильтр;
- контекст компании зашит в `COMPANY_CONTEXT` (стр. 43-53), промпт `SYSTEM_PROMPT` (стр. 55-69);
- ответ `{is_relevant, confidence 0-100, reason}` при `temperature=0.0`;
- результат пишется в `tenders.ai_relevant` и связанные поля. Сбой модели оставляет `None`, а не `False`.

Замечание: `SearchProfile.min_nmck` и `ai_score_threshold` хранятся, но нигде не читаются. Реальный порог уведомлений — `NotificationSettings.ai_score_threshold`, по умолчанию 80.

## 2. Каталог продукции и матрица соответствия

Каталог (`app/models/manufacturer.py`):
- `Manufacturer` (`is_mirtek` — флаг «наша компания», плюс конкуренты);
- `SiType` — запись Госреестра СИ (ГРСИ);
- `Product`;
- `ProductCharacteristic` — EAV-характеристики с приоритетом источников `manual_entry > user_manual > manufacturer_site > fgis_description_type`.

Источники: парсер сайта производителя (`adapters/mirtek_catalog.py`), ФГИС (`fgis_catalog_sync.py`), ручной импорт, руководства. Справочник характеристик — `seed/characteristics_data.py`, 39 «параметров для ПУ» — `seed/meter_parameters.py`, 11 типов прибора — `services/meter_kind.py`.

Подбор моделей в контекст (`product_relevance.py`), топ-6 по баллам:

| Признак | Баллы |
|---|---|
| Модель названа в ТЗ | +100 |
| Фазность совпала / не совпала | ±12 |
| Тип прибора совпал / не совпал | ±15 |
| Совпавшее число или протокол | +1 |
| Снята с производства | −3 |

Матрица (`compliance_service.py`):
1. Берутся требования `kind == product`, извлечённые из ТЗ (`tender_analysis.py`). У каждого есть критичность (`critical|important|minor`) и номер параметра 0-39.
2. LLM сравнивает требования с карточкой каждого производителя пачками по 20 и ставит `meets|partial|not_meets|no_data`.
3. Код правит вердикты экспертными правилами (`apply_expert_rules`, `apply_reference_rules`): трёхпозиционное реле, тип и фазность, Astra, «эталон ТЗ».
4. Записи с уверенностью ниже 0.6 помечаются на ручную проверку.

```
percentage = Σ(w × score) / Σ(w по требованиям без no_data) × 100
w: critical 3, important 2, minor 1
score: meets 1.0, partial 0.5, not_meets 0
```

Verdict (`decide_verdict`):
- есть критичное `not_meets` → `fails`;
- нет оценённых требований или данных нет у более чем 50% критичных → `unknown`;
- есть некритичное `not_meets` либо критичное `partial` или `no_data` → `caveats`;
- иначе → `passes`.

Результат хранится в `compliance_matrix_entries` и `win_percentages`.

## 3. Профиль компании и AI-оценка

Профиль компании (`models/company_profile.py`, `company_profile_service.py`):
- реквизиты;
- `years_of_experience`;
- `licenses` и `past_projects` (JSONB);
- данные rusprofile;
- `is_primary` (используется только основной профиль).

Профиль разворачивается в нумерованный список (`profile_fields` / `profile_block`), и модель ссылается на пункты по номерам. Пустой профиль блокирует расчёт (`require_filled`).

`compute_profile_score` (`ai_profile_service.py:1274`), три измерения.

**Task** — LLM проставляет статусы по 4 критериям, число модель не называет (`STATUS_VALUES`: met 1, partial и unknown 0.5, not_met 0, `not_applicable` вне расчёта):

| Критерий | Вес |
|---|---|
| `subject` — предмет закупки | 40 |
| `product_fit` — продукция подходит | 30 |
| `experience` — опыт | 20 |
| `scope_purity` — чистота предмета | 10 |

Правила:
- `subject = not_met` → Task = 0;
- `experience = met` без ссылки на профиль понижается до `partial`;
- если у «нашего» производителя `verdict == fails`, Task ≤ `FAILED_MATRIX_TASK_CAP = 20`.

**Competencies** — до 12 требований к участнику. `met` без ссылки на профиль становится `unknown`. Любое обязательное `not_met` даёт 0. Иначе результат — среднее × 100. Если требований нет, измерение исключается.

**History** — без модели: `wins / decided × 100` по релевантным участиям. Они отбираются по похожим тендерам, заказчику и схожему предмету (`company_participations`, `tender_outcomes`). Если известны только победы, результат `None`.

**Overall** — среднее по доступным измерениям. Если `fit = not_fit`, потолок `NOT_FIT_OVERALL_CAP = 30`.

Заключение (`ai_conclusion_service.py`): два LLM-вызова (`fit` и план участия), плюс кодовые проверки:
- brand lock чужой марки без эквивалента даёт `not_fit`;
- без матрицы `fit` понижается до `fit_with_caveats`;
- названия моделей и производителей сверяются со справочником.

Вердикт (`_verdict_from_conclusion`):
- `not_fit` или `decision = False` → НЕ ИДТИ;
- `fit` → ИДТИ;
- иначе → С ОГОВОРКАМИ.

Запасной путь по overall: ≥80 — ИДТИ, ≥50 — С ОГОВОРКАМИ, ниже — НЕ ИДТИ.

Хранение: `ai_profile_scores` (история, `is_current`). Показ: `TenderAiScorePanel.tsx`, бейдж «AI N%». Уведомление `HIGH_AI_SCORE` срабатывает при `overall ≥ 80`.

# Часть 2. Как адаптировать систему под другую компанию и другие ОКПД2

Часть 2 — это рекомендация по прочитанному коду, а не готовая реализация. Площадки-источники и парсеры я детально не изучал, поэтому раздел 2.6 написан с оговоркой.

## 2.1 Что в системе универсально, а что привязано к Миртек

| Блок | Универсальный | Привязан к Миртек / электросчётчикам |
|---|---|---|
| Движок профилей (слова, `*`, `~N`, ОКПД2, `any/all`, `narrow/either`) | да | только сид |
| Кэш совпадений, предпросмотр, CRUD профилей | да | нет |
| LLM-доочистка релевантности | механика да | `COMPANY_CONTEXT` и промпт |
| Модель каталога (`Manufacturer`, `Product`, `ProductCharacteristic`) | да | флаг `is_mirtek`; `SiType` (ГРСИ) только для средств измерений |
| Справочник характеристик, 39 параметров, 11 типов ПУ, фазность | нет | да |
| Подбор моделей (`product_relevance`) | механика да | фазность и тип прибора, `_STOP_VALUES` |
| Матрица: пачки, формула процента, verdict | да | экспертные правила (реле, Astra, ПП 719, ГИСП) |
| Извлечение требований | механика да | промпт и список критичных параметров |
| Профиль компании | да | нет |
| Task / Competencies / History, формулы, потолки | да | текст критериев (`subject`: ПУ, АСКУЭ, УСПД) |
| Заключение | механика да | промпты (электросчётчики, Россети) |

Вывод: ядро универсально, а предметная область размазана по сидам, промптам и нескольким сервисам. Главный рефакторинг состоит в выносе этой области в сменный «пакет домена».

## 2.2 Целевая архитектура: «пакет домена» (domain pack)

Сейчас всё зашито в код и сиды. Предлагается вынести предметную часть в один каталог конфигурации:

```
domains/<company_slug>/
  company.yaml          # название, бренд, синонимы бренда, ИНН, флаг «наш производитель»
  okpd2.yaml            # основные и смежные коды, коды-исключения
  profiles.yaml         # группы ключевых слов, исключения, режимы match/okpd2
  collection_terms.yaml # фразы для сбора с площадок
  prompts/
    relevance_context.md   # вместо COMPANY_CONTEXT
    requirements.md        # извлечение требований
    compliance_rules.md    # системный промпт матрицы
    task_criteria.yaml     # критерии Task, вес и тексты met/partial/not_met
    conclusion.md          # промпты fit и плана
  parameters.yaml       # аналог 39 параметров: номер, название, критичность, группа
  expert_rules.py       # реестр кодовых правил (опционально)
  catalog_adapters.py   # парсеры каталога
```

Активный пакет выбирается переменной окружения, например `DOMAIN_PACK=acme_pumps`, либо полем `tenant_id` для мультиарендности. Загрузка идёт в одном месте, остальной код читает конфигурацию через интерфейс. Без этого каждая новая компания означает правки в 10+ файлах.

## 2.3 Пошаговый план (порядок важен)

### Шаг 1. Новая компания и её производитель
- Создать `Manufacturer` для новой компании и заменить `is_mirtek` на нейтральный `is_own` через миграцию. Поле читается в compliance, AI-оценке и заключении, поэтому найдите все обращения (`grep is_mirtek`).
- Подготовить конкурентов в `seed/manufacturers_data.py`: не 12 производителей счётчиков, а реальных игроков новой ниши.
- Заполнить `company_profile` новой компании: реквизиты, `years_of_experience`, `licenses`, `past_projects`. Здесь нужен только ввод данных, кода менять не надо. Пока профиль пуст, расчёт Task и Competencies блокируется.
- Загрузить историю участий в `company_participations` и `tender_outcomes`. Без неё History будет `None` и исключится из среднего, что допустимо.

### Шаг 2. Коды ОКПД2 и профили релевантности
- Заменить `ELECTRIC_METER_CODES` (`okpd2_service.py:56`) на коды новой компании. Лучше хранить их в `okpd2.yaml`.
- Составить `KEYWORD_GROUPS` вместо `search_profile_data.py:71-198`. Для каждой группы нужны ключи, исключения, коды и режим. Типовой набор групп для любой компании: «поставка», «работы и монтаж», «обслуживание и ремонт», «бренд», «комплексные услуги».
- Заменить `_UTILITY_EXCLUSIONS` и `_DOMAIN_EXCLUSIONS` на исключения новой ниши. Для электросчётчиков исключаются вода, газ и тепло; для другой отрасли исключения будут своими. Этот шаг сильнее всего влияет на шум.
- Учесть тонкости матчинга. Для слов с суффиксами окончание должно входить в окно `_MAX_ENDING = 3`, для коротких слов (до 5 букв) используйте точное совпадение или `*`. Если ниша состоит из составных названий («насос*» против «насосн*»), проверяйте их на реальных названиях закупок.
- Заменить `CollectionTerm` на фразы сбора новой компании. Это фразы, которые вы ищете на площадках, а не фильтры.
- Режим ОКПД2: для компании с чёткими кодами ставьте `narrow`, а для широкой номенклатуры без стабильных кодов лучше `either`.
- Прогнать `POST /profiles/preview` (число совпадений и 8 примеров) на накопленной базе закупок и подстраивать правила.
- Для нового запуска без накопленной базы сначала настроить сбор, потом профили.

### Шаг 3. Контекст компании для LLM-фильтра
- Переписать `COMPANY_CONTEXT` (`ai_relevance_service.py:43-53`): чем занимается новая компания, чем НЕ занимается, правило «упомянуто в закупке ≠ предмет закупки». Правило в `SYSTEM_PROMPT` про «воду/газ/тепло — нет» переписать под новую отрасль.
- Вынести контекст в файл `relevance_context.md` и подгружать из пакета.

### Шаг 4. Каталог продукции
Это самая трудоёмкая часть. Что нужно сделать:
- **Структура характеристик.** `CHARACTERISTIC_GROUPS` (13 групп, 138+ полей, `seed/characteristics_data.py`) и `meter_parameters.py` (39 параметров) заточены под счётчики. Для новой продукции нужно составить свой справочник: названия групп и полей, синонимы (`FIELD_SYNONYMS`), основной источник (`PRIMARY_SOURCE`). Таблица `ProductCharacteristic` — EAV и сама менять не нужна.
- **Парсеры.** `adapters/mirtek_catalog.py` разбирает конкретный сайт. Для новой компании надо написать парсер её сайта или использовать ручной импорт (`catalog_import.py`, `product_manual_ingest.py`). Базовый вариант без парсинга: загрузка Excel или CSV с характеристиками.
- **Госреестр.** `SiType`, `fgis_catalog_sync.py` и `mpi_months` нужны только для средств измерений. Если продукция новой компании не СИ, эти связи пустые, и их надо сделать необязательными. `Product.si_type_id` уже nullable, но матрица берёт «описание типа» как источник фактов `[si_type]`, и это нужно проверить.
- **Подбор моделей.** `product_relevance._score` использует фазность (`PHASE_*`) и тип прибора (`KIND_*`, 11 типов из `meter_kind.py`). Заменить на признаки вашей номенклатуры, например «типоразмер», «мощность», «исполнение». Именованные модели (`NAMED_MODEL_SCORE = 100`) и общие признаки можно оставить как есть.
- **Конкуренты.** Для сравнения «мы против рынка» у конкурентов тоже нужны данные каталога, иначе их матрицы будут `no_data` и не дадут пользы. Начните с 3-5 ключевых конкурентов.

### Шаг 5. Извлечение требований и матрица
- В `tender_analysis.py` (`_REQUIREMENTS_SYSTEM_PROMPT`, стр. 113+) заменить список критичных параметров (класс точности, число фаз, ГРСИ, ПП 719 и т.д.) на критичные параметры новой отрасли. От этого зависит `criticality`, а значит веса 3/2/1 и `fails` при критичном `not_meets`.
- Пересобрать список параметров с номерами (`parameter_no`, 0-39). Это ключ, по которому работают экспертные правила; если номера меняются, правила надо переписать.
- `_SYSTEM_PROMPT` матрицы (`compliance_service.py:138-226`, 16 правил) заменить на правила отрасли. Общие правила (не выдумывать, `no_data` при отсутствии данных, ссылка на источник) оставить.
- `apply_expert_rules` (`:1065-1137`): правила для трёхпозиционного реле, Astra, ПП 719 и ГИСП — специфика электроучёта. Для нового домена удалить и добавить свои либо оставить пустой реестр. Все константы вида `THREE_POSITION_RELAY_BRANDS` вынести в пакет.
- `tz_reference.py` («эталон ТЗ») — механика «ТЗ написано под модель X» универсальна, но проверьте на вашем домене (названия моделей, регулярки).
- Формулу процента и `decide_verdict` не трогать. Пороги `LOW_CONFIDENCE_THRESHOLD = 0.6`, `LOW_COVERAGE_RATIO = 0.3`, `UNKNOWN_CRITICAL_RATIO = 0.5` — калибруйте после первых прогонов.

### Шаг 6. AI-оценка и заключение
- `TASK_CRITERIA` (`ai_profile_service.py:169-225`): оставить 4 критерия и веса, переписать только тексты условий. В частности `subject` («закупаются ПУ эл/эн, АСКУЭ, УСПД…») заменить на предмет новой компании. Эти тексты стоит держать в `task_criteria.yaml`.
- `_TASK_PROMPT`, `_COMPETENCIES_PROMPT` в основном универсальны, но проверьте упоминания электроучёта.
- `ai_conclusion_service.py`: `_FIT_PROMPT` и `_PLAN_PROMPT` содержат отраслевую логику (товарный знак, эквивалент, Россети). Переписать под новую отрасль. Кодовые правила (brand lock → `not_fit`, `matrix_built`) можно оставить.
- Калибровка порогов: `FAILED_MATRIX_TASK_CAP = 20`, `NOT_FIT_OVERALL_CAP = 30`, порог уведомления `ai_score_threshold = 80`, пороги вердикта запасного пути 80/50.
- `MATRIX_COVERAGE_THRESHOLD = 0.8` определяет, когда матрица влияет на Task. Для нового домена с неполным каталогом конкурентов оставьте значение или временно понизьте.

### Шаг 7. Фронтенд и брендинг
- Тексты «Миртек», «ПУ», «АСКУЭ», названия вкладок и подписей в `frontend/src` (`grep -ri миртек`). Вынести в словарь `i18n` или конфиг домена.
- Дизайн-система ORACLE-T (`oracle-t-design`) нейтральна к компании. Акцентный цвет можно менять, остальное оставить.
- `Catalog.tsx` и `components/catalog/*` показывают поля счётчиков (фазность, класс точности). Подстроить под новый справочник характеристик.

## 2.4 Что в итоге нужно ввести данными, а что переписать кодом

Данными (без правки кода, если пакет домена вынесен):
- ОКПД2, ключевые слова, исключения, фразы сбора;
- компания, лицензии, проекты, история участий;
- производители, модели, характеристики;
- веса и тексты критериев Task, контексты и промпты.

Кодом (разово):
- вынос `is_mirtek` в `is_own`;
- загрузчик пакета домена и замена зашитых констант;
- парсеры каталога;
- пересмотр экспертных правил матрицы;
- `product_relevance` под ваши признаки;
- фронтенд-тексты.

## 2.5 Порядок запуска и проверки

1. Вынести константы и промпты в пакет домена, пока Миртек остаётся рабочим пакетом. Это даёт регрессионную базу: поведение Миртек не должно измениться (тесты `test_relevance.py`, `test_relevance_profiles.py`, `test_ai_relevance.py`, `test_ai_profile.py`, `test_ai_conclusion.py`, `test_compliance_service.py`, `test_product_relevance.py`, `test_company_profiles.py`).
2. Завести второй пакет и прогнать на нём профили на реальных закупках. Метрики: доля релевантных среди прошедших фильтр (precision) и доля пропущенных нужных закупок на ручной выборке (recall). Начните с 100-200 размеченных закупок.
3. Только после этого настраивать каталог и матрицу. Они зависят от точной настройки профилей и извлечения требований.
4. Калибровка AI-оценки: сравните вердикты на 30-50 закупках с решением профильных специалистов, поправьте тексты критериев и пороги.
5. Включать уведомления последними, чтобы не завалить пользователей шумом.

- Как мультиарендность (если нужна) сочетается с текущей схемой БД. В отчёте этого нет: все таблицы выглядят однокомпанийными (`is_primary` в `company_profile` допускает одну основную компанию).
- Лицензионные ограничения на данные ФГИС и rusprofile при смене отрасли и объёма использования.

## 2.7 Оценка трудоёмкости

Оценка грубая, исходя из объёма изменений в коде. Ориентиры для одного разработчика:
- вынос домена в пакет и замена `is_mirtek`: 3-5 дней;
- профили и ОКПД2 новой компании с первой проверкой: 1-2 дня;
- каталог (справочник характеристик, парсер или импорт): от 1 до 3 недель, зависит от доступности данных;
- матрица и промпты с экспертными правилами: 1-2 недели;
- калибровка AI-оценки: около недели итераций;
- фронтенд-тексты: 1-2 дня.

Профильная часть (профили и ОКПД2) окупается быстро и может быть запущена раньше каталога и матрицы: даже без них вы получите отбор закупок и список с AI-фильтром «наша ли закупка».
