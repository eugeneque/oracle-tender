## 1. Цель и область проекта

**Название:** Система автоматизированного сбора и анализа тендерной информации (САСТ-Тендеры)

**Заказчик:** ООО «МИРТЕК» (производитель приборов учёта — счётчиков электроэнергии и, возможно, других коммунальных ресурсов).

**Цель:** автоматически собирать тендеры на поставку приборов учёта из открытых источников, анализировать требования тендерной документации, сравнивать продукцию МИРТЕК и конкурентов с этими требованиями, рассчитывать процент вероятной победы каждого производителя с обоснованием, формировать аналитические отчёты и выгружать данные в Excel.

**Кто пользуется системой:** тендерный отдел, отдел продаж, руководство ООО «МИРТЕК» (~10–15 человек ежедневно).

**В объём проекта (этот документ) входит:**
- ежедневный сбор тендеров с 12 доступных источников;
- анализ тендерной документации и извлечение требований;
- формирование справочника продукции МИРТЕК и 12 конкурентов на основе реестра ФГИС и документации производителей;
- расчёт процента победителя по каждому производителю с обоснованием;
- веб-интерфейс (список тендеров, карточка, аналитика, настройки);
- выгрузка в Excel;
- уведомления;
- подготовка данных для последующей интеграции с Bitrix24 (без самой интеграции).

**Не входит в объём проекта (сейчас):**
- сбор с корпоративных площадок застройщиков (~20 источников) — они закладываются в архитектуру, но не подключаются;
- реальная интеграция с Bitrix24 (API, автосоздание лидов) — отдельное ТЗ на второй этап;
- этап 2 методики процента победителя (учёт истории торгов и цен) — только задел в схеме данных.

### 1.1. Сводный алгоритм работы (канонический, при расхождениях — приоритет над формулировками в разделах 5.3–5.5)

Систему проще понять как три слоя, работающих на разной скорости. Ниже — обзор; детали и точные формулы — в указанных разделах, здесь ничего не переопределяется, только связывается в одну картину.

**Слой 1 — каталог приборов, живёт отдельно от тендеров, пополняется фоново (раздел 5.3):**
1. Для каждого производителя (МИРТЕК + 12 конкурентов) система ищет в реестре ФГИС Росстандарта их сертифицированные приборы (коды СИ).
2. По каждому коду скачивается официальный документ «Описание типа» — метрологические и электрические характеристики.
3. Что не покрыто этим документом (интерфейсы, протоколы связи, функциональность) — добирается с сайта производителя и «Руководства пользователя».

Это независимая от конкретных тендеров библиотека, которая просто существует и растёт со временем.

**Слой 2 — матрица соответствия, срабатывает на каждый новый тендер (разделы 5.4, 5.5.2):**
4. Скачивается документация тендера (ТЗ, договор).
5. ИИ извлекает требования из **всего текста целиком**, включая приложения и протоколы обмена, а не только явно оформленный список требований.
6. Каждое требование сверяется с каталогом из слоя 1 в 3 шага: сначала метрологические/электрические данные из ФГИС → затем остальные характеристики из каталога → затем точечный fallback на «Руководство пользователя», если и там нет ответа.
7. Результат — таблица «параметр × производитель» с процентом соответствия и обоснованием по каждому производителю.

**Слой 3 — AI-оценка по профилю компании, достраивается поверх слоя 2 (раздел 5.5.1):**
8. Отдельно от сравнения приборов считаются три измерения о готовности **МИРТЕК как компании** участвовать в тендере: **Task** (похожа ли задача на прошлый опыт МИРТЕК — использует и результат слоя 2, и `company_profile`), **Competencies** (есть ли нужные лицензии/стаж — из `company_profile`), **History** (выигрывали ли похожие компании похожие тендеры раньше — не считается, пока не собрана история, показывает честное «недостаточно данных»).

**Таблица источников (чтобы не путать, кто и про кого отвечает):**

| Вопрос | Про кого | Источник | Самоотчёт участника? |
|---|---|---|---|
| Подходит ли прибор под тендер (слой 2) | МИРТЕК **и конкуренты** | ФГИС + сайты производителей | Нет — внешние источники по обоим |
| Кто исторически выигрывает такие тендеры (History) | МИРТЕК **и конкуренты** | OPTI → `niche_statistics`/`tender_outcomes` (раздел 5.5.2) | Нет — внешний источник по всем |
| Есть ли у МИРТЕК опыт/допуски для этого тендера (Task, Competencies) | **Только МИРТЕК** | `company_profile` — ИНН/ОГРН/адрес/СРО автопоиском по ЕГРЮЛ + подтверждение; проекты — вручную | Да, но это не «самоотчёт стороннего участника», а компания вносит свои же данные, конкурентов не спрашиваем |

Единственное место с ручным вводом (`company_profile.past_projects`) — потому что это единственный вопрос из трёх, который **не** о конкурентах, а о нас самих. Везде, где в системе вообще идёт речь о конкурентах (слой 2 и History), источники уже внешние, без самоотчёта.

**Как слои связаны:** слой 3 не подменяет слой 2 — использует его как один из входов для Task, и только когда каталог слоя 1 заполнен минимум на 80% производителей по конкретному тендеру (порог из раздела 5.5.1). До этого порога Task считается только из текста тендера и `company_profile`, без матрицы.

## 3. Пользователи, роли и аутентификация

- Аутентификация обязательна: вход по логину/паролю, пароли хранятся только в виде хеша (argon2 или bcrypt).
- Роль **«Администратор»**: создаёт, редактирует, блокирует учётные записи пользователей; имеет доступ ко всем разделам настроек (источники, справочники, каталог продукции).
- Роль **«Пользователь»**: работает со списком тендеров, карточками, аналитикой; может подтверждать релевантность тендера, оставлять комментарии, поправлять классификацию.
- Первая учётная запись администратора создаётся автоматически при первом запуске системы (bootstrap-скрипт/команда) — на старте разработки создавать её вручную некому.
- Любое действие пользователя в системе (подтверждение релевантности, комментарий, правка классификации, изменение справочника и т.д.) обязательно пишется в лог с указанием, кто и когда его выполнил.
- Расширение ролей под конкретные отделы (тендерный/продажи/руководство) в объём первого этапа не входит, но модель роли — расширяемый enum, а не жёстко зашитые два значения.

## 5. Функциональные требования

### 5.1. Сбор тендеров

- Для каждого источника (раздел 4.1) — отдельный адаптер, реализующий единый интерфейс:
  - `list_new_tenders(since)` — список новых/изменённых тендеров с момента последнего опроса;
  - `get_tender_details(external_id)` — полная карточка тендера (заказчик, организатор, суммы, даты, регион, способ закупки);
  - `download_documents(external_id)` — список и содержимое файлов документации (ТЗ, проект договора, извещение, протоколы).
- Опрос — 2 раза в день (утро и обед) для всех 12 источников, время конкретных запусков настраивается в конфигурации.
- **Дедупликация**: сравнение по паре (номер закупки, источник); если запись уже есть — не создаётся дубль, обновляются изменившиеся поля.
- **Обработка ошибок**: ошибка одного источника не должна останавливать опрос остальных; при ошибке загрузки — повторная попытка через настраиваемый интервал (по умолчанию 3 попытки с экспоненциальной задержкой); все ошибки — в лог (раздел 5.9).
- Каждый адаптер должен уметь пережить незначительные изменения вёрстки источника без падения всей системы — ошибки парсинга отдельных полей логируются, а не прерывают весь цикл сбора.

### 5.1.1. Профиль релевантности (добавлено 03.09.2026, по образцу OPTI)

Быстрый текстовый фильтр **до** глубокого ИИ-анализа (раздел 5.4) — отвечает не «чему соответствует прибор», а «стоит ли вообще тратить на этот тендер дорогой вызов ИИ». Без этого слоя система будет прогонять через LLM весь поток тендеров со всех 12 источников, включая заведомо нерелевантные, что дорого и медленно.

**Структура — набор именованных групп ключевых слов**, а не один поисковый запрос. У МИРТЕК в референсе (OPTI) — 9 групп: поставка оборудования учёта (АСКУЭ/АИИС КУЭ/УСПД), бренд/связь, ОКПД 26.51.63, счётчики/приборы учёта, замена приборов, монтаж, поверка, техобслуживание/ремонт, комплексные услуги. Каждая группа — это отдельный тип потребности заказчика, у каждой свой набор кодов ОКПД2 (например, «Поверка» → 71.12.40.x, а не 26.51.63.x — это разные классификаторы для разных типов закупки одного и того же прибора).

**Синтаксис ключевых слов:**
- `слово*` — поиск по основе слова (стемминг): `электросчётчик*` ловит все словоформы.
- `(слово1* слово2* слово3*)~N` — все слова должны встретиться в пределах N слов друг от друга (proximity/близость). Реализуется через `tsquery` PostgreSQL с оператором расстояния `<N>` (`to_tsquery` + `<->`/`<N>`) — не требует отдельного поискового движка (Elasticsearch и т.п.), укладывается в уже выбранный стек (раздел 6.2).
- `-слово*` — **исключающее** ключевое слово: если оно встретилось в тексте, тендер **не** считается релевантным для этой группы, даже если совпали положительные ключи. У каждой группы, связанной с работами (замена/монтаж/поверка/ремонт), обязательно есть исключения по смежным, но нерелевантным сферам: газ, вода, тепло, связь, медицина, пожарная безопасность, охрана — чтобы не путать, например, «поверку счётчиков» с «поверкой медицинских приборов».

**Настройки профиля (на уровне производителя, не на уровне группы):**
- `min_nmck` — минимальная начальная цена контракта, ниже которой тендер не рассматривается (у МИРТЕК в референсе — от 100 000 ₽). Это прямой ответ на вопрос с созвона 02.09.2026 («есть ли привязка к сумме контракта») — есть, настраиваемая, не жёстко зашитая.
- `ai_score_threshold` — минимальный `overall_score` (раздел 5.5.1), ниже которого тендер не помечается как отобранный (у МИРТЕК в референсе — 60%). Используется и как фильтр в списке (раздел 5.6).
- `regions_scope` — географический охват (по умолчанию «вся РФ», может сужаться).

**Как это используется в пайплайне:** ключевые группы применяются к заголовку/краткому описанию тендера сразу после сбора (раздел 5.1), до скачивания полной документации и до вызова ИИ — это дешёвый первый фильтр. Тендер, не прошедший ни одну группу, помечается как нерелевантный и не идёт дальше по пайплайну (5.2–5.5), но не удаляется — виден в списке при снятии фильтра, на случай если профиль настроен слишком узко.

**Не входит в срочный объём (03–09.09.2026):** административный интерфейс для редактирования групп ключевых слов и AI-помощник «Дозаполнить» (предлагает новые ключевые слова/группы на основе уже введённых — вспомогательная функция, не критичная для работы самого фильтра). На старте можно захардкодить группы по образцу референса, редактируемый UI — отдельная задача.

3. Ручной ввод/импорт через админ-панель — для любых полей, включая корректировку автоматически извлечённых данных.

**Обозначение типа СИ (`SiType`):**
- Одному коду СИ может соответствовать несколько модификаций/моделей прибора.
- По коду СИ хранится документ «Описание типа» (ссылка + извлечённый текст) и список допустимых модификаций/комплектующих, сертифицированных в рамках этого типа.
- Код СИ — обычное редактируемое поле; заполняется автопоиском по умолчанию **или** вручную/импортом.

**Алгоритм заполнения каталога:**
1. Для каждого производителя (МИРТЕК + 12 конкурентов) — поиск в реестре ФГИС по точному юридическому названию (стратегия по умолчанию), получение списка кодов СИ и привязанных моделей; результаты — на проверку человеком перед сохранением.
2. Скачивание и разбор «Описание типа» по каждому найденному коду → автозаполнение метрологических/электрических характеристик.
3. Переход на сайт производителя, поиск карточки модели, скачивание «Руководство пользователя» (PDF), AI-экстракция остальных характеристик — с обязательной проверкой человеком перед сохранением в каталог.
4. Форма/CSV-импорт «Производитель → код СИ → модель» в админ-панели — для ручного добавления или замены записей, когда заказчик предоставит точные коды СИ конкурентов. Ручной ввод имеет приоритет перед автопоиском при конфликте.

Полный перечень характеристик (~80 полей, 11 групп) — Приложение C. Использовать как основу схемы `product_characteristics`.

### 5.5. Оценка тендера: «AI-оценка по профилю» + матрица соответствия характеристик

С 03.09.2026 у тендера — **две взаимодополняющие метрики**, а не одна:

- **5.5.1. «AI-оценка по профилю»** — новая, главная, отображается крупно в списке и в шапке карточки. Отвечает на вопрос «стоит ли МИРТЕК участвовать в этом тендере и с какими рисками» — оценка компании-заявителя, по образцу референс-системы OPTI. Реализуется расширением существующего модуля `tender_insights.py`, а не новым кодом с нуля.
- **5.5.2. Матрица соответствия характеристик** — существовавший ранее механизм (бывший «единственный процент победителя»). Отвечает на вопрос «какой конкретно прибор МИРТЕК/конкурента подходит под техническое задание и по каким пунктам». К 09.09 в формулу Task **не входит** (см. раздел 0.2) — подключается позже как уточняющий вход, когда каталог продукции станет представительным.

#### 5.5.1. AI-оценка по профилю (History / Task / Competencies)

Три отдельных измерения, каждое — своя цифра % + прогресс-бар + разворачиваемый текстовый комментарий (1–3 предложения):

| Измерение | Что оценивает | Источник данных (к 09.09) | Источник данных (позже) | Готовность к 09.09 |
|---|---|---|---|---|
| **History** | Похожие закупки у похожих заказчиков в прошлом: были ли прямые победы, совпадают ли профильные компетенции с предметом закупки | `company_participations` (реальная история участия МИРТЕК по ИНН, синхронизация с OPTI — раздел 7) для похожих тендеров, если есть записи | + `niche_statistics` (рыночный агрегат по нише, парсинг OPTI) + `tender_outcomes` (исходы отдельных закупок, если появится источник) — расширяет охват сверх собственной истории | **(уточнено 03.09.2026) Да, если для похожих тендеров есть записи в `company_participations`** — иначе честное состояние «недостаточно данных», `history_score = null` |
| **Task** | Насколько предмет закупки (что конкретно нужно поставить/сделать) соответствует опыту и продукции компании | Текст тендера (нормализованные требования, раздел 5.4) + `company_profile.past_projects` | + матрица соответствия (5.5.2), когда каталог станет представительным | Да |
| **Competencies** | Обязательные допуски/лицензии тендера vs фактические у компании; требуемый опыт (лет) vs фактический стаж | Требования тендера (раздел «Лицензии, СРО и допуски» из 5.6) + `company_profile.licenses`, `company_profile.years_of_experience` | без изменений | Да, при условии что `company_profile` заполнен |

**Формула итогового `overall_score` (однозначно, чтобы не было двух трактовок):**
```
если history_score is not null:
    overall_score = (history_score + task_score + competencies_score) / 3
иначе:
    overall_score = (task_score + competencies_score) / 2
    # History не «считается нулём» — она исключается из расчёта, а не штрафует оценку
```
Именно `overall_score` (а не отдельные измерения) уходит в цветной бейдж списка, фильтр по диапазону, условное форматирование Excel (5.7) и порог уведомления (5.8). Веса пересматриваются после уточнения у заказчика на созвоне 09.09.2026 — сейчас равные веса внутри доступных измерений, как в формуле выше.

**Прослеживаемость (обязательное требование, не опция):** у каждого измерения, помимо `*_comment`, должно быть поле `*_evidence` — список ссылок на конкретные `requirement_id` / `tender_documents.id` / `similar_tender_id` / поля `company_profile`, из которых сложилось число. Без этого поля число нельзя проверить, а раздел 5.5.1 прямо требует, чтобы каждая цифра была прослеживаема до источника. Структура — в разделе 7 (`ai_profile_scores`).

**Четыре текстовых блока под тремя измерениями** (в этом порядке):

1. **«Резюме»** — вердикт заглавными буквами (`ИДТИ` / `ИДТИ С ОГОВОРКАМИ` / `НЕ ИДТИ`) + 2–4 предложения: суть закупки, главная сложность, ценовой ориентир, если есть.
2. **«Слабые места»** — нумерованный список, у **каждого пункта — метка значимости в начале строки**: `значительно` / `умеренно` / `незначительно`. Это отдельное структурированное поле (severity), не просто текст — используется потом и для сортировки/фильтрации.
3. **«Рекомендуемая стратегия»** — три подпункта фиксированного формата: «Вердикт: …», «Цена: …» (ставка/ориентир, если есть данные), «Первый шаг: …» (одно конкретное следующее действие).
4. **«Использованные похожие тендеры»** — список ID тендеров, по которым считалась History (когда данные появятся); пока пусто.

**Похожие тендеры и эмбеддинги — конкретное техническое решение (было не выбрано, теперь зафиксировано):**
- Эмбеддинги считаются через отдельный эндпоинт **Yandex AI Studio Embeddings** (это другой вызов API, не тот же, что генерация текста через YandexGPT — не путать в реализации).
- В PostgreSQL добавляется расширение **`pgvector`** (раздел 6.2).
- Новая таблица `tender_embeddings` (раздел 7): один вектор на тендер, считается при поступлении тендера.
- `similar_tenders` заполняется расчётом косинусной близости через `pgvector` — либо на лету при открытии вкладки «Похожие», либо фоновой задачей (выбор — на усмотрение реализации, не принципиально).
- Пока эмбеддинги не посчитаны для минимально представительного корпуса тендеров — вкладка «Похожие» показывает то же честное состояние «недостаточно данных», что и History (а не молчаливую пустоту). Это то же самое несоответствие, которое верно подмечено в разборе: в разделе 9 «Похожие» была помечена срочной, а зависимость от эмбеддингов — нет. Теперь состояние явно синхронизировано.

**Требования к структурированному выводу YandexGPT** (чтобы не наступать на грабли повторно):
- Все схемы structured output (особенно `weak_points`, `recommended_strategy`, 9 разделов «Дополнительно») должны задавать **значения по умолчанию** для каждого поля — без этого модель может просто не заполнить часть полей.
- Длинные генерации (9 разделов, список слабых мест) — разбивать на несколько вызовов/пачек, а не запрашивать всё одним промптом: длинный JSON обрывается по лимиту токенов на выходе.

**Требование к прозрачности:** каждое число (% измерения, ценовой ориентир и т.д.) должно быть прослеживаемо до источника (документ/поле/похожий тендер). Немаркированные, необъяснимые цифры — недопустимы (см. соответствующий недочёт финансового блока в отчёте о созвоне ORACLE-T от 02.09.2026).

#### 5.5.2. Матрица соответствия характеристик (детальный уровень, был единственной метрикой до 03.09.2026)

**Механизм сопоставления требование ↔ характеристика** (для каждого производителя МИРТЕК/конкурент):

1. Сначала — проверка по данным `SiType` / «Описание типа» (метрологические/электрические требования) — детерминированное сравнение числовых/категориальных значений, где это возможно, **включая сравнение по числовому порогу** («не менее X суток», «не более Y А» и т.п. — не только категориальное да/нет).
2. Если не покрыто — проверка по каталогу `Product` (интерфейсы, протоколы, функциональность и т.д.) — детерминированно для чётких полей, ИИ-сопоставление для семантических формулировок (например, «удалённый доступ со стороны ИВК "Пирамида-сети" без промежуточного ПО»).
3. Если требование не покрыто ни тем, ни другим — **fallback**: система переходит на сайт производителя, скачивает и анализирует «Руководство пользователя» модели, подходящей под требования тендера, и ищет ответ там.
4. Итоговый статус по каждому требованию: `соответствует` / `частично` / `не соответствует` / `нет данных`, с текстовым пояснением от ИИ и меткой уверенности (confidence). При низкой уверенности — пометка «требует проверки человеком».

**Важно:** извлечение требований для сопоставления (раздел 5.4) должно идти **по всему тексту документации целиком**, включая разделы протоколов обмена и технические приложения, а не только по явно оформленному перечню требований — практический пример пропуска (требование совместимости с ИВК «Пирамида», обнаруженное только вручную на 15-й странице приложения) зафиксирован в отчёте о созвоне ORACLE-T от 02.09.2026.

**Формат таблицы соответствия** (отображается в карточке тендера, вкладка «Конкуренция», раздел 5.6):

| Параметр | МИРТЕК | Конкурент 1 | Конкурент 2 | ... |
|---|---|---|---|---|
| требование 1 | + / − / частично | ... | ... | ... |
| *пояснение* | текст от ИИ | ... | ... | ... |

После таблицы — общее текстовое заключение ИИ по тендеру.

**Формула процента соответствия (этап 1, реализовано):**

1. Вес требования по критичности: критичное = 3, важное = 2, второстепенное = 1.
2. Статус по требованию: соответствует = 1, частично = 0.5, не соответствует = 0, нет данных = исключается из знаменателя.
3. `Процент соответствия = (Σ вес × статус) / (Σ вес по требованиям с определённым статусом) × 100%`.
4. «Причина» — текстовое пояснение ИИ: какие критичные требования выполнены/не выполнены и почему они решающие.

Этот процент подаётся как один из входов измерения **Task** в 5.5.1, и продолжает отдельно отображаться в матрице соответствия по каждому производителю.

**Методика — этап 2 (задел на будущее, отдельный подпроект, не в объёме этого этапа):**

**(Уточнено 03.09.2026)** Источник данных — не сбор протоколов итогов с нуля по каждому из 12 источников, а **парсинг уже агрегированных данных с OPTI** (`mirtek.optihub.ai`): статистика по нише (кто выигрывает, доля побед, типичное снижение цены — то, что видно во вкладке «Конкуренция»/«Расчёт» референс-системы). **Важно:** это агрегаты по нише (ОКПД2 + регион), другая гранулярность, чем исход отдельной закупки — они сохраняются в отдельную таблицу `niche_statistics` (раздел 7), а не в `tender_outcomes`. `tender_outcomes` остаётся для по-тендерных исходов, если такой источник появится отдельно (например, протоколы ЕИС) — используется измерением History (5.5.1), которое ищет именно похожие отдельные тендеры, а не агрегат по нише. Это отдельный адаптер «источник исторических данных» — разовый/периодический парсинг, не непрерывный сбор новых тендеров, как источники раздела 5.1. Учётные данные для входа в OptiHub — не хранить в открытом виде (раздел 13).

При наполнении `tender_outcomes` можно:
- добавить эмпирический коэффициент — исторический % побед производителя в похожих тендерах (это же и есть источник данных для измерения **History** из 5.5.1 — оба используют одну и ту же сущность);
- обучить модель (логистическая регрессия/градиентный бустинг) на признаках: % по этапу 1, ценовая позиция, факт прежних поставок заказчику.

Схема БД должна с самого начала включать `tender_outcomes`, чтобы не переделывать её, когда/если этап 2 понадобится.

### 5.6. Веб-интерфейс

**Режимы отображения:** приложение уже поддерживает несколько режимов просмотра тендеров (Kanban, Таблица, Таймлайн). **С 03.09.2026 добавляется новый режим — двухпанельный master-detail** (по образцу OPTI): слева список тендеров (узкая колонка), справа детальная карточка выбранного тендера с вкладками, без перехода на отдельную страницу. Этот режим устанавливается **основным (по умолчанию при открытии приложения)**, остальные режимы остаются доступны через существующий переключатель — ничего не убирается. Все вкладки карточки и структура списка ниже относятся именно к этому новому режиму.

**Список тендеров (левая панель):**
- поиск по названию/тексту, сортировка (по умолчанию «Опубликовано (новее)»);
- фильтры: по дате, региону, типу конкурса, сумме, статусу, коду ОКПД2, диапазону AI-оценки (5.5.1); активные фильтры показываются чипами с крестиком для снятия по одному + «Сбросить всё»;
- счётчик «N тендеров» с учётом фильтров;
- пагинация;
- в каждой карточке списка: название, итоговый % AI-оценки (цветной бейдж: зелёный ≥80%, жёлтый 50–80%, красный <50%), заказчик, статус-бейдж этапа (см. ниже), дата (красным — если срочно), сумма при наличии, теги (например «СМП»), число участников при наличии.

**Этапы тендера (pipeline):** тендер имеет поле `stage` — не бинарный статус, а последовательность: `ai_selected` (AI отобрал) → `under_review` (на проверке) → `application_submitted` (заявка подана) → `won` / `lost` / `rejected`. Раздел настроек должен поддерживать Kanban-представление по этим этапам как альтернативу списку (см. «Настройки» ниже).

**Карточка тендера — вкладки:**

1. **Основное** — заказчик (полное наименование + регион), контактное лицо, телефон, email, НМЦК, номер тендера, дата публикации, дедлайн подачи, дата аукциона, ОКПД2, площадка, ссылка на источник, этап, ответственный за тендер (отдельное поле от справочника «регион → ответственный», привязано к конкретному тендеру), метки (произвольные теги), блок комментариев с историей.
2. **Дополнительно** — девять разворачиваемых разделов с результатом извлечения ИИ: «Основные требования», «Объём и контекст», «Лицензии, СРО и допуски», «Требования к участнику», «Условия контракта», «Особые условия исполнения», «Место выполнения работ», «Требования к заявке», «Доп. факты». Именно эта вкладка закрывает недочёт «система не погружается вовнутрь тендера», зафиксированный на созвоне 02.09.2026.
3. **Документы** — список файлов с автоклассификацией по типу (например «ТЗ / Описание», «ССР» — сводный сметный расчёт), размер, отметка файла как приоритетного источника для расчёта (звёздочка), раздельная загрузка документов и сметы.
4. **Расчёт** — ценовая аналитика (рыночный ориентир ставки, статистика по конкуренции за нишу: обычное число участников, % с одним участником, медиана снижения цены, обычный срок подачи, топ компаний-победителей в нише с долей побед и типичным дисконтом). Этот блок читает `niche_statistics` по ключу (ОКПД2, регион) — раздел 7; наполняется по мере парсинга агрегатов с OPTI, при недостатке данных — честное состояние «анализ ещё не запускался» вместо пустого/нулевого значения.
5. **Конкуренция** — матрица соответствия характеристик приборов МИРТЕК и конкурентов требованиям тендера (раздел 5.5.2). Показывает, какие приборы каких производителей подходят и почему — **не** историю побед участников закупок (это сознательно разведено с вкладкой «Расчёт», решение с созвона 02.09.2026: «нам надо, чтобы он конкурентов-производителей показывал», а не кто исторически выигрывает лоты на площадке).
6. **Заявка** — чек-лист обязательных документов заявки с статусом сборки по каждому пункту, предупреждение о недостающих данных компании (реквизиты, фирменный бланк — см. `company_profile`), кнопка формирования заявки. Реализуется в последнюю очередь (решение с созвона 02.09.2026), но структуру вкладки заложить сразу.
7. **Похожие** — список похожих тендеров (по схожести текста ТЗ, эмбеддинги), используется также как источник для измерения History (5.5.1).

**Аналитика** (отдельный раздел приложения, не вкладка тендера):
- статистика по тендерам (количество, суммы, по периодам);
- динамика по месяцам;
- распределение по регионам;
- топ заказчиков;
- средняя AI-оценка по профилю (5.5.1) и средний процент соответствия характеристик (5.5.2) по периодам/регионам/типам конкурса.

**Настройки:**
- управление источниками (12 активных + корпоративные со статусом «ожидает доступа»; включение/выключение, ручной запуск опроса);
- управление справочником продукции (каталог, коды СИ, характеристики — ручная правка и импорт);
- **профиль компании** (`company_profile`) — юридические данные и допуски заполняются автопоиском по ЕГРЮЛ с подтверждением человеком, реализованные проекты — только вручную; без заполнения этого раздела измерения Task и Competencies (5.5.1) считать не из чего;
- **(добавлено 03.09.2026) история участий** (`company_participations`, вкладка внутри «Моя компания», по образцу OPTI) — кнопка синхронизации с OPTI (подтягивает записи по ИНН МИРТЕК), сводка (участий/побед/проигрышей/дисквалификаций/win-rate — с раздельным счётом `lost` и `disqualified`), форма ручного добавления записи, не покрытой синхронизацией (юрлицо, итог, ставка, цена контракта, дата, тендер, заметки). Это основной источник для измерения History (5.5.1);
- управление пользователями (только для роли «Администратор»);
- справочник «регион → ответственный / руководитель» (заполняется вручную, поля ожидают данные от заказчика — раздел 11);
- Kanban-режим по этапам тендера — **уже существует в приложении**, но сейчас группирует по `status` (объективное состояние закупки на площадке: приём заявок/оценка/завершена/отменена). Переводится на группировку по новому `tenders.stage` (внутренний пайплайн МИРТЕК). `status` при этом не убирается — остаётся отдельным фильтром/бейджем в интерфейсе, это не дублирующее, а ортогональное полю `stage` состояние.

- Один лист со сводной информацией по тендерам за выбранный период/фильтр.

- **Дополнительные колонки после 19 обязательных** (добавлено 03.09.2026, отражают поля, появившиеся в модели после введения AI-оценки по профилю): AI-оценка (`overall_score`), вердикт (`verdict`), этап (`stage`), ответственный за тендер (`assignee_id` → ФИО).

### 5.9. Логирование и отказоустойчивость

- Полное журналирование: опрос каждого источника, количество найденных тендеров, ошибки загрузки/парсинга/ИИ-анализа, действия пользователей, экспорт данных.
- Формат записи лога: дата и время, уровень (INFO/WARNING/ERROR/CRITICAL), компонент, действие, результат, детали ошибки (если была), пользователь (если применимо).
- Ошибка одного источника/документа не должна останавливать обработку остальных.
- При ошибке загрузки — повторные попытки через настраиваемый интервал.
- При ошибке ИИ-анализа — повторная попытка или пометка на ручную проверку.
- Уведомление администратора о критических ошибках (раздел 5.8).
- Хранение логов — 6 месяцев, документов — 1 год.

### 5.10. Подготовка к интеграции с Bitrix24 (без самой интеграции)

- Все данные тендера, требований, матрицы соответствия и процента победителя хранятся в структурированном виде, пригодном для последующего маппинга на сущности Bitrix24 (лид, сделка, контакт, компания).
- Экспорт данных в формате, пригодном для импорта в Bitrix24 (CSV/XLSX с полями, соответствующими типовой структуре лида).
- REST API для внешнего получения данных по тендерам (для последующего использования интеграцией второго этапа).
- Реальные вызовы к Bitrix24 API, автосоздание лидов, привязка контактов/компаний, создание задач — не реализуются на этом этапе.

## 6. Архитектура и технологический стек

### 6.1. Слои системы

1. **Источники тендеров** — 12 адаптеров (раздел 4.1), единый интерфейс (раздел 5.1). Корпоративные площадки — заложены в справочник источников, без сбора данных.
2. **Сбор и обработка** — планировщик задач, загрузчик документов, парсер (PDF/DOCX/XLSX → текст), дедупликация.
3. **Хранилище** — реляционная БД (структурированные данные тендеров, требований, каталога продукции, матрицы соответствия, логов) + файловое хранилище документов.
4. **Источник каталога продукции** — адаптер к реестру ФГИС + сайты производителей (раздел 5.3), отдельно от источников тендеров.
5. **ИИ-анализ (Yandex AI Studio)** — извлечение требований, нормализация, критичность, классификация типа тендера, извлечение ОКПД2, определение региона, генерация текстовых пояснений (раздел 5.4).
6. **Сопоставление с каталогом продукции** — детерминированные правила + ИИ-сопоставление + fallback на «Руководство пользователя», расчёт процента победителя, формирование матрицы (раздел 5.5).
7. **Приложение (API + веб-интерфейс)** — список тендеров, карточка, аналитика, настройки, аутентификация; экспорт в Excel; уведомления (раздел 5.6–5.8).

- `is_current` bool, default `true` — при пересчёте текущая запись помечается `false`, создаётся новая с `is_current = true`; хранится история пересчётов, а не перезапись
- `calculated_at`
- Уникальный частичный индекс: `(tender_id) WHERE is_current = true` — гарантирует ровно одну «текущую» оценку на тендер, чтобы список/бейджи не получали недетерминированный результат при пересчёте

**similar_tenders** *(схема нужна к 09.09.2026, наполнение данными — по возможности, не блокирует сдачу; см. раздел 0.2)*
- `id` UUID PK
- `tender_id` FK, `similar_tender_id` FK → tenders
- `similarity_score` numeric — косинусная близость по `tender_embeddings`
- используется вкладкой «Похожие» (5.6) и измерением History (5.5.1)

**tender_embeddings** *(новая, срочно к 09.09.2026 — техническое решение по эмбеддингам, раздел 5.5.1)*
- `tender_id` UUID PK, FK → tenders
- `embedding` vector — через расширение PostgreSQL `pgvector` (раздел 6.2), размерность — по документации Yandex AI Studio Embeddings API на момент реализации
- `model_version` string — версия модели эмбеддингов, чтобы не сравнивать векторы из разных моделей при обновлении
- `created_at`

**tender_outcomes** (задел на этап 2 методики) — исход **одной конкретной** завершённой закупки
- `id` UUID PK, `tender_id` FK nullable, `external_tender_id` string
- `winner_manufacturer_name`, `winner_price` numeric nullable
- `protocol_url`, `published_at`
- `source` enum(`eis_protocol`, `optihub_parsed`, `other`) — откуда взята запись

**niche_statistics** *(новая, уточнено по итогам review 03.09.2026)* — агрегаты **по нише** (ОКПД2 + регион), другая гранулярность, не путать с `tender_outcomes`
- `id` UUID PK
- `okpd2_code` string, `region_code` FK → regions
- `sample_size` integer — сколько закупок за период легло в основу агрегата (у OPTI в примере — 1480 за 3 года)
- `avg_participants`, `single_participant_share` numeric — среднее число участников, доля закупок с одним участником
- `median_price_reduction_pct` numeric — медианное снижение цены
- `usual_submission_days` integer — обычный срок подачи в этой нише
- `top_winners` jsonb — список `{manufacturer_name, wins_count, win_share_pct, typical_discount_pct}` (то, что показывает вкладка «Расчёт»/«Кто выигрывает такие закупки», раздел 5.6)
- `source` enum(`optihub_parsed`, `computed_from_tender_outcomes`) — по решению 03.09.2026 (раздел 0.2), в первую очередь заполняется парсингом уже готовых агрегатов с OPTI, а не пересчётом из своих `tender_outcomes`
- `calculated_at`

Вкладка «Расчёт» (раздел 5.6) читает `niche_statistics` по ключу (`okpd2_code`, `region_code`) тендера. `tender_outcomes` при этом не становится ненужной — если позже появится по-тендерный источник данных (например, отдельные протоколы с ЕИС), она используется для измерения History (раздел 5.5.1), которое считается по конкретным похожим тендерам, а не по агрегату ниши.

**regions**
- `code` string PK (2 символа)
- `name`
- `federal_district_code` FK

**federal_districts**
- `code` PK, `name`

**region_responsibles**
- `region_code` FK PK
- `responsible_full_name`, `manager_full_name`

**logs**
- `id` UUID PK, `timestamp`
- `level` enum(`INFO`, `WARNING`, `ERROR`, `CRITICAL`)
- `component`, `action`, `result`
- `details` text, nullable
- `user_id` FK, nullable

**notifications**
- `id` UUID PK
- `type` (`new_relevant_tender`, `high_ai_score`, `deadline_soon`, `critical_error`) — *(исправлено 03.09.2026: `high_win_percentage` переименован в `high_ai_score`, чтобы соответствовать тексту раздела 5.8 после перехода на `overall_score`)*
- `channel`, `recipient`
- `payload` text/jsonb
- `status` enum(`pending`, `sent`, `failed`)
- `sent_at` nullable, `created_at`

> Справочники `regions` и `federal_districts` заполняются seed-миграцией на основе Приложений G и H этого документа.

## 8. Нефункциональные требования

| № | Требование | Значение |
|---|---|---|

| 2 | Время формирования Excel-отчёта | < 30 секунд |

| 6 | Хранение логов | 6 месяцев |
| 7 | Безопасность | Пароли только хешированные (argon2/bcrypt); ключи API и пароли БД — в переменных окружения, не в коде; HTTPS обязателен (reverse-proxy) |

## 9. План разработки по этапам

Этапы рассчитаны на последовательные сессии Claude Code, каждый — самостоятельно тестируемый инкремент. Порядок соответствует зависимостям.

**⚠️ О статусе проекта (уточнено 03.09.2026):** этот раздел описывает **целевой состав каждого этапа** — так, будто разработка идёт с нуля. Реально проект oracle-t уже прошёл этапы 0–7 практически полностью (список источников, сбор тендеров, каталог продукции, ИИ-анализ, базовый веб-интерфейс уже работают). Для greenfield-реализации или для проверки полноты уже сделанного — читайте этапы по порядку ниже. **Для текущей срочной работы (03–09.09.2026)** — не начинайте с «Этапа 0»; актуальный короткий список задач поверх уже готового кода — раздел 0.2. Технические детали, добавленные в разделы 5 и 7 после review 03.09.2026 (`tender_embeddings`, `pgvector`, `*_evidence`, `is_current`, `company_profile_snapshot`, `registry_number`, `poll_times`, `niche_statistics`), продублированы ниже в конкретных этапах, чтобы этот раздел не расходился с разделами 5/7.

### Этап 0 — Инфраструктура и окружение
**Задачи:**
- Инициализация репозитория, структура проекта (backend/frontend/миграции).

- Подключение к PostgreSQL, миграции (Alembic), seed-данные справочников регионов/ФО (Приложения G, H).

**Результат:** приложение поднимается локально/в Docker, БД создаётся миграциями, health-check отвечает.

### Этап 1 — Аутентификация и пользователи
**Задачи:**
- Таблица `users`, хеширование паролей, вход/выход (сессии или JWT).
- Роль «Администратор»: CRUD пользователей (создание, редактирование, блокировка).

- Middleware, привязывающий каждое действие в системе к текущему пользователю.
- Bootstrap-скрипт/CLI-команда создания первого администратора при первом развёртывании.
**Результат:** первый администратор создаётся автоматически при первом запуске; далее он заводит новых пользователей; любое действие в системе пишется в лог с указанием пользователя.

### Этап 2 — Сбор тендеров: MVP на 2–3 источниках
**Задачи:**
- Общий интерфейс адаптера источника (`list_new_tenders`, `get_tender_details`, `download_documents`).

- Планировщик (APScheduler), расписание 2 раза в день (утро, обед); поле `sources.poll_times` — конкретное настраиваемое время запуска (раздел 7), а не только частота.
- Дедупликация по паре (номер закупки, источник); поле `tenders.registry_number` — извлекается при наличии, используется позже для дедупликации между источниками (раздел 7).
- Таблицы `sources`, `tenders`.
**Результат:** новые тендеры с выбранных источников появляются в БД без дублей по расписанию.

### Этап 3 — Загрузка и парсинг документов
**Задачи:**

- Парсеры PDF (+ OCR fallback), DOCX, XLSX → текст.
- Обработка ошибок парсинга: пропуск конкретного документа с логированием, без остановки обработки остальных.

### Этап 4 — Справочник продукции: ФГИС + документация производителей
**Задачи:**

**Результат:** для тестового производителя каталог автоматически заполняется метрологическими характеристиками из ФГИС; код СИ можно поправить/добавить вручную или импортом; остальные группы характеристик дозаполняются через AI-экстрактор или вручную.

**Результат:** для тестового тендера система выдаёт список нормализованных требований с критичностью, код ОКПД2, регион/ФО и корректный тип конкурса.

### Этап 6 — Сопоставление, матрица соответствия и AI-оценка по профилю
**Задачи:**
- Механизм сравнения требование ↔ характеристика в 3 шага: `SiType`/«Описание типа» → каталог `Product` → fallback на «Руководство пользователя», включая сравнение по числовым порогам (не только категориальное да/нет).
- Таблица `compliance_matrix_entries` — статус, пояснение, источник, уверенность, флаг «требует проверки человеком».
- Расчёт процента соответствия по формуле раздела 5.5.2, сохранение в `win_percentages` (с полем `is_current` и уникальным индексом `(tender_id, manufacturer_id) WHERE is_current`, раздел 7 — версионность при пересчёте).
- **(срочно)** Таблица `company_profile`: автопоиск юридических данных по ЕГРЮЛ + подтверждение человеком (раздел 7); реализованные проекты, реквизиты, бланк — только ручной ввод администратором.
- **(срочно)** Расчёт `ai_profile_scores`: Task и Competencies — по формулам раздела 5.5.1, с обязательным заполнением `task_evidence`/`competencies_evidence` (ссылки на requirement_id/tender_documents.id/company_profile-поля) и `company_profile_snapshot` (копия профиля на момент расчёта); поле `is_current` + уникальный индекс `(tender_id) WHERE is_current` — как у `win_percentages`. History — честное состояние «недостаточно данных», пока не наполнены `tender_outcomes`/`niche_statistics`.
- **(срочно)** Генерация текстовых блоков «Резюме» / «Слабые места» (с меткой значимости у каждого пункта) / «Рекомендуемая стратегия» через Yandex AI Studio, с значениями по умолчанию в схеме structured output и разбиением на пачки при длинной генерации (раздел 5.5.1).
- Расширение PostgreSQL `pgvector`, таблица `tender_embeddings` (вектор на тендер через Yandex AI Studio Embeddings API), заполнение `similar_tenders` расчётом косинусной близости — техническая база для вкладки «Похожие» в этапе 7 (без этого пункта вкладка не имеет реализации, только UI-заглушку).
- Заготовка таблиц `tender_outcomes` и `niche_statistics` (схема есть; наполнение `niche_statistics` парсингом агрегатов с OPTI — по возможности, не блокирует сдачу, раздел 0.2).
**Результат:** матрица соответствия и AI-оценка по профилю (минимум Task + Competencies, с evidence и снапшотом профиля) корректно формируются для тестового набора тендеров, есть текстовые пояснения под каждой метрикой и под каждой ячейкой матрицы.

### Этап 7 — Веб-интерфейс: список и карточка тендера (layout по образцу OPTI)

Перед реализацией перевести существующий Kanban-режим с группировки по `status` на группировку по новому `tenders.stage`; `status` не убирать, оставить отдельным фильтром/бейджем.

**Результат:** пользователь видит список слева и карточку справа без перезагрузки страницы; карточка показывает AI-оценку по профилю, матрицу соответствия и все 9 разделов «Дополнительно»; правки сохраняются в истории с привязкой к пользователю.

- REST API для внешнего получения данных по тендерам.
**Результат:** экспортированный файл/API содержит все поля, необходимые для последующего создания лида на втором этапе (без реальных вызовов к Bitrix24 API).

### Этап 14 — Развёртывание на сервере и документация
**Задачи:**
- Docker Compose (backend + PostgreSQL + reverse-proxy с HTTPS).
- Установочный скрипт, резервное копирование (`pg_dump`) по расписанию.
- Руководство пользователя и администратора, описание архитектуры и API, инструкция по развёртыванию, регламент техподдержки.
**Результат:** система запускается на сервере, доступна ~10–15 сотрудникам по сети, работает после перезапуска без ручного вмешательства; документация подготовлена.

## 10. Критерии приёмки

Разделены на то, что реально проверяемо к жёсткому сроку 11.09.2026, и полный объём документа (остальные этапы раздела 9). Смешивать их в одном списке вводило в заблуждение: например, «все 12 источников по расписанию» заведомо не достижимо за несколько дней и не должно стоять в одном ряду с тем, что достижимо.

### 10.1. Функциональные — к сдаче 11.09.2026

| № | Критерий |
|---|---|
| 1 | Система опрашивает **не менее 2–3 источников** по расписанию (2 раза в день) — полный список 12 источников не входит в критерии сдачи 11.09, см. этап 12 |
| 2 | Новые тендеры появляются в системе в течение времени, соответствующего расписанию опроса |
| 3 | Отсутствуют дубликаты записей внутри одного источника (полная дедупликация между источниками по `registry_number` — не критерий сдачи 11.09) |
| 4 | Для каждого тендера сохраняются все обязательные поля (Приложение D) |
| 5 | Документы доступны из карточки тендера |
| 6 | **AI-оценка по профилю** (измерения Task и Competencies, раздел 5.5.1) формируется для всех обработанных тендеров, с прослеживаемым `*_evidence`; History — честное состояние «недостаточно данных» (наполнение отложено, решение №14) |
| 7 | Матрица соответствия характеристик (5.5.2) формируется хотя бы для тендеров, где каталог по МИРТЕК заполнен |
| 8 | Карточка тендера показывает вкладку «Дополнительно» с результатами по всем 9 разделам |
| 9 | Excel-файл открывается в Microsoft Excel без ошибок, все обязательные поля присутствуют, условное форматирование ссылается на `overall_score` |
| 10 | Ошибка одного источника/документа не останавливает систему |
| 11 | Любое действие пользователя фиксируется в логе с указанием, кто его выполнил |

| 13 | Новый двухпанельный режим отображения работает как основной (по умолчанию), Kanban/Таблица/Таймлайн остаются доступны переключателем; Kanban группирует по `stage`, `status` остаётся отдельным фильтром/бейджем (поля не сведены в одно) |

| № | Критерий |
|---|---|

**Переиспользование существующего кода вместо параллельной реализации:** `tender_insights.py` уже делал ИИ-разбор карточки на риски и пробелы до начала работы над этим ТЗ — решено расширять этот модуль до 9 разделов вкладки «Дополнительно» и `weak_points` со `severity`, а не писать новый с нуля.
