# План измерения качества подбора и анализа (evals)

Цель: исправлять проблемы подбора и анализа, опираясь на заключения специалистов тендерного
отдела, и видеть цифрами, стало ли лучше. Разметку специалисты уже делают в рабочем процессе —
отдельной разметки не просим.

## 1. Что считаем «правдой» (разметка специалистов)

| Слой | Что измеряем | Источник правды | Где лежит |
|---|---|---|---|
| A. Профили | прошла ли закупка сито профилей | решение человека по закупке | `tenders.stage`: `under_review/application_submitted/won/lost` = «релевантна», `rejected` = «неактуально» |
| B. Модель отбора | `ai_relevant` | то же | `tenders.ai_relevant`, `ai_relevance_confidence` |
| C. Матрица соответствия | вердикт «требование × производитель» | исправление специалиста | `compliance_verdict_reviews` (`kind`, `reason`, `is_current`) |
| D. Заключение / AI-оценка | итог и вердикт `ai_profile_scores` | согласие / несогласие | `ai_score_feedback` (`kind`, `text`, `before`/`after`) |

## 2. Метрики

**A/B (отбор).** Матрица ошибок против решения человека; precision, recall, F1.
- Ложный пропуск (FN) дороже ложного срабатывания: потерянный тендер не вернуть, лишний
  специалист закроет за секунды. Главная метрика — recall по «релевантна», при приемлемой precision.
- Отдельно: по площадке, по профилю, по основанию совпадения (`via`: слова / ОКПД2),
  по причине «не нашёл» (нет кода ОКПД2, исключающее слово, площадка вне `source_keys`).

**C (матрица).** Доля вердиктов, с которыми специалист согласился (agree / (agree + disagree)).
- Разрез по причине ошибки: `fact` (каталог/реестр), `requirement` (неверно понято требование),
  `model` (не та модель/тип прибора), `other`. Это прямая карта «что чинить».
- Отдельно «ложные не проходит» (ИИ: не проходит, специалист: проходит) — прежний известный дефект.
- Покрытие: доля ячеек, которые вообще оценили (иначе «согласие» — смещённая выборка).

**D (заключение).** Доля согласий; доля несогласий, после которых пересмотр принят
(`status=applied`); сдвиг `overall_score` до/после замечания; повторяемость тем замечаний.

**Сквозная.** Стоимость и токены на закупку (`ai_usage_service`), время разбора.

## 3. Ловушки измерения (учесть сразу)

1. **Смещение выборки.** Специалист видит только то, что прошло профили и модель. Закупки,
   отсеянные ситом, никто не размечал, поэтому recall по одним решениям людей завышен.
   Лечение: *аудит-выборка* — раз в неделю случайные ~30 отсеянных закупок отдаём специалисту на
   просмотр («не пропустили ли нужное?»). Без неё recall мерить нельзя.
2. **Шум меток.** «Неактуально» ставят и по нерелевантным причинам (срок, регион, НМЦ). Нужна
   причина отклонения (выпадающий список) — иначе эти закупки портят precision.
3. **Дрейф.** Разметка стареет вместе с профилями и каталогом. Каждый прогон фиксирует
   `rules_version` профилей, модель, версию промпта и дату выгрузки.
4. **Утечка.** Исправления специалистов уходят в промпт прецедентами. Эталон для проверки
   нужно *отложить* (hold-out ~30%, не попадающий в прецеденты), иначе меряем заученное.
5. **Малые числа.** Меньше ~30 примеров в разрезе — показываем число, а не процент.

## 4. Этапы

**Этап 0. Инвентаризация (сейчас).** `python -m evals.inventory` — сколько разметки есть по
каждому слою и разрезу. Решение, какие слои мерить в первую очередь, принимаем по цифрам.

**Этап 1. Эталон отбора (слои A/B), без вызовов ИИ.**
- `python -m evals.relevance --export golden/relevance.jsonl` — заморозить эталон.
- `python -m evals.relevance --golden golden/relevance.jsonl [--replay]` — метрики по сохранённым
  отметкам; с `--replay` движок профилей `match_profile` гоняется заново на текущих профилях
  (так видно эффект правки профиля до включения её в работу).
- Разбор ошибок: список FN/FP с причиной — основа для правки ключевых слов, ОКПД2, режима `narrow`.

**Этап 2. Матрица (слой C).** Выгрузка исправлений в эталон (требование, производитель, верный
статус, причина). Прогон `compliance_service` на этих ячейках в режиме «без прецедентов»
и «с прецедентами из обучающей части». Метрика — совпадение вердикта; ИИ вызывается, поэтому
запуск ручной, с лимитом токенов.

**Этап 3. Заключение и оценка (слой D).** Несогласия специалистов превращаем в кейсы:
закупка + что не устроило. Оценка — «проверочный список» по тексту замечания (учёл ли пересмотр
возражение), часть через модель-судью, с выборочной проверкой человеком.

**Этап 4. Регулярность.** Недельный прогон (cron/планировщик), таблица тренда в «Логирование»
или отчёт в `logs/`; порог-сторож: падение recall > 3 п.п. — красный флаг. Любая правка профиля,
промпта или модели сопровождается прогоном «до / после».

**Этап 5. Сбор недостающей разметки в интерфейсе.** Причина «Неактуально», аудит-выборка
отсеянного, оценка ячеек матрицы с покрытием на дашборде.

## 5. Порядок работы над проблемой

1. Метрика показывает провал в разрезе (например, recall по площадке X).
2. Выгружаем ошибки разреза, читаем 10–20 примеров, формулируем гипотезу.
3. Правка (профиль / промпт / правило), прогон `--replay` или ИИ-прогон на эталоне.
4. Сравнение «до / после» на hold-out; фиксируем в `ARCHITECTURE.md` и `changelog.ts`.

## 6. Критерии «стало лучше»

- Отбор: recall не ниже прежнего, precision выше (или наоборот) на hold-out, без регрессий по площадкам.
- Матрица: согласие специалистов растёт, доля `fact`/`requirement`-исправлений падает.
- Заключение: падает доля повторных несогласий по одной теме.
