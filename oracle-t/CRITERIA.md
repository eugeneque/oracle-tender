# Критерии оценки соответствия продукции МИРТЕК техническому заданию заказчика

Методика, по которой Sova Scanner строит матрицу соответствия и «процент победителя»
(раздел 5.5 ТЗ, вкладка «Конкуренция» карточки закупки). Документ — источник истины для
кода: `backend/app/services/compliance_service.py` обязан ему соответствовать, а
расхождение — ошибка в коде, а не в документе. Составлен 17.09.2026 по замечанию
тестировщика «разработать критерии оценки соответствия продукции МИРТЕК ТЗ заказчика».

Оценка отвечает на два вопроса: **подходит ли конкретный прибор под ТЗ** (вердикт по
каждому требованию) и **насколько заявка с этим прибором конкурентоспособна** (процент и
сравнение с конкурентами). Она не заменяет решение об участии — она делает его
проверяемым: у каждого числа есть требование, факт и источник факта.

## 1. Что оценивается

Оцениваются **требования к товару** — проверяемые условия к прибору учёта, его
характеристикам, комплектации, допускам и сопроводительным документам, извлечённые из
документации закупки (вкладка «Требования»). Строка спецификации («Счётчик СЕ208, 30 шт.»)
— тоже требование: к типу прибора.

**Не оцениваются** и в матрицу не попадают: требования к участнику (опыт, лицензии, СРО,
отсутствие в РНП), условия контракта, сроки и порядок оплаты, требования к заявке. Они
извлекаются отдельно во вкладку «Дополнительно» и участвуют в AI-оценке по профилю
(раздел 5.5.1 ТЗ), но к соответствию продукции отношения не имеют.

Сопоставление ведётся по **каждому производителю справочника** (МИРТЕК и конкуренты) —
для МИРТЕК это ответ «подходит ли наш прибор», для конкурентов — «кто ещё пройдёт и с
каким счётом».

## 2. Классы требований и источники истины

Каждое требование относится к одному из классов. Класс определяет, **какой факт может
подтвердить или опровергнуть требование** и откуда этот факт берётся. Факт из другого
источника решением не считается.

| Класс | Примеры требований | Источник истины | Пометка факта |
|---|---|---|---|
| A. Метрологические и электрические | класс точности, Uном, Iном/Iмакс, число фаз, частота, стартовый ток, межповерочный интервал, наличие в Госреестре СИ | «Описание типа» из ФГИС «Аршин» (в т.ч. структура условного обозначения — допустимые исполнения) | `[si_type]` |
| B. Функциональные, интерфейсы, протоколы, конструктив | реле, профили нагрузки, тарифы, RS-485/PLC/RF/GSM, СПОДЭС/DLMS, степень защиты, диапазон температур, крепление | каталог продукции (характеристики Приложения C); если каталог молчит — руководство по эксплуатации | `[catalog]`, затем `[manual]` |
| C. Допуски и реестры | реестр российской промышленной продукции (ПП РФ № 719, ГИСП), заключение аттестационной комиссии ПАО «Россети» (ЗАК) / «Перечень допущенного оборудования», реестр российского ПО | записи о допуске у модели каталога (номер, дата, срок действия; либо «проверено: записи нет») | `[registry]` |
| D. Интеграция в ПО верхнего уровня | «интеграция в ПК Пирамида / Энфорс / Энергосфера / яЭнергетик / АльфаЦЕНТР / Некта / ЛЭРС», «в ПО верхнего уровня» без названия | официальные списки поддерживаемого оборудования на сайтах разработчиков ПО | `[software]` |
| E. Комплектация, документация, гарантия | паспорт, поверка при поставке, пломбы, срок гарантии, комплект крепежа | каталог, руководство | `[catalog]`, `[manual]` |
| F. Тип и наименование прибора | «счётчик трёхфазный многотарифный», «СЕ208 или эквивалент» | описание типа + каталог | `[si_type]`, `[catalog]` |

Пять источников фактов подаются модели **с пометкой происхождения**; в матрице у каждого
вердикта показан источник, по которому он вынесен.

## 3. Правила вердикта

По каждой паре «требование × производитель» выносится ровно один из четырёх статусов.

| Статус | Когда ставится | Вклад в оценку |
|---|---|---|
| **соответствует** (`meets`) | есть факт, прямо подтверждающий выполнение требования | 1,0 |
| **частично** (`partial`) | требование выполняется частично, только для части исполнений, или подтверждено косвенно (например, поддержка по протоколу без конкретной модели) | 0,5 |
| **не соответствует** (`not_meets`) | есть факт, прямо противоречащий требованию | 0,0 |
| **нет данных** (`no_data`) | ни подтверждающего, ни опровергающего факта нет | не участвует |

Главное правило: **отсутствие упоминания — это «нет данных», а не «не соответствует»**.
«Не соответствует» означает «прибор точно не подходит», и ставить его из-за неполноты
справочника нельзя: процент занижался бы из-за состояния базы, а не из-за свойств прибора.
Исключения из этого правила названы явно — там источник полный и официальный (п. 3.3, 3.4).

### 3.1. Числовые и перечислимые параметры (классы A, B, F)

- Точное совпадение или лучшее значение — `meets` («класс точности не хуже 1,0», у прибора 0,5S — соответствует; «не хуже» / «не менее» / «не более» трактуются по смыслу параметра).
- Требуемое значение внутри заявленного диапазона — `meets` (диапазон температур −40…+70 покрывает требуемый −30…+60).
- Требуемое значение достигается только частью исполнений типа (по структуре условного обозначения) — `partial` с указанием исполнения; матрица показывает лучшую модель.
- Заявленное значение хуже требуемого или требуемая опция у типа не предусмотрена вовсе — `not_meets`.
- Наименование конкурента с оговоркой «или эквивалент» — оценивается как требование к типу прибора по параметрам, а не по имени.

### 3.2. Каталог и руководство (классы B, E)

Руководство по эксплуатации — **запасной источник**: подключается только к требованиям,
оставшимся без данных после описания типа и каталога (раздел 5.5 ТЗ, шаг 3). Значение,
подтверждённое человеком в каталоге, имеет приоритет над извлечённым автоматически.

### 3.3. Допуски и реестры (класс C)

Состояние записи считается **кодом по датам**, а не моделью:

| Состояние записи | Вердикт |
|---|---|
| действует (срок не истёк или не ограничен) | `meets` |
| истекает (менее 90 дней до конца срока) | `meets`, но в пояснении — дата окончания: к поставке допуск может кончиться |
| истекла | `not_meets` — ТЗ требует **действующее** заключение |
| проверено: записи в реестре нет | `not_meets` |
| запись не заведена | `no_data` |

Записи о допуске ведутся вручную в карточке модели (раздел «Реестры допуска»): сами реестры
закрыты для автоматической сверки. У каждой записи — номер, даты, ссылка на карточку в
реестре и отметка «сверено» с датой. Наличие в **Госреестре СИ** — не реестр допуска, оно
проверяется по описанию типа (класс A).

### 3.4. Интеграция в ПО верхнего уровня (класс D)

Списки разработчиков ПО официальные и полные, поэтому здесь действует обратное правило:

- прибор производителя есть в списке названного ПО — `meets`;
- в списке названного ПО приборов производителя **нет** — `not_meets` (это факт, а не отсутствие данных);
- поддержка заявлена только по протоколу СПОДЭС, без конкретной модели — `partial`;
- ПО в требовании не названо («в ПО верхнего уровня») — достаточно присутствия хотя бы в одном списке;
- список требуемого ПО системой не прочитан — `no_data`.

## 4. Критичность требований

Критичность назначается при извлечении требования по правилам ниже и определяет его
**вес** в проценте. Подтверждённые человеком требования при повторном анализе сохраняются
вместе с их критичностью.

| Критичность | Вес | Что относится |
|---|---|---|
| **критичное** | 3 | без выполнения заявку отклонят: класс точности, номинальные ток и напряжение, число фаз, тип прибора, наличие в Госреестре СИ, допуски-реестры (ПП 719, ЗАК Россетей, реестр ПО — когда их требует ТЗ) |
| **важное** | 2 | существенно влияет на выбор: интерфейсы, протоколы, реле, диапазон температур, межповерочный интервал, интеграция в ПО верхнего уровня, комплектация |
| **второстепенное** | 1 | цвет корпуса, упаковка, пожелания без «должен» |

## 5. Расчёт процента

Формула раздела 5.5 ТЗ:

```
процент = Σ(вес × вклад статуса) / Σ(вес требований с определённым статусом) × 100
```

- Требования со статусом «нет данных» **исключаются из знаменателя**: процент показывает соответствие по тому, что удалось проверить, а не наказывает за пустоту каталога.
- Рядом с процентом всегда указано, **по скольким требованиям из скольких** он посчитан. Если оценено меньше 30 % требований, процент помечается как **ненадёжный** — 100 % по трём требованиям из пятидесяти ничего не значат.
- **Невыполненное критичное требование** называется в пояснении к проценту прямо («не выполнены критичные требования: …»): заявку отклонят независимо от того, сколько остальных требований выполнено. Само число при этом не подменяется — методика ТЗ считает его арифметически, а решение «не идти» принимает человек по названной причине.
- Пересчёт не правит прежнюю оценку, а гасит её и записывает новую: история пересчётов объясняет, почему процент изменился после пополнения каталога.

Цветовая интерпретация — та же, что у AI-оценки: **≥ 80 %** зелёный (подходит),
**50–80 %** жёлтый (подходит с оговорками — смотреть, какие требования не закрыты),
**< 50 %** красный (не подходит или данных слишком мало).

## 6. Уверенность и проверка человеком

- У каждого вердикта есть уверенность 0–1. Точное совпадение числового параметра — около 1,0; вывод по смыслу — 0,5–0,7; детерминированные вердикты по реестрам и спискам ПО — 0,9–1,0.
- Вердикт с уверенностью **ниже 0,6** помечается «требует проверки человеком» и выделяется в матрице; «нет данных» такой пометки не получает — там проверять нечего.
- Пояснение к вердикту обязательно: одно предложение — какой факт из карточки к нему привёл, либо чего именно не хватает.

## 7. Что делать с результатом

1. Критичное «не соответствует» у МИРТЕК — участие возможно только после уточнения у заказчика или выбора другой модели; матрица показывает лучшую модель, но человек проверяет исполнение.
2. «Нет данных» по критичному требованию — сначала пополнить справочник (карточка модели: характеристики, реестры допуска, документация), затем пересчитать; процент без этих данных ненадёжен.
3. Сравнение с конкурентами читается по той же матрице: конкурент с более высоким процентом при том же покрытии — реальная угроза; конкурент с 100 % по пяти требованиям из сорока — нет.
