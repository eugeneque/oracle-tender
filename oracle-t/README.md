# ORACLE-T (Oracle-Tender)

Платформа автоматизированного сбора и анализа тендерной информации. Реализация по ТЗ
«САСТ-Тендеры» v2.0 (`../ТЗ/ТЗ/ТЗразработка.md`). Архитектура всей системы — в
[ARCHITECTURE.md](./ARCHITECTURE.md). На данный момент реализованы **Этап 0** (инфраструктура),
**Этап 1** (аутентификация и пользователи), **Этап 2** (сбор тендеров: адаптерная архитектура,
планировщик, дедупликация; источники подключаются волнами — см. раздел «Источники тендеров»
ниже и `/settings` в интерфейсе) и **Этап 3** (загрузка и разбор документов: PDF/DOCX/XLSX →
текст, OCR-fallback для сканов без текстового слоя — раздел «Карточка тендера и документы»
ниже; разбор документов самих источников пока реализован только у ЕИС, у остальных —
следующий шаг вместе с Этапом 12). **Этап 4** (справочник продукции) — реализован:
13 производителей (раздел 4.3 ТЗ), справочник характеристик Приложения C, автопоиск кодов СИ
через ФГИС, AI-экстракция характеристик через YandexGPT — из «Описания типа» и из
«Руководства пользователя» на сайте производителя (обе проверены вживую), админ-CRUD каталога,
CSV-импорт и раздел «Каталог продукции» в интерфейсе (см. ARCHITECTURE.md, раздел 12).
С 04.09.2026 оба источника характеристик — **полноценные источники в планировщике**, а не
разовые операции по кнопке: ФГИС ревалидирует сохранённые карточки типов СИ по расписанию и
ищет по событию из модуля сопоставления (с защитой от коллизии наименований в реестре —
случай «Пульсар»), каталоги на сайтах производителей обходятся раз в неделю и наполняют справочник —
`mirtekgroup.com` собственной продукцией, сайты Энергомеры, КПЗ и Промэнерго — продукцией
конкурентов (см. ARCHITECTURE.md, разделы 28 и 29). Найденные коды СИ подставляются к
моделям автоматически.
Подключение к Yandex AI Studio настраивается в разделе «Интеграции» на `/settings` — **нужен
Folder ID папки, а не облака** (см. ARCHITECTURE.md, раздел 11).

**Этапы 5 и 6** (ИИ-анализ требований и матрица соответствия) — реализованы: из документации
тендера извлекаются требования с критичностью, тип конкурса, ОКПД2 и регион; по каждому
производителю строится матрица соответствия с пояснениями и считается «процент победителя»
(ARCHITECTURE.md, раздел 13). Запускается из карточки тендера кнопками «Анализ документов» и
«Расчёт соответствия». Обе операции выполняются **фоновой задачей**: ответ приходит сразу,
карточку можно закрыть, а ход работы виден в разделе «Логирование» настроек. Сбой обращения
к модели повторяется автоматически (ARCHITECTURE.md, раздел 17). Методика оценки —
классы требований, источники истины, правила вердикта, веса и формула процента — описана в
[CRITERIA.md](./CRITERIA.md); коротко она же раскрывается на вкладке «Конкуренция» («Как
считается соответствие»).

**Допуски: реестры и аттестация.** Требования «включён в реестр российской промышленной
продукции (ПП 719)», «действующее ЗАК ПАО „Россети“», «ПО в реестре Минцифры» проверяются
по записям о допуске в карточке модели каталога (номер, даты, ссылка на реестр); состояние
«действует / истекает / истекла / записи нет» считается по датам, а в карточке закупки блок
«Допуски» над матрицей показывает его по каждому производителю. Сами реестры заведены в
«Источники» с проверкой доступности — автоматической сверки нет, они закрыты для роботов
(ARCHITECTURE.md, раздел 37).

**Ручные заявки** — кнопка «Новая заявка» на странице тендеров: закупка, которую заказчик
прислал напрямую (проект договора, ТЗ), заводится руками с приложенными файлами и проходит
тот же ИИ-анализ, матрицу соответствия и карточку, что и собранные тендеры. Файл можно
приложить и к уже собранной закупке — кнопка «Добавить файл» во вкладке «Документы»
(ARCHITECTURE.md, раздел 34).

**Список по умолчанию и избранное.** Страница тендеров по умолчанию показывает только
открытые закупки, прошедшие профиль релевантности, — строка «Показано N из M собранных» под
шапкой говорит об этом прямо, ссылка «Показать все собранные» снимает оба фильтра.
Закупку можно отложить звёздочкой в карточке; раздел «Избранное» (кнопка рядом с
«Фильтры») показывает отложенное независимо от срока подачи и профиля. Поля для фильтров —
ОКПД2, регион, тип конкурса — дозаполняются из карточек ЕИС и по наименованию после
каждого опроса (`TENDER_GAPS_FILL_ENABLED`, `oracle-t-cli fill-gaps`; ARCHITECTURE.md,
раздел 36).

**Учётные данные площадок** — раздел «Пользовательские данные» в `/settings` (только для
роли «Администратор»): блоки «площадка → логин → пароль» для источников, требующих входа в
личный кабинет. Пароль шифруется ключом из файла `.credentials_key` в корне проекта
(создаётся автоматически, лежит вне базы и вне `.env`, добавлен в `.gitignore`), хранится в
локальной БД и переживает перезагрузку. Обратно через API пароль не отдаётся — его можно
только заменить. **Не удаляйте `.credentials_key`**: без него сохранённые пароли не
восстановить (ARCHITECTURE.md, раздел 15).

**Этап 7** (веб-интерфейс тендеров) — реализован: список с фильтрами (дата, регион, тип
конкурса, статус, сумма, ОКПД2, AI-оценка, процент соответствия, этап, релевантность),
серверной сортировкой по любому столбцу и постраничной выдачей; карточка тендера с
вкладками, исправлением классификации, отметками релевантности и комментариями — всё с
записью в историю и журнал (ARCHITECTURE.md, раздел 14).

**AI-оценка по профилю (решение 03.09.2026)** — главная метрика тендера, реализована:
три измерения (History / Task / Competencies), «Резюме» с вердиктом ИДТИ / ИДТИ С
ОГОВОРКАМИ / НЕ ИДТИ, список слабых мест со значимостью и рекомендуемая стратегия.
Считается по тексту тендера и **профилю компании** («Настройки → Профиль компании»): без
него Task и Competencies считать не из чего, и расчёт честно отказывается с подсказкой.
Каждое число прослеживаемо до источника — под каждым измерением раскрывается список
требований и полей профиля, из которых оно сложилось. History без данных показывается как
«недостаточно данных» и **исключается** из итога, а не считается нулём (ARCHITECTURE.md,
раздел 23).

Вместе с ней:

* **Этапы тендера** (`stage`): AI отобрал → на проверке → заявка подана → выиграли /
  проиграли / отклонён. Kanban переведён на этапы; статус закупки на площадке остался
  отдельным фильтром и бейджем. Прежнее поле `relevance_status` во внешнем API, выгрузке и
  Bitrix-интеграции сохранено — оно вычисляется из этапа.
* **Двухпанельный режим** (список слева, карточка справа) — новый режим отображения и
  режим по умолчанию; Kanban, таблица и таймплан остались на прежнем переключателе.
* **Вкладки карточки** по разделу 5.6 ТЗ: Основное, Дополнительно (девять разделов
  извлечённых из документации условий — допуски, условия контракта, требования к заявке),
  Документы (автоклассификация типа и звёздочка «считать в первую очередь по этому файлу»),
  Расчёт, Конкуренция, Заявка, Похожие.
* **Похожие тендеры** — по близости текста через Yandex AI Studio Embeddings; пока корпус
  не накоплен, вкладка честно говорит «недостаточно данных».
* **Уведомления** переведены на AI-оценку: порог настраивается там же, где раньше был порог
  процента победителя (значение сохраняется при обновлении).
* **«Моя компания»** (04.09.2026) — отдельный раздел в боковом меню, а не секция настроек:
  профиль и история участий питают главную метрику каждого тендера и пополняются регулярно,
  прятать их за «Настройками» неправильно. Две вкладки — «Профиль компании» и «История
  участий».
* **История участий** — реальная история участия компании в закупках, **основной источник
  измерения «История»**: оно считается по нашим участиям в похожих закупках и у того же
  заказчика. Наполняется автоматически двумя путями:
  * **победы** — выгрузка из реестра контрактов ЕИС по ИНН компании;
  * **проигрыши** — вычисляются: закупка, отмеченная как «заявка подана», завершилась, а
    контракт достался не нам. Выгрузить их неоткуда — реестра протоколов с поиском по
    участнику в ЕИС не существует, а в протоколах электронных процедур участники обезличены
    номерами заявок, раскрывается только победитель.

  Сводка: участий / побед / проигрышей / **дисквалификаций отдельно** / win-rate. Пока в
  истории одни победы из реестра контрактов, win-rate равен 100% по устройству выборки, а не
  по заслугам — интерфейс говорит об этом прямо, а измерение «История» по таким данным долю
  побед **не считает** и остаётся в состоянии «недостаточно данных». Повторное обновление не
  затирает то, что вписал человек: заметку «Выводы» и проставленный вручную исход.

  *Синхронизация с OPTI, предполагавшаяся в ЧТЗ, отменена: у сервиса нет ни публичного API,
  ни выдаваемых нам токенов, а данные ЕИС открыты и ключа не требуют.*
* **Юридические данные компании** — наименование, ИНН, **КПП**, ОГРН, дата регистрации и
  адрес. Автопоиск за одной кнопкой ходит в два источника: ссылка на карточку rusprofile
  разбирается напрямую (единственный путь, дающий КПП — в выдаче ЕГРЮЛ его нет), а ИНН, ОГРН
  или название ищутся в ЕГРЮЛ. Найденное подставляется в форму, но **не сохраняется**:
  записывает человек кнопкой «Сохранить».
* **Профиль релевантности** (04.09.2026) — что система вообще считает «нашим» тендером.
  Раньше охват был константой в коде: каждый адаптер искал две фразы, «счетчик электрической
  энергии» и «прибор учета электрической энергии», поэтому поверка, монтаж, замена,
  техобслуживание и АСКУЭ **не попадали в систему вовсе**. Теперь это девять групп
  потребностей с ключевыми словами, исключениями и своими кодами ОКПД2 — 13 поисковых фраз
  вместо двух.

  У рабочих групп обязательны исключения: «поверка счётчиков» без запрета на воду, газ,
  тепло и медицину собирает поверку чего угодно. Не прошедший фильтр тендер **не удаляется**
  — он скрыт галочкой «Только прошедшие профиль релевантности» и виден при её снятии, потому
  что профиль настраивают люди и он может оказаться слишком узким. Настраивается в
  «Настройках → Профиль релевантности», там же кнопка пересчёта по всем собранным тендерам.
* **Виды отображения** — «Две панели» (по умолчанию), Kanban и «Таблица». Виды «Список» и
  «Таймплан» убраны: первый дублировал левую колонку двухпанельного режима, второй — сроки
  из таблицы.
* **Фильтры свёрнуты по умолчанию** — всегда видны поиск, вилка суммы и срок подачи;
  остальное (регион, ОКПД2, AI-оценка, площадки, этап, статус) раскрывается кнопкой «Ещё
  фильтры».
* **«Подобрано ИИ»** (04.09.2026) — модель сама решает, действительно ли закупка профильная,
  и такие идут в списке первыми. Профиль ключевых слов отбирает кандидатов дёшево и слепо
  («есть нужные слова»), модель проверяет их по смыслу — отличает поставку счётчиков от
  стройки, где приборы учёта упомянуты в составе объекта. Новые закупки проверяются сами при
  сборе, накопленный архив — кнопкой «Проверить моделью» в настройках. Сбой модели оставляет
  закупку непроверенной, а не отклонённой: авария не должна прятать тендер из списка.
* **Страница тендеров переработана** — прокручивается только содержимое, а не вся страница:
  карточку закупки больше не нужно «доставать» скроллом. Верх собран в одну строку: поиск,
  переключатель видов, кнопка «Фильтры» с числом активных условий и счётчик «Найдено N
  тендеров». Панель фильтров по умолчанию свёрнута.
* **Дедупликация между площадками** — одна закупка, опубликованная и в ЕИС, и на ЭТП, больше
  не попадает в список дважды: записи сводятся по реестровому номеру закупки.
* **Время** — хранится в UTC, показывается в МСК явно (и в интерфейсе, и в шапке
  Excel-выгрузки), независимо от часового пояса сервера и браузера.

**Карточка закупки целиком** — в модальном окне тендера теперь есть всё, что видно на
сайте источника: сведения о заказчике с ИНН и адресом, контактное лицо с почтой и телефоном,
порядок предоставления документации, список лотов, изменения и разъяснения, протоколы,
сведения о договорах и журнал событий. Данные забираются с `zakupki.gov.ru` — в том числе
для закупок с коммерческих площадок: страница ЕИС есть у любой закупки 44-ФЗ и 223-ФЗ, и
данных на ней больше, чем в карточке площадки.

**Регион определяется автоматически.** Раньше он заполнялся только ИИ-анализом документации,
которого на большинстве закупок никто не запускал, — тысячи тендеров висели с «регион не
определён», хотя на странице ЕИС регион есть всегда. Теперь он берётся из адреса заказчика
(сверкой со справочником Приложения H) и из первых двух цифр ИНН — это код субъекта в
справочнике ФНС. Источник значения записывается в историю тендера: подставленное системой
значение отличимо от введённого человеком и проверяемо. Для уже собранных тендеров есть
команда дозаполнения:

```bash
cd backend
POSTGRES_HOST=localhost .venv/bin/python -m app.cli backfill-cards --limit 500
```

**Разбор ИИ прямо в карточке** — блок «Разбор ИИ» на вкладке «Обзор» (со светящейся сферой,
чтобы граница между данными источника и суждением модели была видна). Модель читает карточку
целиком и возвращает: суть закупки простым языком, риски с указанием того, на чём основан
вывод, чего не хватает в данных, восстановленные из текста значения (контакты, сроки, регион)
и чек-лист «что проверить перед подачей». Это не замена анализу документов: там разбирается
документация и извлекаются технические требования, здесь — сама карточка.

**Документы площадок** — реальные файлы документации теперь скачиваются со **всех девяти
подключённых площадок**, а не только с ЕИС. У каждой площадки свой способ: ЭТП ГПБ и ЕЭТП
отдают ссылки в серверном HTML карточки, ТЭК-Торг — в состоянии Next.js со ссылками на своё
открытое API, Фабрикант — отдельной страницей документации, Сбербанк-АСТ дорисовывает таблицу
файлов скриптом (нужен браузер). Там, где площадка не показывает файлы анонимно (Lot-online,
Росэлторг, ЭТП РФ), документы берутся **из ЕИС по реестровому номеру закупки**: закупки
44-ФЗ и 223-ФЗ публикуются там по закону, независимо от площадки проведения
(`app/adapters/eis_documents.py`).

**Форматы документов.** Кроме PDF/DOCX/XLSX разбираются `.doc` и `.xls` (Word/Excel
97-2003 — основной формат документации коммерческих площадок), `.rtf`, а также архивы
`.zip`, `.7z` и `.rar` — документацию часто выкладывают одним комплектом. Разбор `.doc`
собственный, без внешних конвертеров (`app/services/doc_binary.py`); RAR распаковывается
системным `bsdtar`, который есть в macOS и большинстве Linux. Тип файла определяется и по
содержимому — часть площадок отдаёт документ по ссылке без расширения.

**Интеграция с Bitrix24** (Этап 13) — раздел «Интеграция с Bitrix24» в `/settings`:

- **выгрузка лидов** (`GET /export/bitrix24-leads.csv`) — CSV с полями лида CRM: название,
  компания-заказчик, сумма, ответственный по региону, номер закупки, ОКПД2, сроки, процент
  победителя, ссылка. Вторая строка файла — технические имена полей, по ним Bitrix24
  сопоставляет колонки при импорте;
- **внешний REST API** (`/api/integration/v1/tenders`, `/tenders/{id}`, `/leads`, `/health`)
  с доступом по ключу в заголовке `X-API-Key`. Ключи выпускает администратор в том же
  разделе; ключ показывается один раз, в базе хранится только его хеш. Реальных вызовов к
  Bitrix24 нет — ТЗ выносит их во вторую очередь.

**Логирование и уведомления** (Этапы 10-11) — два новых свёрнутых блока в `/settings`:

- **«Логирование»** — журнал операций системы в виде, близком к терминалу: уровень,
  компонент, действие, результат, детали и пользователь, с фильтрами по уровню, компоненту,
  периоду и поиском. Обновляется сам, пока раздел открыт (кнопка «слежение»/«пауза»).
  Доступен **всем пользователям**: по нему видно, почему у тендера нет требований или почему
  площадка не опрашивалась. Записи хранятся 6 месяцев, уборка — ночью по расписанию.
- **«Уведомления»** — журнал отправленных писем (всем пользователям) и настройки почтового
  ящика (только «Администратор»). Четыре триггера раздела 5.8 ТЗ: новый релевантный тендер,
  высокий процент победителя (порог настраивается, по умолчанию 80%), приём заявок
  закрывается меньше чем через N дней (по умолчанию 5), критическая ошибка системы —
  отдельным адресатам. Пока ящик не заполнен, события всё равно пишутся в журнал со статусом
  «не отправлено» — так видно, что триггеры работают (ARCHITECTURE.md, раздел 18).
  Там же администратор может написать **произвольное письмо** пользователям — о новостях
  платформы, работах, изменениях: редактор с форматированием (полужирный, курсив, списки,
  заголовки, ссылки) и поле получателей, которое подсказывает адреса, на которые система уже
  отправляла письма. Разметка очищается на сервере по белому списку тегов, письмо уходит
  двумя частями (оформленной и текстовой) и попадает в общий журнал с пометкой автора.

**Почта: нужны данные SMTP, а не IMAP.** IMAP читает входящие, отправляет — SMTP. Логин и
пароль у ящика те же, отличается только адрес сервера: `smtp.yandex.ru:465` (SSL),
`smtp.mail.ru:465`, у корпоративной почты — свой. Пароль шифруется тем же ключом
`.credentials_key`, что и пароли площадок, и обратно через API не отдаётся.

**Ящик задаётся в `.env` (`NOTIFY_*`), адресаты — в интерфейсе.** Отправитель один на
установку и заводится админом почтового домена, поэтому он переносится из `.env` в базу при
первом запуске — иначе после пересоздания базы рассылка молча выключалась бы. Дальше `.env`
не читается: всё правится в «Настройки → Уведомления», и правки не откатываются при
перезапуске. Проверить ящик на сервере, не открывая браузер и не отправляя письма:

```bash
cd backend && ./.venv/bin/python -m app.cli check-mail
```

## Быстрый старт для разработки (без Docker)

Важно: `frontend/index.html` — это Vite-приложение (React/TypeScript), его **нельзя** открыть
двойным кликом в браузере как обычный HTML-файл — браузер не умеет собирать TS/JSX на лету.
Нужно поднять dev-сервер, и именно его адрес открывать в браузере.

Проще всего — один скрипт, который сам поднимает Postgres (через Homebrew), накатывает миграции
и запускает backend + frontend:

```bash
./run.sh
```

Требуется заранее один раз поставить (если ещё не стоит):

```bash
brew install python@3.11 postgresql@15 tesseract tesseract-lang
```

`tesseract-lang` ставит языковые пакеты (в т.ч. `rus`) — нужны для OCR-fallback при разборе
сканированных PDF без текстового слоя (Этап 3, раздел 5.2 ТЗ). Без tesseract система по-прежнему
работает — просто у отсканированных документов не будет извлечённого текста, они не перестают
скачиваться и сохраняться.

RAR-архивы распаковываются системным `bsdtar` — он входит в macOS, ставить ничего не нужно;
в Docker-образе он устанавливается пакетом `libarchive-tools`. Остальные форматы (`.doc`,
`.xls`, `.rtf`, `.zip`, `.7z`) разбираются библиотеками Python без внешних программ.

После `./run.sh` открой в браузере **http://localhost:5173** (не `index.html` из проводника/Finder!).
API — на `http://localhost:8000/health`. Логин/пароль первого администратора — в `.env`
(`BOOTSTRAP_ADMIN_USERNAME` / `BOOTSTRAP_ADMIN_PASSWORD`, создаётся при первом запуске). Остановить
всё — `Ctrl+C` **или просто закрыть окно терминала**: скрипт гасит backend и frontend по обоим
сигналам, включая тот, что приходит при закрытии окна.

**Адреса всегда одни и те же** — 5173 и 8000, без «а сегодня почему-то 5175». Занятый порт
означает недобитый прошлый запуск (окно закрыли жёстко, процесс сняли `kill -9`), и скрипт
сам его останавливает перед стартом — но только свой: процесс постороннего проекта он не
трогает, а честно скажет, кто занял порт, и остановится. У Vite для этого выключен подбор
свободного порта (`strictPort`), иначе он молча уезжает на соседний, и открытая вкладка
показывает вчерашний стенд.

Backend поднимается с автоперезагрузкой: правки в `backend/**.py` подхватываются без
перезапуска скрипта — иначе легко час отлаживать поведение, которого в работающем процессе
уже нет. Отключается `RELOAD=0 ./run.sh`; порты меняются `BACKEND_PORT=... FRONTEND_PORT=...`.

Скрипт идемпотентен: при повторном запуске просто переиспользует уже созданные venv/БД/зависимости.

### Логин/пароль администратора — сброс или узнать текущий

Пароль администратора никогда не хранится в базе в открытом виде, поэтому его нельзя
«посмотреть» — только сбросить на новый. Для этого есть отдельная команда, её можно запускать
сколько угодно раз: она либо создаст администратора, либо перезапишет пароль уже существующего,
и сохранит логин/пароль в `.env` (и в корне проекта, и в `backend/.env`).

```bash
cd backend
source .venv/bin/activate
python reset_admin.py                          # сгенерирует случайный пароль
python reset_admin.py --password MyNewPass123   # или задать пароль самому
python reset_admin.py --username ivan --password Pass1234 --full-name "Иван Иванов"
```

Команда печатает итоговые логин/пароль в терминал и пишет их в `.env`, поэтому смотреть текущее
значение проще всего в `.env` (`BOOTSTRAP_ADMIN_USERNAME` / `BOOTSTRAP_ADMIN_PASSWORD`) — но если
пароль забыт/потерян, надёжнее просто запустить `reset_admin.py` заново.

## Docker Compose

В `docker-compose.yml` три службы: `db` (PostgreSQL 15), `backend` (образ с tesseract, bsdtar
и браузером Playwright, миграции накатываются при старте) и `frontend` (сборка Vite, которую
раздаёт nginx). Наружу открыт один порт — веб-интерфейс; API доступен по тому же адресу на
`/api/`, а backend и Postgres в хостовую сеть не выставлены.

```bash
cp .env.example .env   # заполнить пароли/секреты
docker compose up -d --build
```

Проще запустить это установщиком — он сам сгенерирует секреты и дождётся готовности:
`./install.sh --mode docker` из корня репозитория. Порт интерфейса меняется переменной
`HTTP_PORT` в `.env` (или ключом `--http-port`).

**Ключ шифрования учётных данных площадок в контейнере живёт в `.env`**
(`CREDENTIALS_ENCRYPTION_KEY`), а не в файле `.credentials_key`: файл лежит внутри образа и
исчез бы при пересборке, а вместе с ним стали бы нечитаемыми все сохранённые пароли от личных
кабинетов ЭТП. Установщик создаёт этот ключ сам; при ручной настройке сгенерировать его можно
так:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

## Источники тендеров (Этап 2)

Источники раздела 4.1 ТЗ (ЕИС + коммерческие ЭТП) подключаются волнами (раздел 9 ТЗ,
Этап 2 → Этап 12): сначала технически простые (серверный HTML, без JS), затем те, что требуют
Playwright, а для действительно проблемных (антибот-защита, пейволы) — площадка остаётся в
системе только как запись в справочнике источников (видна в `/settings`) с примечанием о
причине. Текущий статус каждого источника — там же, в интерфейсе, или через
`python -m app.cli list-sources`.

**Доступность площадок** проверяется автоматически раз в минуту, независимо от того,
реализован ли адаптер (`app/services/availability_service.py`) — лёгкий пинг URL источника, без
скачивания содержимого. В «Настройках» рядом с каждым источником — «Доступно» / «Недоступно» с
краткой причиной (таймаут, HTTP-код, ошибка TLS и т.д.). Раздел «Источники тендеров» в
«Настройках» — сворачиваемый, чтобы не занимать место, когда появятся другие разделы настроек.

**Синхронизация со страницы «Тендеры»**: кнопка «Ресурсы» открывает модальное окно выбора
источников (выбор сохраняется в браузере), «Сохранить» сразу запускает их опрос, «Отмена» ничего
не применяет. Кнопка «Синхронизировать» повторно опрашивает ранее выбранные источники без
модального окна. На время опроса список тендеров блюрится и поверх показывается лоадер.

Реализовано пять адаптеров:

- **ЕИС** (`app/adapters/eis.py`) — HTML-скрапинг страницы результатов расширенного поиска
  (`httpx` + `BeautifulSoup`, верстка серверная, JS не нужен). Публичный экспорт открытых
  данных ЕИС (`/epz/opendata/`, исторически раздававшийся и по FTP) недоступен — проверено при
  реализации, поэтому открытый вопрос №2 ТЗ решён в пользу скрапинга, как и предполагал раздел
  6.2 ТЗ.
- **Росэлторг** (`app/adapters/roseltorg.py`) — тоже обычный серверный HTML
  (`/procedures/search?query_field=...`), несмотря на React-виджеты в отдельных частях сайта.
- **ЭТП ГПБ** (`app/adapters/etpgpb.py`) — сайт на Nuxt/Vue, список процедур не рендерится
  на сервере (нужен клиентский JS), но при наблюдении за сетевыми запросами страницы нашёлся
  публичный JSON API (`/api/v2/procedures/?search=...`), которым сама страница и пользуется —
  Playwright не понадобился, `httpx` напрямую к API быстрее и надёжнее.
- **ЕЭТП / zakazrf** (`app/adapters/zakazrf.py`) и **ЭТП РФ** (`app/adapters/etprf.py`) —
  сводный реестр извещений на обеих площадках сам по себе обычный серверный HTML (у обеих —
  один и тот же грид-движок, судя по идентичным CSS-классам и именам полей формы, похоже общий
  вендор-шаблон), но быстрый поиск реализован через AJAX-постбэк с недокументированным
  контрактом (динамические ID полей формы на каждой загрузке) — воспроизводить его напрямую
  через httpx ненадёжно. Оба адаптера используют Playwright: реально вводят ключевое слово в
  поле поиска и нажимают «Найти», как пользователь, затем разбирают получившуюся таблицу тем же
  способом, что и остальные адаптеры.

**TLS-особенности** (важно при развёртывании на сервере вне РФ): сертификат `*.zakupki.gov.ru`
и `*.astgoz.ru` подписан государственным `Russian Trusted Sub CA` (Минцифры России), которого
нет в стандартном доверенном списке — для этих доменов клиент доверяет только сохранённой
цепочке `backend/app/certs/russian_trusted_ca.pem` (снята с боевого TLS-хендшейка). У `etprf.ru`
другая проблема — сервер не досылает промежуточный сертификат `GlobalSign GCC R6 AlphaSSL CA
2025` (частая ошибка конфигурации; корневой GlobalSign R6 давно в любом системном списке) —
недостающий сертификат (`backend/app/certs/globalsign_gcc_r6_alphassl_2025.pem`, официальный
публичный CA, скачан по ссылке из Authority Information Access самого сертификата) подставляется
к системному списку, не заменяя его. Логика — `app/adapters/http_utils.resolve_verify`; тот же
клиент использует и пинг доступности, поэтому оба источника стали «Доступно» без правок на их
стороне.

**Три площадки удалены из системы** (миграция `0038_remove_blocked_sources`, правка по итогам
показа 15.09.2026). Подключить их технически невозможно, и запись «заблокировано» в разделе
источников только путала пользователя — площадка есть, а тендеров с неё нет и не будет:
- **РТС-тендер** — намеренная защита от автоматизации («Anti-DDoS защита»): проверено, что даже
  реальный headless-браузер (Playwright, с ожиданием) её не проходит; попытки обхода (подмена
  fingerprint и т.п.) сознательно не предпринимались.
- **АСТ ГОЗ** — система торгов по гособоронзаказу; публичного списка закупок без входа и
  электронной подписи (КриптоПро) нет — легитимное ограничение доступа, не техническая проблема.
- **ЭТП ГПБ (Стратег)** — отдельный раздел ЭТП ГПБ для закрытых тендеров по приглашениям, без
  публичного списка (в отличие от основного раздела площадки, где как раз реализован адаптер).

В системе остаётся девять источников: ЕИС и восемь коммерческих ЭТП, у всех адаптер реализован.

**Playwright** ставится вместе с проектом (`requirements.txt`, `Dockerfile`, `run.sh`) — часть
оставшихся площадок из раздела 4.1 ТЗ рендерит список тендеров через JS-фреймворк без открытого
API: Фабрикант и Tektorg — на Next.js (у Фабриканта — с RSC, поток данных сериализован не как
обычный JSON), Сбербанк-АСТ — на Vue, Lot-online — на Angular. Все четыре — следующая волна
подключения.

Ручной опрос источника (не дожидаясь расписания 2 раза в день):

```bash
cd backend && source .venv/bin/activate
python -m app.cli list-sources
python -m app.cli poll-source eis
python -m app.cli poll-source roseltorg
python -m app.cli poll-source etpgpb
python -m app.cli poll-source zakazrf
python -m app.cli poll-source etprf
python -m app.cli ping-sources
```

## Документы по СИ и руководства: даты актуальности

Раздел «Каталог продукции» → блок «Документы по СИ и руководства». По каждой модели и
каждому коду СИ — руководство, паспорт, «Описание типа», сертификат, декларация с
актуальной датой документа и подписью, откуда дата взята (дата файла на сайте, редакция в
ФГИС или дата фиксации системой). Раз в неделю (вторник 06:00 МСК, настраивается
`DOCUMENT_REGISTRY_CHECK_ENABLED/WEEKDAY/TIME`) система сверяет документы с источниками; если
что-то переиздано, появилось, пропало или перестало открываться — на почту уходит
отдельный отчёт (триггер «Обновление документов по СИ и руководств» в настройках
уведомлений), он же остаётся в журнале отправок. Кнопка «Проверить актуальность» запускает
ту же сверку по одному производителю, не дожидаясь недели.

## Обучение по Аршину и поиск документации

Раздел «Каталог продукции» → блок «Обучение по Аршину». Система учится характеристикам
приборов всех производителей по реестру ФГИС (Аршин) и замечает изменения в «Описании
типа»: новая редакция или новое исполнение в карточке типа (у НАРТИС-И100 корпус W115
появился в реестре раньше, чем на сайте производителя) заводится в каталог с пометкой
«из реестра ФГИС · проверить», а его характеристики берутся из «Описания типа» и
расшифровки условного обозначения. Документацию на прибор, которого нет в каталоге сайта,
система ищет через Яндекс — только на официальном сайте производителя — и разбирает
найденное руководство.

Полный проход по всем производителям идёт раз в неделю (понедельник 08:00 МСК,
`CATALOG_LEARNING_ENABLED/WEEKDAY/TIME`), через очередь справочника; кнопка «Обучить
(в фоне)» запускает его по одному производителю, кнопки «Исполнения из реестра»,
«Разобрать „Описания типа“» и «Найти документацию» выполняют отдельные шаги сразу, а у
модели есть своя «Найти документацию». Поиск использует тот же API-ключ и Folder ID
Yandex Cloud, что и YandexGPT («Настройки → Интеграции»); ключу нужна роль
`search-api.executor`. Характеристики, которым не нашлось поля в Приложении C, не
теряются — они видны в карточке модели и в сводке «вне справочника» того же блока.

## Интеграция в ПО верхнего уровня

Требование «интеграция в ПО верхнего уровня» (часто с названием продукта — «Пирамида
2.0», «Энергосфера», «АльфаЦЕНТР») проверяется по спискам поддерживаемого оборудования на
сайтах семи разработчиков АСКУЭ: Пирамида (sicon.ru), Энфорс, ПК «Энергосфера»,
яЭнергетик, АльфаЦЕНТР, ПК «Некта», ЛЭРС УЧЁТ. Списки читаются раз в неделю (понедельник
10:00 МСК, `UPPER_SOFTWARE_SYNC_ENABLED/WEEKDAY/TIME`) и кнопкой «Прочитать» в блоке
«ПО верхнего уровня» раздела «Каталог продукции»; записи связываются с моделями справочника
по номеру ГРСИ и по обозначению. В каталоге видно, на каких площадках производитель есть,
а на каких его **нет**; у модели — подпись, в чьих списках она числится. В карточке закупки
(вкладка «Конкуренция») над матрицей стоит блок с требованиями об интеграции и матрицей
«производитель × ПО», а сама матрица соответствия ставит по таким требованиям
«не соответствует», если приборов производителя в проверенном списке нет
(ARCHITECTURE.md, раздел 35).

## Карточка тендера и документы

Клик по карточке тендера (в Kanban) открывает модальное окно с полными данными и списком
документов. Документы скачиваются лениво — при первом открытии карточки, а не при плановом
опросе источника (тысячи собранных тендеров никто не откроет, качать документацию по всем сразу
бессмысленно): `GET /tenders/{id}/documents` вызывает
`app/services/document_service.sync_tender_documents`, которая скачивает файлы через
`SourceAdapter.download_documents`, кладёт их в `storage/{tender_id}/{doc_id}.ext` и извлекает
текст (PDF — `pdfplumber`, DOCX — `python-docx`, XLSX — `openpyxl`; для сканов без
текстового слоя — OCR через tesseract, включается настройкой `OCR_ENABLED`). Повторное открытие той
же карточки просто отдаёт уже сохранённые записи, не перекачивая заново. Скачивание файла из
интерфейса (`GET /tenders/{id}/documents/{doc_id}/download`) идёт через наш собственный API — мы
не отдаём пользователю прямую ссылку на источник, файл реально хранится и раздаётся с нашего
сервера.

Реально разобрана карточка и документы пока только у **ЕИС** (`EisAdapter.get_tender_details`/
`download_documents` — раздел «Источники тендеров» ниже про TLS не при чём здесь, речь о разборе
вкладки «Документы» карточки закупки, отдельно для 44-ФЗ и 223-ФЗ, у которых разная верстка).
У остальных восьми адаптеров `download_documents` — временная заглушка (ссылка на карточку
тендера как единственный "документ") — по договорённости, следующим шагом.

**Карточка тендера** с 03.09.2026 собрана из вкладок раздела 5.6 ТЗ: «Основное» (AI-оценка
по профилю в шапке, основные поля, исправление классификации, разбор карточки ИИ),
«Дополнительно» (девять разделов условий закупки), «Документы» (автоклассификация типа,
звёздочка приоритетного источника, скачивание), «Расчёт» (статистика по нише),
«Конкуренция» (матрица соответствия характеристик по производителям), «Заявка» (чек-лист
пакета документов), «Похожие», а также служебные «Карточка закупки», «Требования» и
«История». Анализ документов, расчёт соответствия и AI-оценка запускаются кнопками в шапке
и выполняются **фоновой задачей**: карточку можно закрыть, ход виден в «Настройках →
Логирование».

Та же карточка показывается в правой части двухпанельного режима — это один и тот же
компонент, а не две копии.
