# Sova Scanner — архитектура платформы

Реализация по ТЗ «САСТ-Тендеры» v2.0 (`../ТЗ/ТЗ/ТЗразработка.md`). Документ описывает целевую
архитектуру всей платформы и то, что из неё уже реализовано на текущий момент (Этапы 0—3 и
5—7 целиком, Этап 4 частично — см. разделы 12—14).

## 1. Слои системы (раздел 6.1 ТЗ)

```
┌─────────────────────────────────────────────────────────────────┐
│ 7. Приложение: API + веб-интерфейс                               │
│    auth, users, tenders, cards, analytics, settings, export,     │
│    notifications                                                 │
├─────────────────────────────────────────────────────────────────┤
│ 6. Сопоставление с каталогом продукции                           │
│    правила + AI-сопоставление + fallback на "Руководство         │
│    пользователя" → compliance_matrix, win_percentages            │
├─────────────────────────────────────────────────────────────────┤
│ 5. ИИ-анализ (YandexGPT или Claude через RouterAI — по выбору)   │
│    извлечение требований, критичность, тип тендера, ОКПД2, регион│
├─────────────────────────────────────────────────────────────────┤
│ 4. Источник каталога продукции                                   │
│    адаптер ФГИС (fgis.gost.ru) + сайты производителей            │
├─────────────────────────────────────────────────────────────────┤
│ 3. Хранилище                                                     │
│    PostgreSQL 15+ (структурированные данные) + файловое          │
│    хранилище документов (storage/{tender_id}/{doc_id}.ext)       │
├─────────────────────────────────────────────────────────────────┤
│ 2. Сбор и обработка                                              │
│    планировщик (APScheduler → Celery/Redis при росте нагрузки),  │
│    загрузчик документов, парсер PDF/DOCX/XLSX, дедупликация      │
├─────────────────────────────────────────────────────────────────┤
│ 1. Источники тендеров — 12 адаптеров, единый интерфейс           │
│    list_new_tenders / get_tender_details / download_documents    │
└─────────────────────────────────────────────────────────────────┘
```

Каждый слой независим и общается с соседними через явные интерфейсы (адаптеры источников,
сервисный слой), чтобы сбой/расширение одного слоя не требовало переработки остальных
(принципы — раздел 6.3 ТЗ).

## 2. Технологический стек (раздел 6.2 ТЗ)

| Слой | Технология |
|---|---|
| Backend / API | Python 3.11+, FastAPI, Uvicorn |
| ORM / БД-доступ | SQLAlchemy 2.0 (sync), Alembic (миграции) |
| Аутентификация | JWT (access-токен), пароли — Argon2 (`passlib[argon2]`) |
| БД | PostgreSQL 15+ |
| Файловое хранилище | Локальная ФС `storage/{tender_id}/{doc_id}.ext`, путь — в БД |
| Планировщик задач | APScheduler (этапы 2+) |
| Скрапинг | httpx/BeautifulSoup, Playwright для JS-тяжёлых источников (этапы 2+) |
| Парсинг документов | pdfplumber (+ pypdfium2 для рендера страниц) + pytesseract (OCR-fallback), python-docx, openpyxl (этап 3) |
| ИИ-модуль | YandexGPT (Yandex AI Studio SDK) или Claude через RouterAI (OpenAI-совместимый API) — переключается в настройках (раздел 40) |
| Фронтенд | React + Vite + TypeScript + Tailwind CSS |
| Логирование | `loguru` (файлы) + таблица `logs` в БД (структурированный аудит) |
| Развёртывание | Docker Compose (backend + PostgreSQL + reverse-proxy) |

Справочник продукции и AI-модуль сознательно не создаются пустыми "заглушками" заранее — они
появятся начиная с Этапа 4-5, когда для них будет реальная логика (принцип "не проектировать
под гипотетические будущие требования"). Адаптеры источников тендеров, наоборот, уже
реализуются на Этапе 2: единый интерфейс — `SourceAdapter` (ABC) в `app/adapters/base.py`,
конкретные адаптеры подключаются волнами по мере технической готовности площадки (см. раздел
9 ТЗ, Этап 2 → Этап 12, и таблицу статусов в `/settings` фронтенда).

## 4. Модель данных — что уже создано (Этап 0—2)

Полная целевая схема — раздел 7 ТЗ (16 таблиц). На Этапе 0—2 созданы только те таблицы,
которые реально используются:

- `federal_districts` — справочник ФО (Приложение G), сид-данные, 8 строк.
- `regions` — справочник регионов (Приложение H), сид-данные, 89 строк, FK → `federal_districts`.
- `users` — учётные записи, роль хранится как строка (не нативный enum БД), чтобы можно было
  добавлять новые роли (тендерный отдел/продажи/руководство — открытый вопрос №10 ТЗ) без
  миграции типа enum. Пароли — только хеш (Argon2).
- `logs` — журнал действий (раздел 5.9 ТЗ), связан с `users.id` (nullable — для системных
  событий без пользователя).
- `sources` — источники тендеров (раздел 4.1 ТЗ: ЕИС + коммерческие ЭТП; из двенадцати в
  системе девять — три неподключаемые удалены миграцией 0038), сид-данные.
  Помимо полей раздела 7 ТЗ добавлены `key` (стабильный идентификатор для связи с классом
  адаптера — раздел 7 ТЗ не описывает этот механизм явно), `adapter_key`/`adapter_status`/`note`
  (готовность программного адаптера — отдельная ось от `status`, который описывает бизнес-доступ
  к площадке) и `availability_status`/`availability_checked_at`/`availability_error` (результат
  автоматического пинга раз в минуту, раздел 7 ниже).
- `tenders` — полная целевая схема раздела 7 ТЗ создана уже сейчас (решение №11 ТЗ — не
  переделывать схему на следующих этапах), но поля более поздних этапов (регион/ФО/ОКПД2/тип
  конкурса — Этап 5, комментарий ИИ — Этап 5-6) остаются nullable и пустыми до соответствующего
  этапа. Уникальность `(source_id, external_id)` — основа дедупликации (раздел 5.1 ТЗ).

Также созданы `tender_documents` (Этап 3, раздел 8 ниже), `yandex_ai_studio_settings` (раздел
11 ниже) и `manufacturers`/`si_types`/`products`/`product_characteristics` (Этап 4, раздел 12
ниже — последние две пока не заполняются логикой, только схема).

Остальные таблицы (`requirements`, `compliance_matrix_entries`, `win_percentages`,
`tender_outcomes`, `region_responsibles`, `notifications`) появятся вместе с этапами 5—10,
когда для них будет реализована сама логика — их преждевременное создание сейчас увеличило бы
объём миграций без пользы.

## 5. Аутентификация и роли (Этап 1, раздел 3 ТЗ)

- JWT access-токен (`Authorization: Bearer <token>`), срок жизни настраивается через
  `.env` (`ACCESS_TOKEN_EXPIRE_MINUTES`).
- Пароли хешируются Argon2 (`passlib`), в БД и логах пароль никогда не хранится и не пишется
  в открытом виде.
- Роль — `admin` / `user` как расширяемый Python `Enum`, хранится строкой в колонке `role`.
  Добавление новой роли — правка enum + бизнес-правил доступа, без ALTER TYPE в БД.
- `require_role(...)` — FastAPI-зависимость для ограничения эндпоинтов ролью.
- **Bootstrap первого администратора**: при отсутствии в БД ни одного пользователя система
  создаёт первого администратора автоматически при старте приложения (или отдельной CLI-командой
  `python -m app.cli bootstrap-admin`), используя логин/пароль из `.env`
  (`BOOTSTRAP_ADMIN_USERNAME`, `BOOTSTRAP_ADMIN_PASSWORD`). Идемпотентно — повторный запуск не
  создаёт дубликат.
- **Сброс администратора для разработки/эксплуатации**: отдельная команда
  `python reset_admin.py` (или `python -m app.cli reset-admin`) создаёт администратора с нуля
  либо, если он уже есть, перезаписывает его пароль/ФИО — в отличие от bootstrap-механизма выше,
  её можно запускать многократно. Пароль (свой или сгенерированный случайно) и логин сохраняются
  в `.env` через `app/core/env_file.py`, который точечно обновляет нужные строки, не трогая
  остальное содержимое файла.
- **Аудит действий**: ASGI-middleware перехватывает все не-`GET` запросы, определяет
  текущего пользователя (если есть валидный токен) и пишет запись в `logs`
  (`component="http"`, `action=f"{method} {path}"`, `result=<status>`). Дополнительно ключевые
  бизнес-события (вход, выход, создание/блокировка пользователя) пишутся сервисным слоем
  (`app/services/audit.py`) с более содержательным описанием — это не дублирование, а
  разные уровни детализации одного и того же журнала.

## 6. Здоровье системы и логирование (Этап 0)

- `GET /health` — не требует аутентификации, проверяет доступность БД (`SELECT 1`), отвечает
  `{"status": "ok", "database": "ok"}` либо 503 при недоступности БД.
- `loguru` пишет в stdout (для Docker) и ротируемый файл `logs/app.log` (хранение — 6 месяцев,
  раздел 5.9 ТЗ; ротация и retention настроены в `core/logging.py`).

## 7. Сбор тендеров (Этап 2, раздел 5.1, 9 ТЗ)

- **Интерфейс адаптера** (`app/adapters/base.py`, ABC `SourceAdapter`): `list_new_tenders(since)`,
  `get_tender_details(external_id)`, `download_documents(external_id)` — как задано в разделе
  5.1 ТЗ. Возвращаемые типы — dataclasses (`TenderSummary`, `TenderDetails`, `DocumentRef`,
  `PollOutcome`), не ORM-модели: адаптер не знает о сессии БД, это забота сервисного слоя.
- **Реестр** (`app/adapters/registry.py`) связывает `Source.adapter_key` с классом адаптера —
  планировщик и CLI обращаются только к реестру, не к конкретным классам (раздел 6.3 ТЗ).
- **Повторные попытки** (`app/adapters/http_utils.fetch_with_retry`) — общий хелпер поверх
  `httpx`, 3 попытки с экспоненциальной задержкой по умолчанию (раздел 5.1, 5.9 ТЗ), настройки —
  `HTTP_RETRY_ATTEMPTS`/`HTTP_RETRY_BACKOFF_BASE` в `.env`.
- **Дедупликация и сохранение** (`app/services/tender_service.py`) — по паре
  `(source_id, external_id)`. Реализована с явным `db.flush()` после каждой вставки: сессия
  работает с `autoflush=False` (`app/db/session.py`), поэтому без явного flush дубль в одной
  пачке результатов (например, из-за пересечения страниц выдачи источника) не находился бы
  обычным `SELECT` и приводил бы к нарушению уникального ограничения при коммите — это
  подтверждено тестом `test_poll_source_dedups_within_single_batch`.
- **Изоляция ошибок** (раздел 5.1, 5.9 ТЗ): ошибка одного источника не прерывает опрос
  остальных (try/except на уровне `poll_source`), ошибка одной карточки — не прерывает разбор
  остальных (try/except на уровне адаптера, копится в `PollOutcome.errors`).
- **Планировщик** (`app/core/scheduler.py`, APScheduler) — два ежедневных `CronTrigger`
  ("утро"/"обед", раздел 4.1 ТЗ), время — `SCHEDULER_MORNING_TIME`/`SCHEDULER_AFTERNOON_TIME` в
  `.env`. Отключается через `SCHEDULER_ENABLED=false` (используется в тестах, чтобы не поднимать
  фоновые задачи при каждом прогоне `pytest`).
- **Ручной запуск** — `python -m app.cli poll-source <key>` (CLI) или кнопка «Опросить сейчас»
  в `/settings` (только роль `admin`, эндпоинт `POST /sources/{id}/poll`) — не дожидаясь
  расписания, для разработки и разовой проверки конкретного источника.
- **Общие хелперы разбора** (`app/adapters/parsing_utils.py`) — даты ДД.ММ.ГГГГ, суммы с
  разделителями разрядов, извлечение текста из элемента без артефактов от тегов подсветки
  найденного слова (см. докстринг файла). Вынесены из `eis.py`, когда та же логика
  понадобилась в `zakazrf.py` — площадки используют одинаковый формат чисел/дат.
- **Адаптер ЕИС** (`app/adapters/eis.py`). HTML-скрапинг страницы результатов расширенного
  поиска (`httpx` + `BeautifulSoup`, JS не требуется — верстка серверная). Фильтрация
  релевантности — полнотекстовый поиск по ключевым словам (`DEFAULT_SEARCH_KEYWORDS`), а не по
  коду ОКПД2: скрытые поля формы ЕИС (`okpd2Ids`/`okpd2IdsCodes`) требуют внутренний GUID
  категории из справочника площадки, а не сам код — прямая фильтрация по коду при проверке
  молча игнорировалась площадкой. Резолвинг кода в GUID — задел на будущую доработку (TODO в
  `_search_params`).
- **Адаптеры ЕЭТП / zakazrf и ЭТП РФ** (`app/adapters/zakazrf.py`, `app/adapters/etprf.py`).
  Сводный реестр извещений на обеих площадках сам по себе обычный серверный HTML, но быстрый
  поиск — AJAX-постбэк одного и того же грид-фреймворка («ORM», идентичные CSS-классы
  `reporttable`/`orm-grid-table-header` и поле `Filter.FastFilter`, похоже — общий вендор-
  шаблон) с недокументированным контрактом (ID полей формы меняются на каждой загрузке
  страницы; проверка через простой GET-параметр результата не дала). Поэтому оба адаптера
  используют **Playwright** — реально вводят ключевое слово в поле поиска и жмут «Найти», как
  пользователь, вместо воспроизведения непубличного AJAX-запроса. Нюанс, на который стоит
  обратить внимание при добавлении следующих Playwright-адаптеров: `page.content()` после
  AJAX-обновления сериализует DOM уже с неявным `<tbody>`, которого нет в исходном серверном
  HTML — `find_all(..., recursive=False)` на таком дереве может молча найти 0 строк вместо
  реальных данных (см. тест `test_parse_row_handles_implicit_tbody_from_rendered_dom` в
  `tests/test_zakazrf_adapter.py`). У ЭТП РФ статус извещения ("Опубликован"/"Отменен") тоже
  обманчив — "Опубликован" не означает "сейчас идёт приём заявок" (встречаются записи с таким
  статусом при сроке подачи, истёкшем на годы раньше) — размечается только "Отменен", остальное
  осознанно оставлено пустым.
- **Адаптер Росэлторг** (`app/adapters/roseltorg.py`). Несмотря на React-виджеты на сайте, сама
  выдача поиска (`/procedures/search?query_field=...`) — обычный серверный HTML (Drupal-бэкенд,
  судя по `data-drupal-selector`), `httpx` + `BeautifulSoup` без Playwright.
- **Адаптер ЭТП ГПБ** (`app/adapters/etpgpb.py`). Сайт на Nuxt/Vue, список процедур не в
  исходном HTML (нужен клиентский JS) — типичный кейс для Playwright. Но при наблюдении за
  сетевыми запросами реальной страницы поиска (через Playwright, только для разведки — не в
  самом адаптере) нашёлся публичный JSON API, которым страница сама пользуется:
  `GET /api/v2/procedures/?search=<текст>&page=<N>&per=<M>&sort=by_published_desc` — обычный
  JSON:API-подобный ответ (`data[]`, `meta.total_pages`), без авторизации. Playwright оказался
  не нужен вообще — адаптер ходит в этот API напрямую через `httpx`, что и быстрее (весь
  keyword-поиск на ~3400 записей — около 25 секунд), и надёжнее HTML/JS-рендеринга. Без явного
  `sort=by_published_desc` API отдаёт "по релевантности", которая заметно нестабильна между
  последовательными запросами — при постраничном обходе это давало расхождения между запусками.
- **TLS-особенности при работе адаптеров и пинга** (`app/adapters/http_utils.resolve_verify`,
  общая точка для обоих механизмов): сертификаты `*.zakupki.gov.ru` и `*.astgoz.ru` подписаны
  государственным `Russian Trusted Sub CA` (Минцифры России), которого нет в стандартном
  доверенном списке большинства окружений вне РФ — для этих доменов клиент доверяет только
  сохранённой цепочке `app/certs/russian_trusted_ca.pem` (снята напрямую с боевого TLS-
  хендшейка), не отключая проверку целиком. У `etprf.ru` другой случай: сервер не досылает
  промежуточный сертификат `GlobalSign GCC R6 AlphaSSL CA 2025` (частая ошибка конфигурации,
  сам корневой CA давно в любом системном списке) — недостающий сертификат
  (`app/certs/globalsign_gcc_r6_alphassl_2025.pem`, официальный публичный CA, получен по ссылке
  из Authority Information Access самого сертификата) подставляется к системному списку через
  `ssl.SSLContext`, не заменяя его. Обе проблемы найдены и решены через пинг доступности —
  раньше эти две площадки показывали «Недоступно» по TLS-причине, не связанной с бизнес-доступом.
- **Остальные источники** (раздел 4.1 ТЗ) — статус и причина видны в `sources.note` (сид-данные
  — `app/seed/sources_data.py`, дополнена миграциями 0005-0007 по итогам реального исследования
  каждой площадки) и на странице `/settings`. Делятся на две категории:
  - **В очереди на Playwright** (`adapter_status=not_implemented`, но причина уже известна):
    Фабрикант и Tektorg — на Next.js (у Фабриканта — с RSC, поток данных сериализован не как
    обычный JSON), Сбербанк-АСТ — на Vue, Lot-online — на Angular. Ни у одной из четырёх не
    нашлось открытого API уровня ЭТП ГПБ при беглой проверке — следующая волна подключения.
  - **Удалены из системы** (миграция `0038_remove_blocked_sources`, правка по итогам показа
    15.09.2026) — три площадки, которые нельзя подключить техническими средствами; пока они
    висели в разделе источников как «заблокировано», это путало конечного пользователя:
    - **РТС-тендер** — страница «Anti-DDoS защита», не проходит даже реальный headless-браузер
      после ожидания — проверено, дальнейший обход (подмена fingerprint и т.п.) намеренно не
      предпринимался;
    - **АСТ ГОЗ** — система торгов по гособоронзаказу, публичного списка закупок без входа и
      электронной подписи (КриптоПро) нет — легитимное ограничение доступа, не техническая
      проблема;
    - **ЭТП ГПБ (Стратег)** — отдельный раздел ЭТП ГПБ для закрытых тендеров по приглашениям,
      без публичного списка (в отличие от основного раздела площадки, где как раз реализован
      адаптер через открытый JSON API).
- **Доступность источников** (`app/services/availability_service.py`) — раз в минуту (не по
  расписанию 2 раза в день, отдельный, гораздо более частый `IntervalTrigger` в
  `app/core/scheduler.py`) система лёгким HTTP-запросом (`httpx` `stream`, тело ответа не
  читается) проверяет, отвечает ли URL каждого источника — независимо от того, реализован ли
  для него адаптер: пользователю нужно видеть в «Настройках» состояние всех площадок сразу,
  чтобы осмысленно выбирать следующую волну подключения. Результат (`available`/`unavailable` +
  краткая причина: таймаут, HTTP-код, ошибка TLS и т.д.) — в `sources.availability_*`; в `logs`
  пишется только смена состояния, не каждый пинг, иначе журнал захлебнётся при частоте раз в
  минуту на 12 источников. При реальном прогоне сразу нашёл настоящие проблемы у нескольких
  коммерческих площадок (антибот-защита у РТС-тендера, неполная TLS-цепочка у АСТ ГОЗ и ЭТП РФ)
  — не гипотетический сценарий, а результат первого же запуска.
- **API тендеров** (`app/api/endpoints/tenders.py`) — `GET /tenders` (`limit` до 1000) и
  `GET /tenders/stats` (общее число + разбивка по статусу). `Tender.source` — eager-loaded
  (`lazy="joined"`) relationship к `Source`, чтобы имя площадки в списке не требовало N+1
  запросов. Фильтры (`TenderFilters` в `app/services/tender_service.py`) — осмысленное
  подмножество раздела 5.6 ТЗ, только по полям, которые реально заполняются на Этапе 2: поиск
  по названию/заказчику, источник, диапазон даты размещения, диапазон срока подачи заявок,
  диапазон суммы, скрытие тендеров с истёкшим сроком подачи (учитывает `NULL` — не скрывает
  записи с неизвестным сроком). Регион/ОКПД2/тип конкурса/процент победителя не фильтруются:
  эти поля появятся только с Этапами 5-6, фильтр по ним сейчас был бы фиктивным. Полноценная
  пагинация — Этап 7 ТЗ.
- **Массовый опрос выбранных источников** — `POST /sources/poll` (тело: `source_keys: string[]`),
  в отличие от поточечного `/sources/{id}/poll` в «Настройках» (только `admin`, раздел 5.6 ТЗ)
  доступен любому авторизованному пользователю: это рабочий сценарий «обновить список тендеров»
  со страницы «Тендеры» (кнопки «Ресурсы»/«Синхронизировать»), а не управление источниками.
  Выбор источников хранится в `localStorage` браузера (`oraclet_selected_source_keys`) — это
  предпочтение конкретного пользователя на своём устройстве, не системная настройка.

## 8. Карточка тендера и документы (Этап 3, раздел 5.2, 7 ТЗ)

Модель хранения, загрузчик, парсеры (PDF/DOCX/XLSX + OCR-fallback) и API документов —
раздел 9 ТЗ, Этап 3 — подтянуты раньше срока по запросу заказчика вместе с модальным окном
карточки тендера на странице «Тендеры» (само модальное окно целиком — уже Этап 7 ТЗ), поверх
уже готового Этапа 2. Разбор документов реализован пока только для адаптера ЕИС — см. ниже.

- **`tender_documents`** (`app/models/tender_document.py`) — по схеме раздела 7 ТЗ:
  `file_name`, `file_type`, `storage_path`, `extracted_text`, `parse_status`
  (`pending`/`success`/`error`), `parse_error`, `downloaded_at`, плюс `source_url` (не было в
  ТЗ явно, нужен как естественный ключ идемпотентности — `UNIQUE(tender_id, source_url)`, чтобы
  не создавать дубль записи при повторной синхронизации).
- **Ленивое скачивание** (`app/services/document_service.sync_tender_documents`) — запускается
  при первом обращении к `GET /tenders/{id}/documents`, не при плановом опросе: скачивать
  документацию по всем тысячам собранных тендеров сразу бессмысленно, если их не открывают.
  Повторное обращение просто отдаёт уже сохранённые записи.
- **Гонка при параллельных запросах**: если два запроса к документам одной и той же карточки
  стартуют почти одновременно (например, двойной вызов `useEffect` в React StrictMode при
  разработке — воспроизведено вживую), оба видят пустой список существующих документов и оба
  пытаются вставить одни и те же записи — второй INSERT падает на `UNIQUE(tender_id,
  source_url)`. Без изоляции это не сбой одного документа, а падение ВСЕЙ транзакции разом
  (Postgres требует ROLLBACK после любой ошибки внутри транзакции, прежде чем продолжать) —
  решено через `db.begin_nested()` (SAVEPOINT) на каждую вставку: конфликт откатывает только эту
  одну вставку, остальные документы в пачке не страдают, а при конфликте просто переиспользуется
  запись, созданная параллельным запросом.
- **Извлечение текста** (`app/services/document_extraction.py`) — PDF (`pdfplumber`), DOCX
  (`python-docx`), XLSX (`openpyxl`), как в разделе 6.2 ТЗ. **OCR-fallback** для сканов без
  текстового слоя (раздел 5.2 ТЗ) — постранично: если `page.extract_text()` не дал текста,
  страница рендерится в изображение через `page.to_image()` (использует `pypdfium2` — уже тянется
  как зависимость `pdfplumber`, отдельный `poppler`/`PyMuPDF` не нужен) и распознаётся
  `pytesseract` с языками `rus+eng` (настраивается — `OCR_LANGUAGES`, `OCR_RESOLUTION`,
  `OCR_ENABLED` в `.env`). Отсутствие системного бинарника `tesseract` на сервере (или любая
  другая ошибка OCR) не роняет разбор документа — просто у конкретной страницы не будет
  извлечённого текста, залогировано предупреждением; в Docker-образе `tesseract-ocr` +
  языковые пакеты ставятся автоматически (`backend/Dockerfile`). Ошибка разбора конкретного
  документа (например, файл с
  расширением `.pdf`, который на деле не обычный PDF, а специальный контейнер подписанного
  документа — встретилось на реальных данных ЕИС) помечается `parse_status=error` с текстом
  ошибки, сам файл при этом уже скачан и сохранён — раздел 5.2 ТЗ прямо требует не прерывать
  обработку остальных документов из-за одного.
- **Скачивание из интерфейса** — `GET /tenders/{id}/documents/{document_id}/download`,
  `FileResponse` с нашего сервера, не прямая ссылка на источник: пользователь получает файл
  через наш API, а не уходит на сторонний сайт. Фронтенд (`downloadFile` в `api/client.ts`)
  забирает файл через авторизованный `fetch` и запускает нативное сохранение через blob-ссылку —
  обычный `<a href>` не подошёл бы, потому что авторизация у нас на Bearer-токене, а не на куках.
- **Реализован пока только у ЕИС** (`EisAdapter.get_tender_details`/`download_documents`) — у
  44-ФЗ и 223-ФЗ разная верстка вкладки "Документы" (у 223-ФЗ, например, имя файла в
  `data-tooltip` с вложенным HTML, а не в атрибуте `title`, как у 44-ФЗ) и разный URL этой
  вкладки (у 223-ФЗ дополнительно нужен `noticeGuid`, которого нет в одном лишь номере закупки).
  Вместо угадывания URL по шаблону адаптер берёт реальную ссылку "Документы" со страницы карточки
  (`a.tabsNav__item`, общий класс для обеих разновидностей), а сами файлы находит по общему для
  обеих признаку — прямая ссылка на скачивание всегда ведёт на `.../filestore/public/...`,
  независимо от 44-ФЗ/223-ФЗ. У остальных восьми адаптеров `download_documents` — временная
  заглушка (единственная "документ"-ссылка на саму карточку тендера в источнике), реальный разбор
  документов для них — следующий шаг (вместе с Этапом 12 ТЗ, расширение источников).
- **Блок «ИИ-помощник»** в карточке (`TenderDetailModal.tsx`) — пока чистый UI-плейсхолдер, без
  какой-либо логики; сам ИИ-модуль — Этап 5-6 ТЗ.

## 11. Настройки интеграций: Yandex AI Studio (задел на Этап 5, раздел 5.4 ТЗ)

Подтянуто раньше срока по запросу заказчика — ключ понадобился уже на Этапе 3/4 (тест
OCR-fallback, планируемый разбор legacy `.doc` через ИИ), а заходить в код/`.env` сервера
каждый раз для смены ключа заказчик не хочет.

- **`yandex_ai_studio_settings`** (`app/models/integration_setting.py`) — синглтон-таблица
  (один фиксированный `id`), а не запись в `.env`: `api_key`, `folder_id`, `updated_at`,
  `updated_by_id`. Управляется только ролью «Администратор» — `GET/PATCH
  /integrations/yandex-ai-studio`, UI — раздел «Интеграции» на `/settings`.
- **Ключ никогда не возвращается в открытом виде** — `GET` отдаёт только `api_key_masked`
  (последние 4 символа) и `is_configured`. `PATCH` — частичное обновление (поле, не присланное
  в теле запроса, не трогается; пустая строка — явная очистка) через `model_fields_set`.
- **`POST /integrations/yandex-ai-studio/test`** — реальный вызов Yandex Vision OCR
  (`yandex-ai-studio-sdk`) на маленьком заглушечном PNG, сгенерированном через Pillow и
  проверенном round-trip тестом (`test_probe_png_is_a_valid_decodable_image` в
  `tests/test_integrations.py`) — захардкоженные вручную байты изображения один раз уже
  оказались повреждены и ошибка `Can't decode image` от Yandex выглядела как проблема с
  ключом/Folder ID, хотя ей не была; тест — защита от повтора именно этой ошибки.
- Подключение проверено вживую реальными учётными данными заказчика (Folder ID + API-ключ,
  тип auth — `APIKeyAuth`, endpoint `ocr.api.cloud.yandex.net`) — `test_connection` подтверждён
  рабочим, не только в тестах с моками.
- **Важно про Folder ID**: нужен идентификатор **папки** (`b1gd43...`), а не **облака**
  (`b1gika...`) — внешне они неотличимы. Vision OCR с ID облака отвечает успехом, а текстовая
  генерация — `INVALID_ARGUMENT: Specified folder ID does not match with service account
  folder ID`, поэтому ошибка обнаруживается не сразу. Сообщение самого Yandex называет
  правильный ID в тексте ошибки.
- **`app/services/yandex_ai_client.py`** — клиент текстовой генерации: берёт учётные данные из
  БД, поддерживает structured output (ответ по pydantic-схеме) и нарезку длинного текста на
  куски. Модель по умолчанию — `yandexgpt` (Pro), не `-lite`: задачи разделов 5.4-5.5 ТЗ
  требуют аккуратности на длинных технических текстах. `temperature=0.0` — извлечение фактов
  из документа должно быть воспроизводимым.
- Используется на Этапе 4 для AI-экстракции характеристик (раздел 12 ниже). Извлечение
  требований тендера (раздел 5.4 ТЗ, Этап 5) и fallback-парсер для legacy `.doc` (за рамками
  ТЗ, обсуждалось отдельно) — ещё не реализованы.
- С 18.09.2026 это один из двух провайдеров: потребители ходят через
  `app/services/ai_client.py`, второй — Claude через RouterAI (раздел 40).

## 12. Справочник продукции (Этап 4, раздел 4.3, 5.3, 7 ТЗ) — частично

> «по кнопке» — ФГИС и каталог МИРТЕК заведены как источники в общем планировщике, с
> очередью, дисамбигуацией кандидатов реестра и автонаполнением справочника. См. **раздел 28**;
> написанное ниже описывает исходное состояние.

- **`manufacturers`** — сид-данные, 13 строк (МИРТЕК + 12 конкурентов, раздел 4.3 ТЗ). Сайт
  ООО «НПК "Инкотекс"» не указан в ТЗ (раздел 11, открытый вопрос №3) — `website = NULL`,
  заполняется позже вручную. Сайт МИРТЕК (`mirtekgroup.com`) заполнен миграцией 0031 вместе

- **`si_types`, `products`, `product_characteristics`** (EAV — раздел 5.3 ТЗ упоминает ~80
  полей по 11 группам, Приложение C; фиксированная широкая таблица потребовала бы миграции на

  заполняется никакой логикой.
- **`app/adapters/fgis.py`** — поиск кодов СИ по точному юр. названию производителя (раздел
  5.3 ТЗ, п.1 алгоритма) и скачивание документа «Описание типа» (переиспользует
  `document_extraction.py` из Этапа 3 — обычно PDF).
  **Важно: написан без доступа к живому `fgis.gost.ru`** — домен не резолвится с машины, на
  которой велась разработка (`dig` возвращает NXDOMAIN/SERVFAIL даже для корневого `gost.ru`,
  через несколько резолверов включая `8.8.8.8` — похоже, ресурс недоступен извне России). В
  отличие от адаптеров источников тендеров (Этап 2), разрабатывавшихся по реальной разметке,
  этот — по описанию ТЗ и общим сведениям о технологии сайта (параметр `rows` в URL из раздела
  4.2 ТЗ характерен для Apache Solr → предположение о JSON-ответе вида `{"response":
  {"docs": [...]}}`). Осознанный риск, принятый явно при планировании Этапа 4, не недосмотр.
  Сетевой слой (запрос, 3 попытки с экспоненциальной задержкой — раздел 5.1 ТЗ, обработка
  ошибок) работает и проверен (в т.ч. вживую — реальный `dig`/HTTP-запрос с сервера корректно
  логирует сбой и возвращает пустой список, не роняя эндпоинт). Разбор полей ответа —
  best-effort по нескольким правдоподобным именам полей, с сохранением исходного JSON-объекта
  целиком в `SiSearchResult.raw` на случай, если предположение о названиях полей неверное —
  требует проверки и, вероятно, правки при первом реальном запуске (сервер будет в РФ и увидит
  сайт иначе, чем машина разработки).
- **Автопоиск и ручная проверка** (раздел 5.3 ТЗ) — `POST
  /manufacturers/{id}/si-types/search` (админ) сохраняет найденное с `verified_by_user=false`;
  `PATCH /si-types/{id}` — ручное подтверждение/правка кода СИ (переключает `source` на
  `manual` — приоритет над повторным автопоиском, раздел 5.3 ТЗ: «ручной ввод имеет приоритет
  перед автопоиском при конфликте»). Дедупликация — `UNIQUE(manufacturer_id, si_code)`, тот же
  принцип, что и `tender_documents` в Этапе 3.
- **Справочник характеристик** (`app/seed/characteristics_data.py`) — Приложение C ТЗ целиком.
  Раздел 5.3 ТЗ говорит «~80 полей, 11 групп», фактически в Приложении C перечислено
  **13 групп и 138 полей** — воспроизведён фактический перечень (расхождение на стороне ТЗ).
  `PRIMARY_SOURCE` задаёт, какая группа откуда заполняется преимущественно (ФГИС / сайт
  производителя / только вручную) — раздел 5.3 ТЗ, «Источники и приоритет».
- **AI-экстракция характеристик** (`app/services/characteristic_extraction.py`, раздел 5.3 ТЗ,
  п.2-3 алгоритма) — текст документа + **явный справочник допустимых полей** в системном
  промпте, structured output (pydantic-схема) через YandexGPT. Всё извлечённое сохраняется с
  `verified_by_user=False` (раздел 5.3 ТЗ требует проверку человеком), значения с ручным вводом
  или подтверждённые человеком повторной экстракцией не перезаписываются.
  Длинный документ режется на куски **с перекрытием** (`chunk_text`), чтобы не терять значения
  на стыке.
  Два бага, найденные живыми прогонами на реальном API (оба закрыты регрессионными тестами):
  1. *Отсутствие `flush()` после вставки.* Из-за перекрытия одна характеристика закономерно
     приходит из двух соседних кусков; `select` не видел ещё не сброшенный в БД объект, вторая
     вставка падала на `uq_product_characteristics_field` и роняла ВСЮ транзакцию — терялись все
     характеристики документа. Проявился бы на первом же многостраничном «Описании типа».
  2. *Плоский формат списка полей в промпте* («группа → поле» одной строкой) — модель
     воспроизводила строку целиком в `field_name`
     («Электрические характеристики → Номинальное напряжение»), и **все 13** корректно
     извлечённых характеристик отбраковывались фильтром по справочнику (`saved=0`). Промпт
     перестроен (поля сгруппированы), плюс оставлена нормализация `field_name` как страховка.
  Проверено вживую на реальном ключе заказчика: 13/13 характеристик тестового «Описания типа»
  извлечены и разложены по полям Приложения C; повторный прогон после ручной правки корректно
  сохранил ручное значение (`skipped_protected=1`).
- **Админ-CRUD каталога** — модели приборов (`GET/POST /manufacturers/{id}/products`,
  `PATCH /products/{id}`), характеристики (`GET /products/{id}/characteristics`,
  `PUT` — ручной ввод, `POST /characteristics/{id}/verify` — подтверждение человеком).
  Ручной ввод всегда `source=manual_entry` + `verified_by_user=True`; поле вне Приложения C
  отклоняется с 422, а не создаёт произвольную запись в каталоге.
- **CSV-импорт** «Производитель → код СИ → модель» (`app/services/catalog_import.py`,
  `POST /catalog/import`, раздел 5.3 ТЗ, п.4) — для загрузки точных кодов СИ конкурентов, когда
  заказчик их предоставит (п.11 истории решений ТЗ). Понимает русские заголовки, разделитель
  `;` и кодировку cp1251 (типичная выгрузка из Excel в русской локали), идемпотентен при
  повторном импорте, ошибочная строка не отменяет остальные (раздел 5.9 ТЗ). Импортированные
  записи — `source=import` + `verified_by_user=True` (приоритет над автопоиском).
- **Адаптер сайтов производителей** (`app/adapters/manufacturer_site.py`, раздел 5.3 ТЗ, п.3
  алгоритма) — в отличие от адаптера ФГИС, писался **по реальной разметке живых сайтов**
  (они доступны). Обходит сайт вширь от стартовой страницы, отдавая приоритет страницам,
  похожим на карточку искомой модели, и ищет ссылку на «Руководство по эксплуатации».
  Что показала разведка по сайтам раздела 4.3 ТЗ и определило конструкцию:
  - Единого шаблона нет: у «Энергомеры» карточка `/ru/products/meters/ce101-r5-145-m6` с
    осмысленной подписью ссылки; у «Тайпит» подпись — просто «PDF», а имя файла информативно
    (`manual-nevapro.pdf`); у «Милур» подпись «Скачать», название документа — в имени файла.
  - Отсюда главное правило: ключевые слова ищутся **и в тексте ссылки, и в её URL**. Опора
    только на текст (интуитивно очевидный вариант) пропустила бы «Тайпит» и «Милур».
  - Отсекаются документы-соседи, которые лежат на тех же карточках и ловятся общим фильтром:
    сертификаты, декларации, формуляры, «Описание типа», политика конфиденциальности.
  - Обход намеренно ограничен (`max_pages`, `max_depth`, пауза между запросами): мы ходим по
    чужому публичному сайту, цель — найти один документ, а не выкачать сайт.
  Проверено вживую: для модели CE308-C36 на сайте «Энергомеры» найдено руководство именно этой
  модели (`ce308_c36_iu_bu03.pdf`), скачано, разобрано и через YandexGPT заполнило группы,
  которых нет в ФГИС — «Интерфейсы и связь», «Функциональные возможности», «Конструктивные
  характеристики», «Дополнительные функции», «Комплектация».
- **Веб-интерфейс каталога** (`frontend/src/pages/Catalog.tsx`, `/catalog`) — производители →

  ФГИС, загрузка «Описания типа», обе AI-экстракции (из «Описания типа» и с сайта
  производителя), CSV-импорт, ручная правка значения и подтверждение проверки. У каждого
  значения видно источник, `confidence` и статус проверки человеком — раздел 5.3 ТЗ требует
  проверку перед использованием, поэтому статус вынесен в интерфейс, а не спрятан в БД.
- **Не реализовано**: привязка нескольких моделей к одному коду СИ через UI (в схеме
  поддержана — `Product.si_type_id`), пакетная экстракция сразу по всем моделям производителя
  (сейчас по одной модели за раз — обход внешнего сайта занимает до минуты).

## 13. Анализ тендера: требования и матрица соответствия (Этапы 5-6, разделы 5.4, 5.5 ТЗ)

Цепочка из трёх звеньев: документы → требования → вердикты по производителям → процент
победителя. Каждое звено сохраняется в БД, поэтому карточку можно открыть без единого
обращения к модели, а пересчёт запускается кнопкой, а не просмотром.

**Извлечение требований** (`app/services/tender_analysis.py`, `POST /tenders/{id}/analyze`).
Текст документов разбивается на куски и уходит в YandexGPT со схемой ответа; модель
возвращает требования с критичностью (критичное/важное/второстепенное — веса формулы
раздела 5.5), тип конкурса (Приложение E), код ОКПД2 (Приложение F) и регион (Приложения G,
H). Результат — строки `requirements` плюс заполненные поля самого тендера.

**Сопоставление** (`app/services/compliance_service.py`, `POST /tenders/{id}/evaluate`).
Три шага раздела 5.5 реализованы как три источника фактов о продукции, каждый с пометкой
происхождения: `[si_type]` — «Описание типа» из ФГИС, `[catalog]` — характеристики моделей,
`[manual]` — руководство пользователя (подключается только для требований, оставшихся без
ответа). Один запрос на производителя, а не на пару «требование × производитель»: 13
производителей × 50 требований — это 650 обращений вместо 13.

Два ограничения YandexGPT, на которые наступили вживую и которые определяют форму кода:
поля схемы ответа объявляются **без значений по умолчанию** (иначе модель их не заполняет —
все вердикты вернулись с пустым пояснением), а требования отдаются пачками по 20
(`REQUIREMENTS_PER_REQUEST`) — длинный ответ обрывается по лимиту токенов посреди JSON, и
терялись вердикты по целому производителю.

**Процент победителя** считает код, а не модель: вес требования по критичности (3/2/1),
вклад статуса (соответствует 1.0, частично 0.5, не соответствует 0.0). `no_data` исключается
из знаменателя, а не считается провалом — иначе процент занижала бы неполнота каталога, а не
свойства прибора; поэтому рядом с числом всегда показывается охват «учтено N из M».
Вердикты с уверенностью ниже 0.6 помечаются флагом «требует проверки человеком».

`tender_outcomes` — задел на вторую очередь методики (история состоявшихся закупок): схема
заведена, логикой не заполняется; с 03.09.2026 её читает измерение History (раздел 23).

**Версионность (03.09.2026).** Пересчёт процента не переписывает строку, а гасит прежнюю
(`is_current = false`) и добавляет новую. Каталог продукции пополняется, процент от этого
меняется, и без истории пересчётов объяснить скачок с 46% до 88% было бы нечем. «Текущая»
запись по паре (тендер, производитель) при этом ровно одна — частичный уникальный индекс.

**Терминология.** С 03.09.2026 этот процент — не главная метрика тендера, а деталь уровня
матрицы соответствия: он отвечает на вопрос «какой прибор подходит», тогда как решение об
участии принимается по AI-оценке по профилю (раздел 23). В интерфейсе и выгрузке он
называется «процент соответствия».

## 14. Список и карточка тендера (Этап 7, раздел 5.6 ТЗ)

**Список** (`GET /tenders`) отдаёт страницу `{items, total, limit, offset}`, а не голый
массив: без `total` интерфейс не может показать ни объём найденного, ни число страниц.
Фильтры — дата, регион (совпадение по региону заказчика **или** поставки), ФО, тип конкурса,
статус, релевантность, сумма, ОКПД2 (по префиксу — код иерархичен, «26.51» обязано находить
26.51.63.130) и диапазон процента победителя. Сортировка — по любому столбцу, из явного
белого списка `_SORTABLE_COLUMNS`: имя поля приходит из query-параметра, и сортировка по
произвольному атрибуту модели была бы дырой. Процент победителя МИРТЕК живёт в отдельной
таблице и участвует в фильтре и сортировке через коррелированный подзапрос — join размножил
бы строки тендеров по числу производителей. Пустые значения всегда уходят в конец выдачи в
обоих направлениях сортировки.

Сортировка на фронте — серверная (`sort_by`/`sort_dir`), а не по загруженному массиву:
страница показывает 50 записей, и сортировка массива дала бы «самый дорогой тендер среди
показанных», а не среди найденных.

**Карточка** (`components/TenderDetailModal.tsx`) — пять вкладок: обзор с редактируемой
классификацией и комментарием ИИ, документы, требования с критичностью, матрица соответствия
и история. Данные вкладок грузятся лениво, по первому открытию: матрица на полсотни
требований × тринадцать производителей — сотни строк, и тянуть их, когда человек открыл
карточку посмотреть сроки, незачем. В матрице стоят короткие статусы, а текстовые пояснения
раскрываются по клику на строку требования — показать сотни предложений разом нечитаемо.

**Правки человека** (`app/services/tender_edit_service.py`): исправление классификации (тип
конкурса, регионы, ОКПД2), подтверждение релевантности, отметка «неактуально», комментарий.
Каждое изменение пишется в две стороны — в `tender_history` (лента карточки, пара
«было → стало» с автором) и в общий журнал `logs` (раздел 5.9 ТЗ). Дублирование намеренное:
журнал отвечает на вопрос «что происходило в системе», история — «почему в этом тендере
стоит такой тип конкурса». Поля, значение которых не изменилось, в историю не попадают, а
смена региона заказчика тянет за собой федеральный округ (Приложение G) — иначе карточка
противоречила бы сама себе.

Справочники регионов и ФО для фильтров и форм — `GET /dictionaries/regions` и
`/dictionaries/federal-districts`, отдаются целиком: 85 строк, меняются раз в пятилетку.

- **Не реализовано на Этапе 7**: раздел аналитики и настройки региональной ответственности
  (Этап 8), экспорт в Excel (Этап 9). Фоновая очередь для анализа: сейчас `analyze` и
  `evaluate` выполняются синхронно в запросе, на большом тендере это десятки секунд.

## 15. Учётные данные площадок (раздел 4.1, 5.1 ТЗ)

Часть площадок отдаёт закупки только авторизованному пользователю: без входа в личный
кабинет адаптер видит публичную витрину, а закрытые разделы (корпоративные закупки, 223-ФЗ
у отдельных ЭТП) остаются недоступны. Логины и пароли вводит администратор в разделе
«Пользовательские данные» настроек.

**Хранение.** Таблица `source_credentials`: несколько блоков на один источник (у площадки
бывает учётка на юрлицо), уникальность по паре (источник, название блока). Пароль лежит
шифротекстом Fernet (AES-128-CBC + HMAC-SHA256), не хешем — адаптеру нужен исходный пароль,
чтобы подставить его в форму входа.

**Ключ шифрования** — в файле `.credentials_key` в корне проекта, права 600, в `.gitignore`;
переменная `CREDENTIALS_ENCRYPTION_KEY` переопределяет его для контейнера. Ключ **не** в БД
(секрет и шифротекст в одном дампе — это отсутствие шифрования) и **не** в `.env` (`run.sh`
перезаписывает `backend/.env` копией корневого, и ключ терялся бы молча). При первом
обращении ключ создаётся сам; удаление файла делает сохранённые пароли нечитаемыми — код
говорит об этом явной ошибкой, а не молча возвращает пустую строку: попытка входа с пустым
паролем блокирует учётную запись на площадке.

**Пароль не покидает сервер.** API отдаёт только маску; `credentials_service` расшифровывает
пароль ровно в одном месте — `get_credentials_for_source(db, source_key)`, которым
пользуется адаптер. В журнал (раздел 5.9 ТЗ) пишутся действие, площадка, название блока и
логин — никогда значение пароля. Весь раздел под ролью «Администратор».

- **Не реализовано**: собственно использование учёток адаптерами (вход через Playwright с
  сохранением cookies) — следующий шаг вместе с подключением закрытых разделов площадок; и
  авторизация по ЭЦП/сертификату, которая нужна части ЭТП вместо пары логин-пароль — под неё
  потребуется отдельный тип учётки с файлом сертификата.

## 16. Аналитика и выгрузка в Excel (Этапы 8-9, разделы 5.6, 5.7 ТЗ)

**Дашборд** (`app/services/analytics_service.py`, `GET /analytics/overview`, страница
`frontend/src/pages/Analytics.tsx`). Пять разрезов раздела 5.6 ТЗ — количество и суммы,
динамика по месяцам, распределение по регионам, топ заказчиков, средний процент победителя
по периодам/регионам/типам — считаются агрегатами в БД и отдаются **одним** ответом: пять
параллельных запросов ради одной страницы дают заметное мерцание блоков при загрузке. На
5401 тендере ответ собирается за ~80 мс.

Все агрегаты проходят через `apply_tender_filters` — ту же функцию, что и список тендеров.
Это принципиально: цифры на дашборде обязаны совпадать с тем, что пользователь только что
отфильтровал в списке, иначе расхождение нечем объяснить.

**Динамика по месяцам** группируется по `publish_date` (месяц размещения — как в поле
«Месяц» Приложения D), а не по `created_at`: интересен месяц закупки, а не момент, когда до
неё добрался сборщик. Месяцы без данных возвращаются нулями, а ряд строится от последнего
месяца **с данными**, а не от «сегодня» — иначе на базе без свежих закупок график из пустых
месяцев читался бы как неработающая система.

**График** (`frontend/src/components/analytics/TrendChart.tsx`) — свой SVG, без charting-
библиотеки: в проекте нет ни одной такой зависимости, а нужен ровно один график с тремя
переключаемыми метриками. Кривая сглаживается кубическими Безье с **горизонтальными**
касательными: наклонные (по соседним точкам) на резких скачках уводят линию за пределы
данных — ниже нуля между двумя положительными точками.

**Виджеты состояния системы** (`get_widgets`) — не предметная аналитика, а ответ на вопрос
«система вообще работает?»: источники с адаптером, документы с извлечённым текстом,
заполненность каталога, покрытие ИИ-анализом, доля определённых ячеек матрицы, ошибки за
сутки. Тон плитки (ok/warn/danger) вычисляет **сервер** вместе со значением — пороги живут
в одном месте, иначе они разъехались бы между бэкендом и фронтом.

Доля документов считается по наличию `extracted_text`, а не по `parse_status`:
неподдержанные форматы (`.doc`, `.xls`, `.zip`) сохраняются со статусом `success` и пустым
текстом, и по статусу проблема не видна — а в анализ такой документ уходит пустым.

**ИИ-сводка** (`generate_ai_summary`, `POST /analytics/ai-summary`) — YandexGPT разбирает
числовую выжимку по всем разделам и возвращает заголовок, наблюдения, риски и следующие
шаги. Выжимку собирает код (`build_summary_context`), а не модель: цифры обязаны совпадать
с нарисованными на дашборде. Запрос идёт только по кнопке и методом POST — каждый вызов
платный, и он не должен повторяться при обновлении вкладки или уходить в кэш браузера. Сбой
модели не роняет дашборд: аналитика остаётся, блок сводки сообщает об ошибке.

**Выгрузка в Excel** (`app/services/export_service.py`, `GET /export/tenders.xlsx`) — один
лист, 19 обязательных полей Приложения D в точном порядке приложения, плюс двадцатой
колонкой процент победителя (без числа в файле нечего красить по требованию 5.7-07, а
порядок Приложения D ломать нельзя). Шапка файла — название, дата формирования, период
отбора; заголовки с автофильтром и закреплением; условное форматирование по сроку подачи
(<5 дней) и по проценту победителя с теми же порогами 80/50, что в интерфейсе — отчёт и
экран должны красить одну цифру одинаково.

Форматирование именно условное, а не заливка при генерации: пользователь пересортировывает
выгрузку руками, и цвет должен следовать за значением. Даты и суммы пишутся форматами ячеек,
а не строками — иначе по ним нельзя ни отсортировать, ни посчитать итог. Полная выгрузка
5401 тендера собирается за 2.1 с при требовании ≤30 с (REQ-5.7-12) и журналируется
(REQ-5.9-07).

Кнопка выгрузки есть и на списке тендеров, и на дашборде; со списка уезжают **текущие
фильтры без пагинации** (`buildExportQuery`) — отчёт повторяет отобранный срез, а не
страницу из пятидесяти строк.

**Справочник «регион → ответственный/руководитель»** (`RegionResponsible`,
`/dictionaries/region-responsibles`, секция в настройках под ролью «Администратор»). Два
поля Приложения D больше взять неоткуда — в тендерных данных этой информации нет. Отдельная
таблица, а не колонки в `regions`: справочник регионов сидируется из Приложения H и
переписывается при пересиде, а назначения вводит заказчик и терять их нельзя. Регион
поставки, если в документации не указан отдельно, дублируется из региона организатора
**в выгрузке**, а не в БД: пустое поле в базе означает «не определено», и затирать это
молчаливым дублем нельзя.

- **Не реализовано**: экспорт в формате Bitrix24 (раздел 5.10 ТЗ) — следующий этап.
  Уведомления (раздел 5.8 ТЗ) — см. раздел 18 ниже.

## 17. Фоновые задачи и отказоустойчивость (Этап 11, раздел 5.9 ТЗ)

**Очередь** (`app/core/jobs.py`, обработчики — `app/services/job_runner.py`, таблица
`background_jobs`). ИИ-анализ и расчёт соответствия ушли из HTTP-запроса в фон. Причина
простая: на крупном тендере разбор занимает десятки секунд, браузер всё это время держал
запрос открытым, при обрыве связи результат терялся, а закрытая вкладка выглядела как
«ничего не произошло». Теперь `POST /tenders/{id}/analyze` и `/evaluate` возвращают запись
задачи, а карточка опрашивает `GET /jobs?tender_id=…` раз в две секунды.

Свой мини-пул на `ThreadPoolExecutor`, а не Celery/RQ: операций всего две, обе внутри одного
процесса, и брокер добавил бы к развёртыванию Redis и отдельный воркер ради двух кнопок
(раздел 6.3 ТЗ — не усложнять инфраструктуру без необходимости). Два потока: узкое место —
YandexGPT, больше параллельных разборов упрутся в квоты модели.

Состояние задачи живёт в БД, а не в памяти: пользователь должен видеть ход работы после
перезагрузки страницы и с другого компьютера. При старте приложения `recover_interrupted_jobs`
помечает задачи, оборванные предыдущим запуском, — иначе в карточке навсегда остался бы
индикатор «идёт анализ».

**Повторные попытки** на двух уровнях. Внутри клиента модели (`run_structured`) — три попытки
с линейной задержкой: сбои YandexGPT почти всегда сетевые, квотные или «ответ не по схеме»
(обрыв по лимиту токенов), и повтор при `temperature=0` обычно проходит. На уровне задачи —
ещё один прогон целиком, если сервис всё-таки упал. Исчерпав попытки, задача честно
помечается ошибкой с текстом причины и порождает уведомление администратору.

**Изоляция** осталась там же, где была (сбой одного источника, документа или фрагмента
документации не останавливает остальные), и дополнена уведомлением: полностью сорвавшийся
опрос площадки уходит письмом администратору, а не только строкой в журнале.

**Журнал** (`app/services/log_service.py`, `GET /logs`, раздел «Логирование» в настройках).
Формат раздела 5.9 ТЗ — время, уровень, компонент, действие, результат, детали, пользователь.
Открыт всем пользователям, а не только администратору: по журналу видно, почему у тендера нет
требований или почему площадка не опрашивалась, и это вопрос не администрирования, а работы.
Раздел свёрнут по умолчанию и не опрашивает сервер, пока закрыт.

Метка времени — `clock_timestamp()`, а не `now()`: в PostgreSQL `now()` возвращает время
начала транзакции, и записи одной операции (опрос источника пишет их пачкой) получали
одинаковое время, отчего журнал показывал их в произвольном порядке. Хранение — 6 месяцев
(миграция `0022`), уборка ночью по расписанию, сама уборка тоже пишется в журнал.

## 18. Уведомления (Этап 10, раздел 5.8 ТЗ)

**Канал** — SMTP (`app/services/notification_service.py`, таблицы `notification_settings` и
`notifications`). Настройки живут в БД и правятся из `/settings`, как ключ Yandex AI Studio;
пароль ящика шифруется тем же `.credentials_key`, что и пароли площадок, и наружу отдаётся
только признаком «задан». Второй канал ТЗ («Compas», открытый вопрос №12) не реализован, но
не потребует переделки: точка отправки одна (`_dispatch`), колонка `channel` в журнале уже
есть.

**Ящик-отправитель, в отличие от ключа Yandex AI Studio, задаётся в `.env` (`NOTIFY_*`).**
Ключ ИИ выдаёт заказчик и меняет по своему усмотрению — ему нужен интерфейс. Почтовый ящик
устроен иначе: он один на установку, заводится админом почтового домена вместе с сервером,
умеет только отправлять и меняется раз в несколько лет. Храни его только в БД — и после
пересоздания базы (переезд, откат, свежий стенд) рассылка выключилась бы молча, а заметить
это можно лишь по ненаступившему письму. Поэтому `bootstrap_from_env` при старте переносит
`NOTIFY_*` в `notification_settings` — по образцу `bootstrap_admin`.

**Перенос происходит ровно один раз**: если SMTP-сервер в таблице уже задан, `.env` не
смотрится вовсе. Иначе адресаты, добавленные администратором через `/settings`, откатывались
бы при каждом перезапуске — а список получателей правят чаще всего. Чтобы перечитать `.env`,
нужно очистить поле «SMTP-сервер» в интерфейсе. Адресаты в `.env` (`NOTIFY_RECIPIENTS`) —
только удобство для чистого развёртывания; их естественное место — интерфейс.

**Пятое письмо — не по триггеру.** «Интеграции → Уведомления» умеют отправить произвольное
письмо, написанное администратором: новости платформы, регламентные работы, объявления. Оно
идёт тем же каналом и попадает в тот же журнал (триггер `manual_broadcast`, автор в колонке
`sent_by_id`), но отличается двумя вещами. Во-первых, адресаты берутся не из настроек, а из
формы — `_dispatch` принимает их параметром. Во-вторых, флаг «рассылка включена» на него не
влияет: флаг выключает автоматические письма, а здесь человек только что нажал кнопку, и
положить его письмо в журнал со статусом «не отправлено» значило бы соврать в ответ на явное
действие.

**Тело письма приходит как HTML и очищается на сервере** (`app/services/email_html.py`):
белый список тегов, все атрибуты кроме `href` у ссылок снимаются, `<script>` и `<style>`
выбрасываются с содержимым. Очистка нужна дважды — HTML едет в чужой почтовый клиент и
показывается в журнале на нашей же странице, — и делается один раз, при сохранении: в
`notifications.body_html` попадает уже безопасная разметка, поэтому интерфейс рендерит её,
а не показывает разметкой. Текстовая версия (`body`) получается из того же HTML и уходит
первой частью `multipart/alternative`: часть клиентов показывает только её, а письмо совсем
без текстовой части охотнее попадает в спам. Своя очистка вместо `bleach` — разбирается
ровно один, полностью известный нам вид HTML, и это дешевле ещё одной зависимости в сборке,
которая ставится офлайн.

**Адреса подсказываются из журнала** (`GET /notifications/recipients`): если система однажды
написала Иванову, его адрес не нужно вспоминать второй раз. Отдельного справочника контактов
нет намеренно — он немедленно разошёлся бы с тем, куда письма уходят на самом деле. Адрес
запоминается и после неудачной отправки (его уже вводили, и терять его из-за упавшего в тот
момент сервера незачем), но счётчик писем растёт только на успешных. Имя берётся из формы
записи «Иванов Иван <ivanov@example.ru>» — она же уходит в заголовок `To`.

**`python -m app.cli check-mail`** проверяет соединение и логин, не отправляя письма. На
сервере это единственный способ отличить «письма не приходят, потому что ящик не настроен»
от «не приходят, потому что триггер не сработал»: проверочное письмо из интерфейса требует и
браузера, и заполненного списка получателей. Соединение с авторизацией вынесено в `_connect`
и общее у проверки с отправкой — почти все ошибки настройки (недоступный хост, не тот порт
для выбранного шифрования, отвергнутый пароль) вылезают именно там.

**Четыре триггера раздела 5.8.** Новый релевантный тендер и высокий процент победителя
срабатывают после фоновых задач анализа и расчёта — до разбора документации ни ОКПД2, ни
процента ещё нет. Приближение срока подачи проверяется по расписанию раз в сутки: это
единственный триггер без события в системе, срок наступает сам. Критические ошибки уходят
отдельному списку адресатов — письма о сбоях нужны тем, кто чинит систему.

**Каждое письмо по тендеру отправляется один раз.** Анализ перезапускают при обновлении
документации, и повторное «новый релевантный тендер» про тот же тендер — шум, из-за которого
перестают читать и остальные письма. У критических ошибок вместо этого пауза в 30 минут на
одинаковый заголовок: упавший источник роняет задачи пачкой.

**Событие пишется в журнал даже когда почта не настроена** — со статусом «не отправлено».
Иначе после включения ящика нельзя ответить на вопрос «почему нам раньше ничего не
приходило», и нельзя проверить триггеры, не имея рабочего SMTP. Сбой отправки не поднимается
наружу: письмо — побочный эффект, недоступность почтового сервера не должна ронять анализ
тендера, из которого оно вызвано.

## 19. Документы площадок и форматы (раздел 5.2 ТЗ)

**Было.** По-настоящему документы скачивались только с ЕИС; остальные восемь адаптеров
подставляли вместо файла ссылку на карточку тендера. Внешне карточка выглядела заполненной —
документ есть, статус «успех», — но текста не было, и ИИ-анализ по таким закупкам не работал
вовсе. На ЭТП ГПБ, крупнейшем источнике, это 3400 тендеров.

**Стало.** У каждой площадки свой способ, и он выбран по тому, как она устроена:

| Площадка | Откуда берутся файлы |
|---|---|
| ЕИС | вкладка «Документы» карточки закупки (44-ФЗ и 223-ФЗ — разная вёрстка) |
| ЭТП ГПБ | блок «Документация» на странице процедуры (Nuxt SSR, файлы на `etp.gpb.ru`) |
| ЕЭТП (zakazrf) | прямые ссылки на карточке извещения |
| ТЭК-Торг | `__NEXT_DATA__` страницы → открытое API `api.tektorg.ru` |
| Фабрикант | отдельная страница документации (`file_documentations_view`) |
| Сбербанк-АСТ | таблица файлов на карточке, дорисовывается скриптом — нужен Playwright |
| Lot-online, Росэлторг, ЭТП РФ | из ЕИС по реестровому номеру закупки |

**Запасной путь через ЕИС** (`app/adapters/eis_documents.py`) работает не «на всякий случай»:
закупки 44-ФЗ и 223-ФЗ публикуются в ЕИС по закону независимо от площадки проведения, а
реестровый номер — общий ключ. Он же включается, когда родной разбор площадки ничего не дал
(у закупок 44-ФЗ на коммерческой площадке файлов в её собственной карточке обычно нет). Для
закупок с внутренним номером площадки (`ПИ602053`, `SBR003-...`) путь не применяется — в ЕИС
их нет, и ходить туда бессмысленно.

**Адрес карточки передаётся адаптеру из базы** (`download_documents(external_id, source_url)`):
иначе каждый запрос документов означал бы поиск закупки в выдаче площадки — десятки страниц,
а у закупки с истёкшим сроком подачи её там уже нет.

**Форматы** (`app/services/document_extraction.py`). К PDF/DOCX/XLSX добавились `.doc`,
`.xls`, `.rtf` и архивы `.zip`, `.7z`, `.rar`. Это не расширение ради полноты: на коммерческих
площадках `.doc` — основной формат документации, а комплект приложений часто выкладывают
одним архивом.

Разбор `.doc` — собственный (`app/services/doc_binary.py`, формат [MS-DOC]): внешние
конвертеры (`antiword`, `catdoc`) больше не поставляются в Homebrew, LibreOffice — полтора
гигабайта в образе ради одного формата, а пакеты PyPI либо обёртки над теми же бинарниками,
либо платные. Главная сложность формата — piece table: текст лежит кусками в порядке правок,
и однобайтовые куски закодированы cp1251; прочитать поток подряд — получить мусор, внешне
похожий на текст.

Имена файлов внутри ZIP из Windows восстанавливаются из cp866 (иначе «Åα¿½«ªÑ¡¿Ñ» вместо
«Приложение»), RAR распаковывается системным `bsdtar` (libarchive), тип файла при
отсутствующем расширении определяется по сигнатуре содержимого.

Скачивание переживает нестабильность площадок: до пяти попыток на файл с нарастающей паузой
и секунда между файлами одного комплекта — файловый хост ЭТП ГПБ штатно рвёт соединение при
запросах подряд, и без этого половина комплекта терялась.

Команда `python -m app.cli reparse-documents` перечитывает уже скачанные файлы новыми
разборщиками (после расширения форматов), `purge-placeholder-documents` — удаляет заглушки
прежней схемы, чтобы система скачала настоящие файлы.

## 20. Подготовка к Bitrix24 (Этап 13, раздел 5.10 ТЗ)

**Тендер → лид, а не сделка** (`app/services/bitrix_service.py`). На момент попадания к нам
тендер — это возможность, а не договорённость: заказчик о нас не знает, участие не
подтверждено. В терминах CRM это лид, который менеджер квалифицирует. Иначе воронка забилась
бы сделками, по которым никто не работает.

Стандартные поля лида заполняются напрямую, всё остальное — номер закупки, площадка, ОКПД2,
сроки, регионы, процент победителя — уходит в `UF_CRM_*`. Имена этих полей администратор
Bitrix24 заводит на своём портале, поэтому они собраны в одну таблицу `LEAD_FIELDS`: поменять
соглашение можно в одном месте, не трогая ни выгрузку, ни API.

Сумма пишется числом с точкой: «1 234 567,89» Bitrix24 при импорте примет за текст, и лид
создастся с нулевой суммой — ошибка, которая обнаруживается уже в CRM. Файл — CSV с точкой с
запятой и BOM: так его открывает Excel в русской локали без мастера импорта. Вторая строка —
технические имена полей, чтобы сопоставление колонок при импорте делалось за один проход.

**Внешний API** (`/integration/v1/...`) — отдельный контур доступа: ключ в заголовке
`X-API-Key`, а не пользовательский JWT. Интеграции нужен постоянный доступ без входа по
паролю и без восьмичасового срока жизни токена, а её обращения не должны выглядеть в журнале
действиями человека. Ключ хранится хешем (argon2, как пароли пользователей) и показывается
один раз; поиск при проверке идёт по префиксу — перебирать все ключи медленным argon2
означало бы секунды на запрос.

Ответы плоские и самодостаточные: интеграция не должна ходить в наш справочник регионов,
чтобы расшифровать код, или считать процент победителя по матрице. Параметр `updated_since`
терпим к незакодированному `+` в смещении часового пояса — в query-строке он превращается в
пробел, и строгий разбор давал бы 422 с невнятной жалобой на формат.

## 21. Карточка закупки и разбор ИИ (раздел 5.6, 5.4 ТЗ)

**Было.** Из ЕИС забиралась только строка реестра — наименование, сумма, сроки — и документы.
Всё остальное, что видит человек на странице закупки, до карточки тендера не доезжало.
Главное следствие: у тендера не определялся регион, хотя на странице он есть и в адресе
заказчика, и в его ИНН. Регион — фильтр раздела 5.6 и два поля Приложения D, и без него
тендер наполовину бесполезен.

**Карточка** (`app/adapters/eis_card.py`, таблица `tender_cards`, `GET /tenders/{id}/card`).
Забираются все вкладки извещения: общая информация, лоты, изменения и разъяснения, протоколы,
договоры, журнал событий. Адреса вкладок берутся из самой страницы, а не собираются по
шаблону: у 223-ФЗ в них есть `noticeGuid`, которого в номере закупки нет.

Разбор неспецифичный — забираются все пары «поле-значение», какие есть в секции, а не
перечисленный заранее список. Состав полей у ЕИС меняется между способами закупки и
редакциями формы, и жёсткий список молча терял бы половину карточки. По той же причине
`payload` хранится как JSONB: любая схема из колонок требовала бы миграции на каждое
изменение формы.

Вёрстка у 44-ФЗ и 223-ФЗ разная — это два разных раздела сайта: `.blockInfo` с
`.blockInfo__section` против `section.common-text` с `common-text__title/value`. Разбираются
обе; на 44-ФЗ приходится большинство закупок в базе, и поддержка только одной означала бы,
что половина тендеров осталась бы без карточки.

**Регион** (`app/services/region_resolver.py`) определяется формально, а не моделью: это
справочное соответствие, где модель и медленнее, и способна выдумать регион, которого в
адресе нет. Два источника: название региона в адресе (сверкой со справочником Приложения H) и
первые две цифры ИНН (код субъекта у ФНС; у Москвы, Санкт-Петербурга и ещё нескольких
регионов кодов несколько — они сведены в таблицу псевдонимов).

Из адреса перед поиском отрезается «уличная» часть. Первая версия этого не делала и на
реальном адресе «410012, Саратовская обл, г Саратов, ул Московская, дом 66» уверенно выдала
Московскую область: улица перевесила регион. Ошибка тихая — тендер просто уезжает в чужой
фильтр и к чужому ответственному.

Если адрес и ИНН расходятся (филиал в одном регионе, головная организация в другом), берётся
адрес, но расхождение проговаривается в объяснении: пользователь должен видеть
неоднозначность, а не получать её молча.

**Заполнение пробелов** (`tender_card_service.fill_gaps_from_card`) трогает только пустые
поля — правка человека всегда важнее автоматики — и пишет в историю тендера, откуда взялось
значение.

**Разбор ИИ** (`app/services/tender_insights.py`, `POST /tenders/{id}/insights`) — отдельная
задача от анализа требований: там модель читает документацию и извлекает технические
требования, здесь смотрит на карточку глазами человека, решающего, стоит ли участвовать.
Возвращает суть закупки, риски, пробелы в данных, восстановленные значения и чек-лист.

У каждого наблюдения обязательно есть `evidence` — поле карточки, на котором основан вывод:
без опоры суждение проверить нельзя, а решение об участии принимается по нему. Восстановленные
моделью значения применяются к тендеру только после сверки со справочником (регион) и
форматом (ОКПД2): именно здесь модель ошибается чаще всего — уверенно называет соседний
регион.

Все поля схемы ответа обязательны, без значений по умолчанию: Yandex AI Studio отвечает на
схему с необязательным полем ошибкой «Invalid JSON Schema: all fields must be required».
Побочно это к лучшему — «рисков нет» и «модель забыла про риски» перестают выглядеть одинаково.

**В интерфейсе** окно карточки расширено, вкладки источника (лоты, изменения, протоколы,
договоры, журнал) показываются только когда соответствующий раздел на сайте есть: пустая
вкладка у свежего извещения читалась бы как потерянные данные. Блок разбора вынесен в
отдельную рамку со светящейся сферой и цветовой волной (`src/components/AiOrb.tsx`, чистый
CSS без библиотек) — граница между данными источника, которые можно сверить с сайтом, и
суждением модели, которое нужно проверять, должна быть видна с первого взгляда.

## 23. AI-оценка по профилю и пересборка логики анализа (03.09.2026, разделы 5.5.1, 5.6, 7 ТЗ)

Решение 03.09.2026: у тендера появилась вторая, **главная** метрика — «AI-оценка по
профилю». Прежний процент победителя не отменён, он стал деталью (раздел 13).

**Три измерения** (`app/services/ai_profile_service.py`, `POST /tenders/{id}/ai-score`):

| Измерение | Что оценивает | Источник |
|---|---|---|
| History | Побеждали ли мы в похожих закупках | `company_participations` (реестр контрактов ЕИС по ИНН + ручной ввод) + `similar_tenders`; `tender_outcomes` — запасной путь, см. раздел 24 |
| Task | Соответствует ли предмет закупки опыту и продукции компании | текст тендера + `company_profile.past_projects` |
| Competencies | Хватает ли допусков и стажа | требования и разделы «Дополнительно» + `company_profile.licenses` |

Итог — среднее по **доступным** измерениям. History без данных остаётся `null` и
исключается из расчёта, а не считается нулём: ноль читается как «проверили и не нашли ни
одной победы», то есть клевещет на компанию. То же правило действует во всём новом коде —
вкладки «Расчёт» и «Похожие» показывают «данных нет», а не нули.

**Прослеживаемость — не опция.** Модель не называет проценты «из головы»: ей выдаются
пронумерованные требования тендера и пронумерованные строки профиля компании, а в ответе
она обязана перечислить номера, на которые опирается. Номера превращаются в `*_evidence` со
ссылками на реальные `requirements.id` и ключи полей профиля; номера вне диапазона
отбрасываются — «опора», которой не было в промпте, хуже, чем её отсутствие. Рядом с
оценкой сохраняется снимок профиля (`company_profile_snapshot`): без него после правки
профиля старые оценки стали бы необъяснимыми.

**Три вызова вместо одного.** Task, Competencies и текстовый блок «Резюме / Слабые места /
Стратегия» запрашиваются отдельно, разделы вкладки «Дополнительно» — ещё двумя вызовами:
длинный JSON рвётся по лимиту токенов на выходе. Сбой одного вызова не отменяет остальные —
оценка сохраняется с тем, что посчиталось, и честно сообщает, чего не хватает.

**Версионность** — как у процента соответствия: новая оценка добавляется строкой, прежняя
гасится. Правка профиля компании не запускает массовый пересчёт: он стоит денег и времени
по каждому тендеру, а какие из них актуальны — решает человек.

**Профиль компании** (`company_profile`, `app/services/company_profile_service.py`,
`/company-profile`) — вход обоих измерений. Заполняется вручную в настройках; пока он пуст,
расчёт отклоняется с понятным текстом ДО постановки фоновой задачи, а не падает в фоне.

**`stage` вместо `relevance_status`.** У тендера появился внутренний пайплайн:
`ai_selected → under_review → application_submitted → won/lost/rejected`. Колонка
`relevance_status` из БД убрана, но поле осталось во внешнем REST API, Excel-выгрузке и
Bitrix-интеграции — это внешний контракт. Реализовано гибридным свойством `Tender`
(`STAGE_TO_RELEVANCE`/`RELEVANCE_TO_STAGE`): и чтение, и запись, и фильтры уровня SQL
(`Tender.relevance_status.in_([...])`) продолжают работать, хотя колонки нет. Подтверждение
релевантности при этом не откатывает уже поданную заявку назад в «на проверке».

`stage` ортогонален `status` (состояние закупки на площадке) и не сливается с ним: иначе
терялось бы либо «идёт приём заявок», либо «заявка подана». Kanban переведён на `stage`,
`status` остался фильтром и бейджем.

**Похожие тендеры** (`app/services/similarity_service.py`). Вектор считается через
**Yandex AI Studio Embeddings** — это другой вызов API, не генерация текста через YandexGPT.
ТЗ (раздел 6.2) фиксирует `pgvector`, но расширения нет ни в образе `postgres:15`, ни в
локальной установке: миграция с `CREATE EXTENSION vector` уронила бы разработку и тесты у
всех разом. Поэтому вектор лежит в JSONB, а косинус считается перебором в Python — на
нынешнем объёме это десятки миллисекунд. Переход на `pgvector` с ANN-индексом остаётся
задачей уровня инфраструктуры; интерфейс модуля при этом не меняется.

**Новые таблицы:** `company_profile`, `ai_profile_scores`, `tender_embeddings`,
`similar_tenders`, `niche_statistics` (агрегаты по нише ОКПД2 + регион для вкладки
«Расчёт» — другая гранулярность, чем `tender_outcomes`, и путать их нельзя). Миграция —
`0026_ai_profile_and_stage`.

**Интерфейс.** Добавлен пятый режим отображения — двухпанельный master-detail (список
слева, карточка справа), он же режим по умолчанию; Kanban, таблица и таймплан остались.
Карточка разложена по вкладкам раздела 5.6 ТЗ: Основное, Дополнительно (девять разделов
извлечённых условий), Документы (автоклассификация и звёздочка приоритета), Расчёт,
Конкуренция, Заявка, Похожие. Содержимое карточки вынесено в `TenderDetailPanel`, а модалка
стала обёрткой над ним — иначе двухпанельный режим и модалка разъехались бы в две
расходящиеся карточки.

**Уведомления** (раздел 18) переведены с процента победителя на `overall_score`: триггер
`high_win_percentage` → `high_ai_score`, порог `win_percentage_threshold` →
`ai_score_threshold` (значение порога при миграции сохраняется).

## 24. История участий и источник измерения History (04.09.2026, разделы 5.5.1, 5.6, 7 ТЗ)

Уточнение ЧТЗ v3.3: измерение History перестало ждать, пока появится источник по-тендерных
исходов. Считается оно теперь по **реальной истории участия МИРТЕК в закупках** — таблица
`company_participations`.

### Почему не OPTI

ЧТЗ предписывал наполнять таблицу синхронизацией с `mirtek.optihub.ai`
(`/api/company/participations`). От этого отказались 04.09.2026 по решению заказчика: у OPTI
нет ни публичного API, ни выдаваемых нам токенов — единственный доступ, зафиксированный в
ТЗ, это сессионный JWT из чужого браузера. Строить на нём работающую функцию значит получить
кнопку, которая не нажимается, и зависимость от чужого сервиса там, где данные общедоступны.

**Источник — реестр контрактов ЕИС** (`app/adapters/eis_contracts.py`): открыт, ищется по ИНН
поставщика, не требует ни учётной записи, ни ключа. Фильтр — параметр `supplierTitle`, куда
подаётся ИНН (проверено на боевой выдаче: с ИНН — десятки записей конкретной компании, без
него — весь реестр на десятки миллионов; соседний `supplierIdCode` площадкой игнорируется).
TLS — та же цепочка `Russian Trusted CA`, что у адаптера ЕИС.

### Что источник даёт и чего не даёт — и почему это отдельно обработано

В реестре контрактов лежат **только заключённые контракты**, то есть исключительно наши
победы: проигрышей и снятий с торгов там нет по устройству. Наивный расчёт дал бы win-rate
100% и History 100% по любому тендеру — цифру, которая выглядит убедительно и при этом ничего
не значит.

Поэтому источник помечен как `WINS_ONLY_SOURCES`, и:

* **History отказывается считать долю побед**, если вся относящаяся к делу выборка пришла из
  такого источника: `history_score = null`, измерение исключается из итога. Сами победы не
  теряются — они уходят в комментарий («Подтверждённых побед по этой закупке: N») и в
  `history_evidence`, где их видит человек;
* **интерфейс говорит об этом вслух** — предупреждение под сводкой и подпись «по выборке без
  проигрышей» вместо знаменателя;
* **одна внесённая руками проигранная закупка** снимает ограничение: выборка перестаёт быть
  однобокой, и доля побед считается обычным порядком.

Это зеркальное отражение правила «ноль ≠ нет данных», уже принятого в проекте: цифра,
посчитанная по заведомо однобокой выборке, врёт так же, только в другую сторону.

### Проигрыши: почему их нельзя выгрузить и как они получаются

Прямого источника проигрышей не существует, и это устройство раскрытия информации, а не наш
недосмотр:

* реестра протоколов с поиском по участнику в ЕИС нет — `/epz/protocol/…` отвечает 404 на все
  варианты, поиска по участнику нет ни в одном открытом реестре;
* в протоколах электронных процедур участники **обезличены**: в таблице стоят
  идентификационные номера заявок вида `120100244`, а не ИНН. Раскрывается только победитель,
  после заключения контракта.

Поэтому проигрыши **вычисляются**, а не выгружаются
(`company_participation_service.derive_outcomes_from_pipeline`, адаптер
`app/adapters/eis_results.py`): закупка, которую тендерный отдел отметил как «заявка подана»
(`stage = application_submitted`), завершилась, а контракт достался не МИРТЕК — значит,
проигрыш. Оба факта внешние по отношению к оценке результата: победитель берётся из ЕИС
(вкладка «Результаты определения поставщика» карточки закупки), а участие — из собственного
пайплайна, куда его ставят до того, как исход стал известен.

Границы вывода заданы жёстко: контракт ещё не заключён → исход неизвестен, а не проигран;
контракт достался нам → запись не создаётся вовсе, победы приходят из реестра контрактов и
дублировать их нельзя (удвоился бы знаменатель win-rate); недоступная закупка не обрывает
разбор остальных. Тип процедуры (`ea20`, `ok20`, …) в адресе заранее неизвестен и берётся из
редиректа обобщённого `/epz/order/notice/view/common-info.html`.

Всё, что не покрылось и этим — участие в закупках вне ЕИС, снятия с торгов, история до
появления системы, — вносится вручную через форму.

### Как выбираются «относящиеся к делу» участия

(`ai_profile_service._relevant_participations`)

* участие привязано к тендеру из списка похожих (`similar_tenders`) — та же закупка по смыслу;
* либо у участия тот же заказчик, что у тендера. Второй признак работает даже когда эмбеддинги
  ещё не посчитаны, а «выигрывали ли мы у этого заказчика» — самый прямой ответ на вопрос
  History. Записи, попавшие по обоим признакам, не удваиваются.

Формула — доля побед среди участий с ИЗВЕСТНЫМ исходом. `unknown` в знаменатель не идёт:
неполнота данных не должна выглядеть как череда поражений. Снятия с торгов (`disqualified`) в
знаменателе остаются — контракт мы не получили, — но выносятся в комментарий отдельной цифрой:
лечатся они оформлением заявки, а не ценой. Когда своей истории нет вовсе, включается запасной
путь по `tender_outcomes`; когда нет и его — честное «недостаточно данных».

### Выгрузка

`POST /company-participations/sync`. Идёт по ИНН из `company_profile`; без ИНН запрос
отклоняется с понятным текстом, а кнопка в интерфейсе заблокирована. Ключ дедупликации —
номер **извещения** закупки (а не контракта: тендеры в нашей базе хранятся под номером
извещения, иначе связка не нашлась бы никогда); когда извещения в карточке нет — например, у
закупки у единственного поставщика по ч. 12 ст. 93 — берётся реестровый номер контракта.
Повторный запуск обновляет записи, а не плодит их, и **не трогает поля, которые ведёт
человек** — заметку «Выводы» и уже проставленный вручную исход.

Выполняется синхронно: несколько страниц поисковой выдачи по полсотни записей, десятки секунд
это не занимает, а результат человек ждёт на экране.

### Юридические данные профиля

`company_profile` получил `legal_name`, `inn`, `kpp`, `ogrn`, `registration_date`,
`legal_address` и `field_sources`. КПП — отдельным полем (миграция `0028`), а не внутри
реквизитов: в заявке требуется пара ИНН/КПП, и у обособленных подразделений КПП свой при
общем ИНН.

**Два источника автопоиска за одной кнопкой** (`GET /company-profile/egrul-lookup`), выбор по
виду запроса:

* ссылка на карточку **rusprofile.ru** (`app/adapters/rusprofile.py`) → разбор карточки. Это
  единственный путь, дающий КПП — в выдаче ЕГРЮЛ его нет; он же выручает, когда у ЕГРЮЛ
  включается защита от автозапросов. Данные берутся из якорей `id="clip_*"` и микроразметки
  schema.org, а не из вёрстки: служебные атрибуты «скопировать значение» меняются реже
  оформления. Поиск по ИНН на самом rusprofile программно недоступен (`/search?query=…`
  отвечает 404 при любых заголовках и с сессионной cookie), поэтому принимается именно
  ссылка на карточку — притворяться, что мы умеем там искать, значило бы падать на каждом
  втором вызове;
* ИНН, ОГРН или наименование → **ЕГРЮЛ** (`app/services/egrul_service.py`), первоисточник.

Автопоиск **ничего не сохраняет**: он возвращает кандидатов, подставляет их в форму, а
записывает человек кнопкой «Сохранить». Разделение принципиальное — профиль подаётся в
обоснования AI-оценки, и непроверенный результат внешнего сервиса там неотличим от
подтверждённого факта. Что откуда взялось, помнит `field_sources`
(`{source: auto_search|manual, verified_by_user}`).

### Интерфейс

«Моя компания» — **отдельный раздел приложения** (`/company`, пункт сайдбара), а не секция
настроек. Вынесен сознательно: настройки задают один раз и почти не открывают, а профиль и
история участий питают главную метрику каждого тендера и пополняются регулярно — прятать за
«Настройками» источник цифр, которые люди видят в списке закупок каждый день, неправильно.

Две вкладки: «Профиль компании» и «История участий» (сводка
участий/побед/проигрышей/дисквалификаций/win-rate, кнопка обновления из ЕИС, форма ручного
добавления). Обе монтируются сразу: профиль — источник признака «ИНН заполнен» для соседней
вкладки.

## 25. Профиль релевантности (04.09.2026, раздел 5.1.1 ТЗ)

Закрывает главный пробел сбора: до этого охват системы был **константой в коде** — каждый из
девяти адаптеров искал две фразы, «счетчик электрической энергии» и «прибор учета
электрической энергии». Всё, что заказчики формулируют иначе — поверка, монтаж, замена,
техобслуживание, АСКУЭ, — в систему не попадало вовсе. Отсюда и расхождение с референсной
OPTI, у которой девять групп ключевых слов.

**Что это.** Дешёвый текстовый фильтр ДО дорогого ИИ-анализа. Отвечает не «подходит ли
прибор под ТЗ» (матрица соответствия, 5.5.2) и не «стоит ли идти» (AI-оценка, 5.5.1), а
«стоит ли вообще тратить на этот тендер вызов модели».

**Девять групп потребностей** (`app/seed/search_profile_data.py`): поставка оборудования
учёта (АСКУЭ/АИИС КУЭ/УСПД), бренд и каналы связи, ОКПД 26.51.63, счётчики и приборы учёта,
замена, монтаж, поверка, техобслуживание и ремонт, комплексные услуги. Группа — это отдельный
тип потребности заказчика: один и тот же прибор закупается по разным веткам классификатора
(поверка — 71.12.40, поставка — 26.51.63, монтаж — 43.21), и слитый в кучу список слов не дал
бы ни настроить охват по одному типу, ни понять потом, почему тендер попал в выборку.

**Синтаксис ключей** (`app/services/relevance_service.py`):

* `слово*` — по основе слова;
* `(a* b*)~N` — все слова в пределах N слов друг от друга, в любом порядке (в закупках
  встречается и «поверка счётчиков», и «счётчиков поверка»);
* исключающие ключи на уровне группы — совпало, и группа не срабатывает, даже если совпали
  положительные.

Сопоставление своё, а не через `tsquery`, как предлагает ТЗ: фильтр применяется к одному
тендеру в момент сохранения, когда текст ещё в памяти, и запрос в БД ради каждой записи был
бы лишним кругом. Стемминг — сравнение по префиксу фиксированной длины, а не «отрезать N
символов с конца»: при переменном усечении «счетчик» давал бы основу из четырёх букв, а
«счетчиков» — из шести, и слово переставало совпадать само с собой.

**Исключения — не украшение.** Рабочие группы (поверка, замена, монтаж, ремонт) без запрета
на воду, газ, тепло, медицину и пожарную безопасность собирают эти работы по любой отрасли.
Названия самого ресурса («воды», «газа», «тепла») берутся в точной форме, а не через `*`:
`-вод*` заодно выбросил бы «провода» и «водитель», которых в электрических закупках хватает.
Проверено на боевой выдаче: «Выполнение работ по установке/замене прибора учёта … тепловой
энергии и теплоносителя» отсеивается, «Услуги по сервисному обслуживанию приборов LECO» —
проходит.

**Приоритет при выборе группы.** Сначала полный проход по ключевым словам, и только потом —
по кодам ОКПД2. Вердикт «релевантен» от порядка не зависит, но в карточке пишется, какая
группа сработала, и по неверной подсказке профиль не настроить. Код ОКПД2 при этом не
воскрешает тендер, отклонённый исключением группы, — иначе закупка воды по коду 26.51.63.120
попадала бы к нам через группу, где вода прямо запрещена.

**Как связано со сбором.** `get_adapter(key, search_keywords=...)` берёт фразы из активных
групп (`relevance_service.search_queries`) — 13 фраз вместо прежних двух. Отметка результата
(`tenders.passed_relevance_filter`, `tenders.matched_keyword_group_id`) ставится сразу при
сохранении тендера, до скачивания документации и до вызова модели.

**Не прошедший тендер не удаляется.** Он помечен и скрыт в списке галочкой «Только прошедшие
профиль релевантности» (по умолчанию включена), но виден при её снятии: профиль настраивают
люди, и он вполне может оказаться слишком узким. `passed_relevance_filter = NULL` («фильтр
ещё не применялся») трактуется как «показывать» — тендеры, собранные до появления профиля,
никто не проверял, и прятать их как нерелевантные значило бы соврать. То же правило, что с
History и нулём. Та же галочка прячет и явное «нет» модели (`ai_relevant = FALSE`, раздел
5.4): ключевые слова слепы, «счетчик*» пропускает счётчики банкнот и посетителей, и без
второго слоя всё, что модель уже отклонила, продолжало висеть в списке «по профилю».
Непроверенное моделью (`NULL`) остаётся видимым по тому же правилу «не смотрели ≠ не
подходит». Чтобы хвост непроверенного не копился, после каждого опроса площадок (плановый и
по кнопке) модель добирает до 200 прошедших профиль закупок (`check_pending_ai_relevance`).

**Профиль заводится при старте** (`relevance_service.bootstrap` из `lifespan`, в фоновом
потоке), а не при первом заходе в «Настройки». Пока он создавался лениво, свежий сервер без
визита в настройки жил без отбора: `active_groups` отдавал пустой список, адаптеры ходили на
площадки с двумя фразами из констант, каждый собранный тендер оставался с `NULL`, и список
«по профилю» показывал всю выдачу ЭТП ГПБ — бумагу для заметок, замену светильников,
грозозащиту (находка тестировщицы 19.09.2026). Бутстрап заодно применяет профиль ко всем
записям без отметки, поэтому миграция, меняющая группы (0053), может просто сбросить отметки
в `NULL` — пересчёт произойдёт при следующем старте.

**Код ОКПД2 сам по себе проходит только товар.** Раз код без ключевых слов засчитывается за
совпадение, в группах может стоять только код, который означает ровно наш предмет закупки:
26.51.63.130 «Счётчики производства или потребления электроэнергии». Коды отраслей — 43.21
(все электромонтажные работы), 71.12.40 (вся метрология), 33.12.2/33.13 (ремонт любого
оборудования), 33.20.42, а также 26.51.63 с ветками воды и газа — из групп сняты (миграция
0053): по 43.21.10 в список пришла замена светильников в аэропорту. Работы и услуги по
приборам учёта ловятся ключевыми словами групп.

**Стемминг ограничен длиной слова.** Сравнение по основе из пяти букв само по себе считало
«миртек» и «миртелеком» одним словом — и все закупки заказчика МИРТЕЛЕКОМ (оптические муфты,
дизельные электростанции, грозозащита) проходили группу «Бренд и каналы связи». Теперь слово
текста может быть длиннее ключа не более чем на три буквы — длина русского окончания.

**Про этап «AI отобрал».** До профиля это была надпись на всём подряд: `stage` со значением
по умолчанию `ai_selected` получали все 7166 собранных тендеров, никакого отбора за ней не
стояло. Теперь отбор есть, и он виден: в списке и на доске по умолчанию только то, что прошло
профиль, а в карточке написано, какая группа сработала. Сам `stage` остаётся человеческим
пайплайном (`ai_selected → under_review → application_submitted → won/lost/rejected`), а
машинное решение живёт в отдельном поле — смешивать их нельзя, иначе не отличить «система
отобрала» от «человек подтвердил».

**Настройка** — «Настройки → Профиль релевантности»: группы с ключами, исключениями и кодами,
отдельно список поисковых фраз (именно он объясняет пробелы в сборе) и кнопка пересчёта по
всем собранным тендерам. Без пересчёта правка групп меняла бы только будущие сборы, а старые
отметки остались бы от прежних настроек.

**Новые таблицы:** `search_profiles`, `search_keyword_groups`; новые колонки `tenders`.
Миграция — `0029_search_profile`.

## 26. ИИ-отбор закупок и разбор расхождений с OPTI (04.09.2026, разделы 5.1.1, 5.4, 5.6 ТЗ)

### Почему карточка расходилась с референсом

Сверка одной и той же закупки (№ 32616330676, метрологические услуги для АО «ИЭСК») вскрыла
три разные причины, которые легко спутать в одну:

1. **Неверный ОКПД2 — настоящий баг.** У нас стоял `23.12` («стекло обработанное») вместо
   `71.12.40.120` («услуги в области метрологии»). Код выуживался регулярным выражением из
   текста документации, а выражение `\d{2}(\.\d{1,2}){1,3}` радостно совпадало с датой:
   «Дата подведения итогов: 23.12.2026» → `23.12`. Исправлено двумя шагами:
   * даты маскируются ДО поиска кодов, и отличаются **по смыслу чисел**, а не по форме: у
     даты первое число — день (1–31), второе — месяц (1–12). Слепая маска по форме съедала
     как раз настоящие коды (`71.12.40` под неё подходит идеально);
   * ОКПД2 берётся из таблицы лотов карточки ЕИС (столбец «Классификация по ОКПД2») и
     **перезаписывает** значение, найденное в тексте. Раньше приоритет был обратным
     («заполняем, только если пусто»), и достоверный код проигрывал случайному совпадению.

2. **AI-оценка у нас не считалась автоматически** — только по кнопке, тогда как OPTI
   показывает её сразу. Закрыто ИИ-отбором (ниже) и автозапуском при сборе.

3. **«Площадка» означает разное.** Мы пишем источник, из которого закупка собрана (ЕИС), а
   OPTI — фактическую ЭТП, на которой идут торги (АО «ЕЭТП»). Оба значения верны, это разные
   вопросы; ссылка на площадку у нас есть в карточке закупки.

### ИИ-отбор: «Наша тематика» (до 18.09.2026 — «Подобрано ИИ»)

`app/services/ai_relevance_service.py` — второй слой отбора поверх профиля ключевых слов.
Разделение задач:

* **профиль** (раздел 25) — дешёвый и слепой: «есть ли в тексте нужные слова». Без сети и без
  денег, применяется ко всему потоку;
* **модель** — дорогая и понимающая: «это правда наша закупка». Отличает поставку счётчиков
  от строительно-монтажных работ, где приборы учёта упомянуты в составе объекта. Проверено на
  боевых данных: из 20 прошедших профиль закупок модель подтвердила 16 и отклонила 4 — все
  четыре оказались стройкой с попутным упоминанием приборов.

Порядок обязателен: сначала слова, потом модель. Иначе каждый вызов уходил бы на весь поток со
всех источников — ровно то, от чего предостерегает раздел 5.1.1 ТЗ.

**Это не AI-оценка по профилю (5.5.1).** Та отвечает «стоит ли идти и с какими рисками»,
требует заполненного профиля компании и трёх вызовов модели. Здесь один короткий вызов и один
вопрос: наше это или нет. Отбор не может ждать, пока заполнят профиль компании, — иначе список
остаётся неразобранным.

**Отказ модели — не «нерелевантно».** Сбой сети, кончившаяся квота, выключенная интеграция
оставляют `ai_relevant = NULL` («не проверяли»). Записать `false` значило бы спрятать закупку
из-за нашей же аварии — та же ошибка, что ноль вместо «нет данных» в History. Три сбоя подряд
без единой удачи останавливают пачку: это недоступная интеграция, а не свойство данных.

**Когда запускается.** Новые закупки проверяются сами сразу после сбора (до 25 штук за опрос —
защита от площадки, вывалившей сотню записей). Накопленный архив разбирается кнопкой
«Проверить моделью» в настройках, пачками по 50, с остатком на самой кнопке.

**Как показывается.** Метка «Наша тематика» в карточке списка (с причиной в подсказке) и
сортировка: при сортировке по умолчанию подобранное идёт первым. Как только человек выбрал
столбец сам, правило снимается — он попросил конкретный порядок, и подмешивать свой значит
спорить с пользователем. Есть фильтр «Только подобранные ИИ».

### Переработка страницы тендеров

Раньше страница прокручивалась целиком: чтобы дочитать карточку, нужно было сначала пролистать
шапку, переключатель видов и три ряда фильтров. Теперь `AppShell` фиксирует высоту (`h-screen`
вместо `min-h-screen`), а страница — колонка, где прокручивается только содержимое. Двухпанельный
режим берёт высоту у родителя вместо `calc(100vh - 320px)`: подобранная константа ломалась от
любой правки шапки.

Верх собран в одну плотную строку: поиск, переключатель видов, кнопка «Фильтры» с числом
активных условий и счётчик «Найдено N тендеров». Панель фильтров раскрывается целиком и по
умолчанию свёрнута. Цифра на кнопке нужна именно потому, что панель скрыта: иначе спрятанный
фильтр становится невидимой причиной пустого списка, и человек ищет ошибку в данных, а не в
своих настройках. Полезная высота карточки выросла с 193 до 309 пикселей на том же экране.

**Markdown в «Дополнительно».** YandexGPT возвращает пункты с `**жирным**`, даже когда
просишь простой текст. Показывать звёздочки нельзя, вычищать разметку на бэкенде — потеря:
выделение несёт смысл, это подпись поля внутри пункта. Компонент `InlineMarkdown` разбирает
только `**…**` — свой разбор вместо библиотеки markdown сознательно: нужен ровно один приём, а
полноценный рендерер это и лишняя зависимость, и лишняя поверхность (ссылки, HTML, картинки из
ответа модели).

**Новые колонки:** `tenders.ai_relevant`, `ai_relevance_reason`, `ai_relevance_confidence`,
`ai_relevance_checked_at`. Миграция — `0030_ai_relevance`.

## 27. Правки интерфейса и терминология этапов (04.09.2026)

**«AI отобрал» переименован в «Новая».** Прежняя подпись обманывала: `stage = ai_selected` —
это значение по умолчанию, которое получает КАЖДАЯ собранная закупка (7163 из 7166 на момент
проверки), никакого решения модели за ней не стоит. Решение модели — отдельная метка
«Наша тематика» (`tenders.ai_relevant`, раздел 26), и две разные вещи под похожими названиями
путали работу. Значение в БД (`ai_selected`) не менялось: это внешний контракт (Excel,
integration API, Bitrix), менялась только подпись в интерфейсе и выгрузке.

**Три ортогональных признака, которые нельзя смешивать:**

| Признак | Кто ставит | Отвечает на вопрос |
|---|---|---|
| `status` | площадка | что с торгами: приём заявок / оценка / завершена / отменена |
| `stage` | человек | что МЫ делаем: новая → на проверке → заявка подана → исход |
| `ai_relevant` | модель | наша ли это закупка вообще |

К полю этапа добавлена подсказка (`stageHint`): список из шести значений без пояснений
читается как набор синонимов, а «Заявка подана» вдобавок влияет на учёт проигрышей
(раздел 24) — об этом надо знать в момент выбора, а не после.

**Вкладка «Похожие» убрана.** Она требует посчитанных эмбеддингов по представительному
корпусу, до тех пор честно показывала «недостаточно данных» и только занимала место в ряду.
Похожие закупки никуда не делись — они перечислены в блоке «AI-оценка по профилю» как
обоснование измерения History.

**Ряды карточки — одна строка с горизонтальной прокруткой** вместо переноса. Вкладок бывает
до десятка (у закупки с лотами, протоколами и договорами), и перенос съедал высоту у самой
карточки, а ряд «прыгал» при переключении закупок. Вместе с уплотнением шапки страницы
полезная высота карточки выросла со 193 до 425 пикселей на том же экране — больше чем вдвое.

## 28. Источники справочника продукции: ФГИС в планировщике и каталог МИРТЕК (04.09.2026, разделы 4.2, 4.3, 5.1, 5.3, 5.9 ТЗ)

До этой итерации оба источника характеристик были разовыми операциями «по кнопке»: автопоиск
кодов СИ в ФГИС и поиск руководства на сайте производителя запускал человек из карточки.
Справочник от этого наполнялся ровно настолько, насколько у кого-то доходили руки, а модуль
сопоставления регулярно упирался в «информация отсутствует» по моделям, данные о которых
лежат в открытом реестре. Теперь оба — полноценные источники в общем планировщике.

### Почему они в `sources`, но не в опросе тендеров

Строки ФГИС и «Сайт МИРТЕК» заведены в ту же таблицу `sources`, что и двенадцать площадок:
так они видны и управляются в общем разделе «Источники» — со статусом, расписанием, пингом
доступности и примечанием. Но контракт адаптера у них другой: не «список новых тендеров», а
«карточка типа СИ» / «карточка товара». Поэтому `poll_all_active_sources` их пропускает по
`CATALOG_SOURCE_TYPES` (`app/models/source.py`), а сами адаптеры лежат в отдельном реестре
`CATALOG_ADAPTER_KEYS`. Без этого фильтра плановый опрос площадок ежедневно звал бы у них
несуществующий `list_new_tenders` и писал в журнал ложную ошибку.

### Две модели работы вместо одной

У тендерной площадки режим один — «забрать всё новое». У ФГИС их два, и это не усложнение
ради полноты:

| Триггер | Когда | Что делает |
|---|---|---|
| Расписание (`FGIS_REVALIDATION_TIME`, по умолчанию 04:00) | раз в сутки | ревалидация сохранённых карточек: цел ли номер ГРСИ, не вышла ли новая редакция «Описания типа», не истекло ли свидетельство об утверждении типа |
| Событие из модуля сопоставления | немедленно | производитель, по которому сопоставлять было нечем, ставится в очередь на поиск в реестре — не дожидаясь следующего суточного цикла |

Оба идут через **одну очередь** `catalog_lookup_queue` и один обработчик
(`app/services/fgis_catalog_sync.py`): триггер задаёт только `reason`, а не свой путь
выполнения. Иначе логика обращения к нестабильному реестру существовала бы в двух копиях,
которые неизбежно разошлись бы.

Очередь (`app/services/catalog_queue_service.py`) — отдельная от `background_jobs`, потому
что та привязана к тендеру (`tender_id`), а здесь объект — модель прибора или код СИ.
Устройство то же: состояние в БД (переживает перезапуск), повтор при сетевой ошибке,
изоляция сбоя одной задачи, уведомление администратора о критической ошибке (раздел 5.9 ТЗ).
Пул — **один поток**: и ФГИС, и сайт производителя чужие серверы, и параллелить обращения
к ним ради скорости заполнения своего справочника невежливо.

### Дисамбигуация кандидатов: случай «Пульсар»

`app/adapters/fgis_matching.py` — отдельный модуль с юнит-тестами
(`tests/test_fgis_matching.py`), и вынесен он не ради чистоты слоёв, а из-за конкретной
ошибки. Поиск в реестре полнотекстовый, и по торговой марке «Пульсар» он возвращает
вперемешку счётчики электроэнергии, **пожарные извещатели** и расходомеры воды от разных
юрлиц. Автосохранение первого попавшегося кандидата подкладывало в справочник «Описание
типа» пожарного извещателя — то есть модуль сопоставления начинал сверять требования тендера
с характеристиками чужого прибора, и на выходе получался правдоподобный, но неверный процент.

Отбор идёт по трём признакам, от надёжного к слабому:

1. **Вид измерений.** Справочник проекта ограничен счётчиками электрической энергии (раздел
   2.2.1, 2.2.2 ТТ), и наименование типа в реестре прямо называет класс прибора. Кандидаты
   явно другого вида отбрасываются **с указанием причины** — «отклонён 55555-13, это
   извещатель пожарный» полезнее, чем молчаливое исчезновение из выдачи.
2. **Обозначение типа** против искомой модели. Без этого шага любой производитель с широкой
   линейкой всегда уходил бы «на проверку». Сравнение по «скелету» строки с приведением
   латинских омоглифов к кириллице: «МИРТЕК-12-РУ» и «MИPTEK-12-PУ» визуально одно и то же,
   но это разные кодовые точки.
3. **Способ сопоставления с производителем** — совпадение по юрлицу надёжнее совпадения
   только по марке; марка не обязана принадлежать нужной компании, ровно на этом «Пульсар»
   и ловится.

Автоматически сохраняется только кандидат, оставшийся единственным. Всё остальное —
`review_status = needs_review` на записи, WARNING в журнале со **списком всех рассмотренных
кандидатов** и та же пометка на карточке товара (иначе человек увидел бы просто пустые
характеристики без объяснения). Неопознанное наименование при этом не отбрасывается, а
уходит человеку: реестр формулируется свободно, и глухой отказ терял бы законные записи.

`needs_review` — не то же самое, что `verified_by_user`. Там «человек подтвердил
корректность», здесь «системе не хватило оснований решить самой».

### Каталог МИРТЕК: что показала разведка сайта

`app/adapters/mirtek_catalog.py` писался по реальной разметке `mirtekgroup.com`
(разведка 04.09.2026), а не по предположениям, и почти всё неочевидное в нём — след
конкретной находки:

- **Область сужена до двух категорий** — однофазные и трёхфазные счётчики электроэнергии.
  Вода, тепло, газ, высоковольтные приборы, ПО, щитовое оборудование и поверочные установки
  не собираются: и список конкурентов, и перечень характеристик в ТЗ целиком про
  электросчётчики.
- **Карточка категории — это базовая модель, а не товар.** Под ней лежат ссылки-исполнения
  по заводам: «Таганрог», «Владивосток», «Казахстан», «Беларусь». Российские (`-ru-` в slug)
  сохраняются как **отдельные записи**, и это не формальность: у МИРТЕК-12-РУ-D17 срок
  службы в таганрогском исполнении 48 лет, во владивостокском — 35, и документы разные.
  Казахстанские (`-kz-`) и белорусские (`-by-`) не собираются вовсе — для российских
  тендеров нерелевантны. Модель, выпускаемая только в Беларуси (МИРТЕК-1-BY-W6b), в
  справочник не попадает совсем.
- **Пометка «Снят с производства»** стоит в `<i>` рядом с названием модели и относится ко
  всем её исполнениям — прямой источник поля `Статус`.
- **Набор ключей во вкладке «Характеристики» у трёхфазных совпадает с однофазными** (те же
  13 полей, различаются только значения) — проверено на МИРТЕК-32-РУ-D37 и МИРТЕК-32-РУ-SP31.
  Это снимает опасение п.2.3 задания, но парсер всё равно универсальный (см. ниже).
- **Два поколения карточек.** Это выяснилось только на живом обходе всех 26 позиций: у новых
  моделей (D17, D37, SP31) ключи «Класс точности по активной/реактивной энергии» и «Базовый
  ток», а у выпущенных раньше (W2, W3, W6, SP2, D33) — «Класс точности по ГОСТ 31819.21-2012»,
  «Базовый (номинальный) ток», «Максимальная сила тока» и мощности с добавкой «нормальной
  температуре, номинальной частоте». Одни и те же величины, записанные по-разному; без обоих
  наборов синонимов половина каталога осталась бы без электрических характеристик.
- **Количества фаз и типа монтажа в таблице характеристик нет вовсе.** Первое выводится из
  категории, второе — с бейджа страницы категории («DIN-рейка» / «Сплит» / «Щиток»). Оба
  регулярно стоят требованием в закупках, и терять их нельзя.
- **Ссылки на документы ведут на `/download/<id>` с редиректом 302**, а не на файл.
- `robots.txt` раздел `/produkciya/` не закрывает; закрыты `/search`, `/admin/`, `/en/` и
  служебные каталоги, которые адаптер и так не трогает. Пауза между запросами — 0,7 с.

### Как содержимое карточки попадает в справочник

Три пути, по убыванию надёжности (`app/services/mirtek_catalog_sync.py`):

1. **Таблица «Характеристики»** — пары ключ-значение раскладываются по Приложению C через
   словарь синонимов. Парсер **универсальный**: берёт любые пары, а не заданный список.
   Неизвестные ключи не выбрасываются, а ложатся в `products.extra_specifications` (JSONB) и
   показываются в интерфейсе отдельным блоком — набор полей на сайте шире справочника и
   меняется без предупреждения, а потеря значения обнаружилась бы только когда по нему придёт
   требование тендера.
2. **Метаданные карточки** — модель, артикул, исполнение, статус, ссылки на документы.
   «Сертификат об утверждении и описание типа» на сайте один комбинированный PDF, и он
   заполняет **оба** поля Приложения C: и «Ссылка на сертификат», и «Ссылка на описание типа».
3. **Блок «Ключевые особенности»** — свободный текст, уходит в тот же YandexGPT-модуль, что
   разбирает требования тендеров (`document_source="manufacturer"` → группы «Интерфейсы и
   связь», «Протоколы обмена», «Функциональные возможности» и т.д.). Регулярками его не берут
   сознательно: формулировки не унифицированы и любой шаблон ломается на соседней карточке.

**Коллизии словаря разрешаются явно.** Когда два ключа сайта легли бы в одно поле Приложения C
(класс точности по двум ГОСТам; постоянная счётчика по активной и реактивной энергии),
второй не затирает первый молча — он сохраняется в резервном поле под своим настоящим именем,
иначе значение поля зависело бы от порядка строк в таблице сайта.

В Приложение C добавлены два поля — «Срок службы» и «Средняя наработка на отказ»
(«Конструктивные характеристики»). Обе величины стоят во вкладке «Характеристики» каждой
карточки и регулярно фигурируют в требованиях закупок; положить их в «Примечание» значило бы
сделать их невидимыми для модуля сопоставления, который читает характеристики по имени поля.

### Идемпотентность и пропавшие модели

Ключ записи — **URL карточки** (`products.source_url`, уникальное ограничение в БД), а не
тройка «производитель + модель + артикул»: артикул на сайте может смениться, адрес карточки —
нет. Ограничение именно в БД, а не проверка в коде: два параллельных запуска синхронизации
иначе создали бы дубли.

Модель, пропавшая со страницы категории при повторном обходе, **не удаляется и не
архивируется** — помечается `needs_review` с объяснением (п.2.4 задания). Позиция могла
временно пропасть из-за правки сайта, а автоматическое снятие с производства развернулось бы
в «прибор нельзя предлагать» на следующем же тендере. Вернулась на сайт — пометка снимается.
Чтобы не пометить половину каталога из-за одной недоступной категории, помечаются только
записи из **успешно обойдённых** категорий; а живая страница без единой карточки трактуется
как смена вёрстки (ошибка в журнале), а не как «вся продукция исчезла».

### Привязка моделей к типам СИ — по артикулу, а не по названию

Каталог и реестр наполняются независимо, и без связи `products.si_type_id` модуль
сопоставления видит по производителю два несвязанных набора фактов: он не знает, какое
«Описание типа» относится к какой модели, и в карточку производителя попадают
метрологические данные всех типов сразу — включая теплосчётчики и счётчики воды.

**Связывать нужно по артикулу.** На сайте у таганрогского и владивостокского исполнений
**одно и то же название модели** — «МИРТЕК-12-РУ-D17», — но **разные типы СИ**: 61891-15
«МИРТЕК-12-РУ» и 67662-17 «МИРТЕК-212-РУ». Завод зашит только в артикул
(`mirtek-12-ru-d17` против `mirtek-212-ru-d17`). Связывание по названию модели молча
приписало бы обоим исполнениям таганрогский тип и подставило бы в тендер характеристики
не того прибора — ровно та же категория ошибки, что и коллизия «Пульсар», только внутри
собственной продукции. Название модели используется лишь там, где артикула нет вовсе
(записи из ручного ввода и CSV-импорта).

**Нужна транслитерация.** Артикул — латинский slug сайта, обозначение типа в реестре —
кириллица; прямое сравнение даёт ноль совпадений (проверено на живых данных). Нормализация
здесь своя, отдельная от `_skeleton` в `fgis_matching.py`: та приводит латиницу К кириллице
(сравнивает две «человеческие» строки с омоглифами), эта — наоборот, обозначение к виду
slug'а. Совмещать их нельзя: латинская `p` в омоглифах — это `р`, а в slug'е — `p`.

Совпадение префиксное (обозначение покрывает семейство исполнений), из нескольких берётся
самый длинный префикс. Осталось больше одного — привязки нет, запись помечается
«требует проверки». Отсутствие подходящего типа пометкой **не** сопровождается: у половины
каталога код СИ может быть ещё не найден, и пометка на каждой записи превратилась бы в фон.

**Подстановка автоматическая — во всех четырёх точках, где появляются модели или коды:**

| Событие | Что происходит |
|---|---|
| Автопоиск в ФГИС (`POST …/si-types/search`) | найденные коды сразу подставляются всем подходящим моделям производителя |
| Обход каталога МИРТЕК | привязка в конце обхода, после сохранения моделей |
| Создание модели в админке | код подставляется сразу, если подходящий уже найден |
| Поиск по событию из модуля сопоставления | новый тип получает всё семейство исполнений, а не только модель из очереди |

Отдельная кнопка «Привязать к моделям» (`POST /manufacturers/{id}/link-si-types`) остаётся
как ручной повтор — на случай, когда связи нужно пересчитать после правок в справочнике.
Автоподстановка именно автоматическая, потому что отдельный шаг здесь был бы полумерой:
автопоиск ради того и запускают, чтобы у моделей появился код СИ, а не чтобы получить второй
несвязанный список — и о необходимости нажать вторую кнопку человек попросту не догадается.

Уже привязанные модели не трогаются ни в одной из точек: код СИ мог выставить человек
(раздел 5.3 ТЗ), и явно переданный `si_type_id` при создании модели тоже в приоритете.
`relink=true` пересчитывает и их — это осознанный ручной запуск.

**Типы СИ вне области справочника.** Автопоиск по производителю возвращает всё, что тот
когда-либо утверждал: у МИРТЕК из 28 типов электросчётчиков ровно половина, остальное —
теплосчётчики, счётчики воды и газа, УСПД, поверочные установки, трансформаторы тока.
Записи законные и не удаляются, но помечаются `needs_review` с объяснением и **исключаются
из привязки** — иначе «МИРТЕК-42-РУ» (теплосчётчик) стал бы кандидатом на префиксное
совпадение наравне со счётчиками. Подтверждённые человеком и введённые вручную записи
пометка не трогает.

На живых данных: 27 из 27 моделей каталога привязываются автоматически после автопоиска
(проверено сбросом всех связей и повторным прогоном), 0 неоднозначных;
14 из 28 типов СИ помечены как вне области справочника. Привязка сверена с независимым
источником — названиями документов на самих карточках сайта («Сертификат об утверждении и
описание типа средств измерений **МИРТЕК-12-РУ**» у таганрогской, «Руководство по
эксплуатации **МИРТЕК-212-РУ**» у владивостокской).

### Проверено живым прогоном

Обход `mirtekgroup.com` целиком: **26 записей** (17 однофазных исполнений, 9 трёхфазных),
**708 характеристик**, 8 позиций со статусом «снят с производства», 0 ошибок, ни одного
казахстанского или белорусского исполнения. Повторный запуск: 0 создано, 26 обновлено —

## 29. Каталоги конкурентов: Энергомера, КПЗ, Промэнерго (05.09.2026, разделы 4.3, 5.3, 5.9 ТЗ)

Сайт МИРТЕК (раздел 28) наполнял справочник только собственной продукцией, а процент
соответствия считается по всем производителям сразу — по неполному каталогу конкурентов он
занижался бы не из-за свойств приборов, а из-за пустых строк. Теперь тем же способом
собираются три сайта конкурентов, и **логика сохранения у них общая с МИРТЕК**: один сервис
`app/services/catalog_site_sync.py` (бывший `mirtek_catalog_sync`), одни правила маппинга,
идемпотентности, статусов и привязки к типам СИ. Держать для конкурентов отдельный путь
означало бы наполнять их каталог по другим правилам, чем собственный.

### Движок плюс профили, а не адаптер на каждый сайт

`app/adapters/manufacturer_catalog.py` — один обход и декларативные `SiteProfile`: всё
различающееся (селекторы, шаблон ссылки на карточку, где искать характеристики и особенности)
вынесено в профиль, всё общее написано один раз. Селекторы **проверены на живой разметке**, а
не угаданы: `ManufacturerSiteAdapter` (поиск руководства вслепую) уже показал цену эвристик —
он допустим там, где ищется один документ, а здесь ошибка означает неверную характеристику
в каталоге, по которой считается процент в тендере.

МИРТЕК остался на собственном адаптере: только у него есть заводские исполнения
(Таганрог/Владивосток) со своими характеристиками и своими типами СИ (раздел 28) — под общий
профиль это не ложится, а ломать работающее ради единообразия незачем.

### Что показала разведка (04–05.09.2026)

**Энергомера** — самый структурированный: четыре категории электросчётчиков плюс отдельный
раздел `archive` «снятые с серийного производства» (71 карточка, с активными не
пересекается) — прямой источник статуса, аналог пометки `<i>` у МИРТЕК. В листинге название
и артикул лежат в самой карточке (`h2` и `p.content__item__article`), на карточке товара H1
длиннее («Счетчик электроэнергии однофазный CE101 R5 145 M6»). Две ловушки: заголовочная
строка таблицы («Показатели :: Величины») размечена как обычная строка данных, а список
документов свёрстан **такой же таблицей пар** («Руководство по эксплуатации :: PDF 2 Mb») —
без явных проверок и то и другое попадало в справочник характеристиками. `robots.txt`
закрывает `/documentations/`: ссылки на документы сохраняем, файлы не качаем (они и не нужны —
характеристики берутся со страницы).

**КПЗ** — вся продукция на одной странице. Две особенности, каждая способна создать
впечатление пустого сайта или мусора в каталоге: `www.kpsz.ru` **редиректит** на `kpsz.ru`,
и без перехода по редиректу страница приходит вообще без каталога; категорий как отдельных
страниц нет — тип прибора определяется заголовком секции (`h1`), а модели размечены `h2`.
Секция «Дисплей потребителя» отсеивается тем же правилом, что и любая не-счётчиковая
продукция. У каждой позиции две ссылки на один URL (картинка без подписи и название) —
запись создаётся одна.

**Промэнерго** — ближе всего к МИРТЕК: одна категория, `h3` «Ключевые особенности» и `h3`
«Технические характеристики». Позиция называется длинно («Однофазный прибор учета
электроэнергии i-PROM.1»), поэтому в справочник идёт **код модели** (`i-PROM.1`) — по нему
прибор ищется в Госреестре и сопоставляется с требованием тендера, — а полное название
сохраняется как «Наименование полное». Категория одна на все приборы, так что фазность
выводится из названия позиции: в закупках она стоит требованием почти всегда.

### Словарь синонимов и нормализация ключей

Одна и та же величина записана у четырёх производителей по-разному: «Базовый ток»,
«Базовый ток, А», «Базовый (номинальный) ток», «Базовый / максимальный ток, А»,
«Базовый (максимальный) ток». Вести словарь по каждому написанию — значит ловить каждый
новый вариант по факту потери данных, поэтому ключ сначала нормализуется: снимаются единицы
измерения («, В», «, Гц», «, лет», «, часов»), оговорки «не более»/«не менее» и пометки
вида «(ВхШхГ)». Через ту же нормализацию прогоняется и сам словарь — так он остаётся
похожим на то, что видно на странице, и следующий вариант формулировки добавят туда, куда
нужно.

Когда два ключа сайта претендуют на одно поле Приложения C, второй не затирает первый молча,
а уходит в резервное JSON-поле под своим настоящим именем (раздел 28). Так разошлись
«Тарифность» («Однотарифный») и «Число тарифов» («1») у Энергомеры, «Исполнение»
(«Модульное») и «Установка» («DIN-рейка») у Промэнерго.

### Расписание и запуск

Плановый обход — раз в неделю, **все сайты подряд** (`CATALOG_SITES_SYNC_*`), последовательно
и независимо: недоступность одного не отменяет остальные, собственный каталог идёт первым.
Ручной запуск — кнопка «Обойти сайт производителя» в каталоге (показывается у тех
производителей, для чьего сайта есть профиль) и `POST /catalog/sites/{adapter_key}/sync`
(в очередь) / `/sync-now` (синхронно, с полным отчётом); `GET /catalog/sites` перечисляет
источники вместе с признаком «производитель заведён в справочнике».

Три сайта заведены источниками в `sources` миграцией 0032 — видны и управляются в общем
разделе «Источники», как и остальные.

надо сверять с одним значением. Поле приводится к числу независимо от того, откуда пришло.

### Почему модели конкурентов сперва не связались с кодами СИ (05.09.2026)

Первый живой прогон по Энергомере: 200 моделей, 154 типа СИ, **связана одна**. Три причины,
и ни одна не видна без реальных данных:

1. **Алфавит.** На сайте модель называется «CE101 R5 145 M6» **латиницей**, а в Госреестре
   тот же прибор записан «СЕ 101» **кириллицей** — визуально неотличимо, символы разные.
   Действовавшая нормализация переводила кириллицу транслитерацией, и «СЕ» превращалось в
   `se`, а не в `ce`. Ноль совпадений на всём каталоге.
2. **Артикул.** У МИРТЕК артикул — slug с обозначением внутри, и только он различает
   заводские исполнения, поэтому он и был единственным ключом. У Энергомеры артикул —
   складской номер `101001003007791` (146 моделей из 200), к обозначению отношения не
   имеющий; до названия модели алгоритм просто не доходил.
3. **Несколько обозначений в одном поле.** У КПЗ тип 79474-20 записан как
   «М2М-1 и М2М-1S» — без разбиения не совпадает ни один из двух.

Что изменилось: строка нормализуется **в двух схемах сразу** — транслитерация (нужна МИРТЕК:
кириллическая «Р» → `r`) и омоглифы (нужны Энергомере: «С» → `c`), совпадением считается
совпадение хотя бы по одной. Схемы прямо противоречат друг другу на букве «Р», поэтому и
держатся отдельно, а не сводятся в одну таблицу. Ключей у модели тоже два — артикул и
название: артикул **раньше**, а не «вместо».

Добавились два правила, которые данные потребовали явно:

* **Минимальная длина обозначения (3 символа).** В реестре Энергомеры есть тип с
  обозначением «СЕ» — это название всей серии, и как префикс он подошёл бы разом ко всем
  «CE1xx», «CE2xx», «CE3xx».
* **При равной длине префикса берётся свежая редакция по номеру ГРСИ.** Одно обозначение
  под несколькими номерами — обычное дело (у Энергомеры так живут 85594-22 и 85594-26 с
  «CE318BY»): тип переутверждают, старая запись остаётся в реестре. Отправлять это человеку
  было бы фальшивой неоднозначностью. «Требует проверки» остаётся для случаев, где номера
  нечем упорядочить — ручной ввод, импорт, записи вида «65515-16-ebab».

Результат на живых данных: **205 из 221** модели Энергомеры, 27 из 27 у МИРТЕК, ноль
отправленных на ручную проверку. Оставшиеся 16 — честное «типа нет в реестре»: серии CE210,
CE310, ЦН6802А, СЕ901, обозначений которых среди загруженных 154 типов нет.

Заодно выяснилось, что в раздел счётчиков Энергомеры затесалась позиция «Трансформатор
тока»: теперь позиции, чьё название прямо называет не-счётчик, в каталог не сохраняются —
раньше такой фильтр применялся только к секциям КПЗ.

## 30. Наименования как у производителя и профили ещё трёх сайтов (05.09.2026, разделы 4.3, 5.3 ТЗ)

### Наименование — то, что написано у производителя

Адаптер вычленял из названия позиции код модели и сохранял в справочник именно его: в
каталоге стояло «M2M-1C», тогда как на сайте КПЗ прибор называется «Однофазный счетчик
электрической энергии М2М-1». Для закупки это существенно: в документации пишут полное
наименование, и человек, сверяющий справочник с требованием тендера, должен видеть ту же
строку, что и на сайте.

Но код всё равно нужен, и для другого — по нему модель сопоставляется с обозначением типа
в Госреестре. Внутри полного наименования обозначение префиксным сравнением не находится:
`счетчикэлектроэнергииоднофазныйce101` не начинается с `ce101`.

Поэтому два поля вместо одного (миграция 0033): `products.model_name` — наименование как у
производителя, `products.model_code` — обозначение для сопоставления. В привязке к типам СИ
ключи пробуются по очереди: `model_code` → `article` → `model_name`.

**Откуда брать наименование — из листинга или с карточки — сайты решают по-разному**, и
правило поэтому не «всегда одно»: берётся более полное из двух. У КПЗ в листинге короткое
«М2М-1С», а на карточке «Счетчик электроэнергии однофазный компактный M2M-1С»; у Нартиса
ровно наоборот — в листинге «Счётчик однофазный интеллектуальный НАРТИС-И100», а H1 карточки
просто «НАРТИС-И100».

## 31. Инкрементальный обход и объяснение пустой матрицы (05.09.2026, разделы 5.3, 5.5, 5.6 ТЗ)

### Повторный обход не перезагружает то, что не менялось

Сайты производителей отвечают по 2-6 секунд на страницу (замерено: `kpsz.ru` — 5,8 с,
`nartis.ru` — 5,4 с, `energomera.ru` — 3,2 с), и каталог в две сотни позиций обходится
минутами. При этом между еженедельными прогонами он почти не меняется.

Теперь карточка не перезагружается, если запись обновлялась не позже `FRESH_CARD_MAX_AGE`
(три дня) **и** у неё уже есть характеристики. Второе условие не формальность: позиция, у
которой прошлый обход сорвался на загрузке карточки, тоже «свежая» по времени, но пустая, —
пропустить её значило бы законсервировать пустую строку в справочнике.

Пропуск касается только карточки товара. Всё, что видно на странице категории, обновляется
всё равно и стоит ноль запросов: статус «снят с производства» и снятие пометки «модель
пропала со страницы категории». Иначе запись, вернувшаяся на сайт, оставалась бы помеченной
до первого полного обхода — этот дефект поймал регрессионный тест на возврат модели.

`full_refresh=True` перечитывает всё: нужно после правки профиля сайта или словаря
синонимов, когда старые записи надо собрать заново.

Замер на Тайпите (70 карточек): первый обход **583 секунды**, повторный — **15 секунд**.

### Соединение переиспользуется

Клиент создавался заново на каждую карточку, то есть TLS-хендшейк повторялся столько раз,
сколько позиций в каталоге. Теперь одно соединение на весь обход. Честный замер с прогревом
и обменом порядка дал **+12%** — меньше, чем можно было ждать по времени хендшейка (0,5-2,9 с):
разброс самих сайтов перекрывает эффект. Оставлено прежде всего ради снижения нагрузки на
чужой сервер.

### Пустая матрица соответствия объясняет причину

Вкладка «Конкуренция» в любом случае предлагала «запустить Расчёт соответствия». Когда
требования из документации не извлечены, это отправляло человека нажимать кнопку, которая
только что честно отработала вхолостую: сравнивать каталог не с чем, пока нет требований, и
расчёт завершался успехом с сообщением «У тендера нет извлечённых требований» — но сообщение
жило только до перезагрузки карточки.

Теперь вкладка получает число извлечённых требований и называет причину прямо: «Матрицу
соответствия не с чем сопоставлять» с подсказкой, что делать дальше, — включая случай, когда
анализ уже отработал, а требований всё равно нет (так бывает у закупок на работы, где ТЗ
лежит отдельным приложением).

Кнопка обхода каталога в интерфейсе переведена с синхронного эндпоинта на постановку в
очередь: она вызывала `/sync-now` и держала вкладку открытой все минуты обхода.

## 32. Вложенное ТЗ, шесть новых каталогов и данные приборов в анализе (05.09.2026, разделы 5.2, 5.3, 5.4, 5.5 ТЗ)

### Почему анализ возвращал ноль требований

Закупка «Россети Центр» (32616337073) на расширение системы учёта: 330 тыс. знаков
извлечённого текста, ноль извлечённых требований, ОКПД2 определился как «45.3» —
строительные работы вместо счётчиков.

Причина оказалась не в модели и не в промпте. Комплект документации опубликован одним RAR,
а внутри него отдельным архивом лежало «Приложение №1 — Техническое задание.rar». Вложенные
архивы разбор не разворачивал (осознанное решение против zip-бомбы), и до анализа доходили
извещение, проект договора и требования к гарантам — всё, кроме единственного документа,
в котором эти требования и записаны.

Исправлено тремя шагами:

1. **Вложенные архивы разворачиваются** — на `MAX_ARCHIVE_DEPTH` уровня. Защита от
   zip-бомбы сохранена и усилена: лимиты на число файлов и суммарный объём считаются теперь
   на всё дерево архива сразу (`_ArchiveBudget`), а не на каждый уровень отдельно — иначе
   вложенность их обходила бы.
2. **Один документ в двух форматах читается один раз.** «ТЗ.docx» и «ТЗ.pdf» рядом в архиве
   — обычное дело; разбирать оба значит платить дважды и получить требования дублями.
3. **Документы упорядочиваются перед разбором** (`_prioritised_text`). Модель читает
   ограниченное число кусков с начала, поэтому первым идёт техническое задание, последними —
   смета и проект договора. Повторы выбрасываются по имени файла: заказчик, меняя условия,
   публикует не изменённый файл, а весь комплект заново, и «Уведомление об изменении №1»
   содержало те же семь документов, что и основной архив.

Текст для анализа этой закупки: было 902 тыс. знаков (из них ТЗ — ноль), стало 453 тыс.,
техническое задание первым и целиком в пределах читаемого. Результат: **0 требований → 57**,
ОКПД2 «45.3» → «26.51.63.130».

Отдельная забота — уже скачанные документы. Правила разбора поменялись, а текст у них лежит
в базе, разобранный по старым. Поэтому у документа появилась версия правил
(`EXTRACTION_VERSION`, миграция 0035), и анализ переразбирает устаревшие документы из
хранилища — не скачивая заново, файл-то тот же.

### Шесть каталогов третьей волны

Профили Waviot, РиМ, Милур, Инкотекс, МИР и Пульсар — там же, где остальные
(`app/adapters/manufacturer_catalog.py`), миграция источников 0036. Что потребовало
изменений в самом движке:

* **Разбивка на страницы** (`page_param`, `max_pages`): у Милура и Пульсара каталог не
  помещается на одну страницу. Признак конца разный — Битрикс отдаёт копию последней
  страницы, а Милур отвечает 404; учтены оба.
* **Характеристики парами блоков** (`spec_pair_selector`): у Waviot таблицы на карточке нет
  вовсе. Раньше такая разметка была зашита под МИРТЕК (`.productPropsWrap`), теперь это
  свойство профиля.
* **Обозначения с джокером**: каталог РиМ называет семейство «РиМ 189.4X», а Госреестр
  перечисляет конкретные «РиМ 189.40». Ни одно не является префиксом другого, поэтому для
  таких обозначений сравнение идёт в обратную сторону — подходит тип, обозначение которого
  начинается с части до джокера. Заодно снимается служебное «серии» в записи реестра
  («серии РиМ 189»). Было привязано 1 из 7 моделей, стало 7 из 7.
* **Пауза под сайт**: Waviot отдаёт HTTP 429 при паузе по умолчанию, robots.txt Инкотекса
  требует Crawl-delay: 10.

Справочник закрыт на **13 производителей из 13**: 548 моделей, 527 из них привязаны к
утверждённым типам СИ.

### Данные приборов в анализе

Требование заказчика — характеристики и документация приборов должны работать в оценке
тендера. Три места, где они в неё входят, и что мешало каждому:

**Отбор моделей в карточку производителя.** В запрос к модели помещается
`MAX_PRODUCTS_IN_CONTEXT` моделей; у Энергомеры их 221, и брались первые шесть по алфавиту.
На закупке трёхфазных счётчиков в сравнение уходили CE102M — однофазные, просто стоящие
первыми в списке. Теперь модели отбираются по требованиям закупки
(`app/services/product_relevance.py`): прямое упоминание прибора в требованиях, совпадение
по числу фаз, пересечение числовых значений, действующие впереди снятых с производства.
Отбор детерминированный, кодом: какие модели показать — решение, которое должно быть
воспроизводимым, иначе разбирать расхождения в матрице невозможно.

**Руководства по эксплуатации** (`app/services/product_manual_ingest.py`). Обход сайта
сохранял только ссылку на документ, поэтому третий источник сопоставления (раздел 5.5 ТЗ,
п.3) опирался на пустоту: характеристик из руководств в справочнике было шесть на четыреста
моделей. Теперь руководство скачивается и разбирается — отдельным действием, а не частью
еженедельного обхода: PDF весит мегабайты, а разбор стоит нескольких обращений к модели,
тогда как сам документ меняется куда реже карточки. `robots.txt` сайта соблюдается: у
Энергомеры раздел с документацией закрыт к обходу, ссылки на него мы храним, а файлы не
берём. Одно руководство МИР дало 38 характеристик — интерфейсы, протоколы и функции,
которых в таблице карточки не было вовсе.

Три уточнения, без которых массовый разбор был бы втрое дороже и наполовину пуст:

* **Документ разбирается один раз на семейство.** У 478 моделей справочника всего 134 разных
  руководства: «Меркурий 200/201» описывает десяток исполнений, «НЕВА МТ 113» — сорок пять.
  Разобранное кешируется по адресу документа внутри прогона и раздаётся остальным моделям
  семейства без повторного скачивания и без повторного обращения к модели. Предел прогона
  считается по документам, а не по позициям, — раздача уже разобранного ничего не стоит.
  Ради этого `characteristic_extraction` разделён надвое: `read_characteristics` вычитывает
  документ, `apply_characteristics` записывает вычитанное конкретной модели.
* **Паспорт прибора — тот же материал, что руководство.** У Инкотекса руководства на карточке
  нет вовсе, а паспорт есть; без него всё семейство «Меркурий» осталось бы без разобранной
  документации.
* **Название документа против размера файла.** У Инкотекса подпись ссылки — «642.6 КБ», а
  название стоит перед ней отдельным текстом. В справочник попадали документы с названием
  «452.7 КБ», и отличить среди них паспорт от сертификата было нечем.

**Описания типа из Госреестра.** У четырёх новых производителей типов СИ в справочнике не
было ни одного — автопоиск в ФГИС нашёл 301.

### Справочник характеристик расширен, а имена полей приводятся к нему (06.09.2026)

Разбор руководств показал, что модель раз за разом возвращает поля, которых справочник не
знает, и они молча отбрасывались. Разбор ста отброшенных ответов дал три разных причины —
и лечатся они по-разному:

**1. Поле известно, названо иначе.** Больше половины случаев. Модель приписывает к полю
название его группы («Протокол DLMS/COSEM» вместо «DLMS/COSEM», «Интерфейс ZigBee» вместо
«ZigBee»), называет то же самое другими словами («Вид монтажа» вместо «Тип монтажа», «Класс
защиты от пыли и воды» вместо «Степень защиты») или даёт частное вместо общего («GSM» вместо
«GSM/GPRS/3G/4G»). Расширять справочник тут нечем — надо приводить ответ к нему. Это делает
`resolve_field` в `app/seed/characteristics_data.py`: снимает приставку-название группы,
сверяется с таблицей `FIELD_SYNONYMS`, собранной из живого разбора.

**2. Поле известно, лежит не в той группе.** «Максимальный ток» приходил в «Интерфейсы и
связь», «Номинальное напряжение» — в «Конструктивные характеристики». Значение верное, и
терять его незачем: группа однозначно определяется полем, поэтому берётся из справочника, а
не из ответа модели.

**3. Поля действительно нет.** Здесь справочник и расширен — по согласованию с заказчиком,
восемью полями сверх Приложения C: **СПОДЭС** (обязательный протокол интеллектуальных приборов
учёта по ПП РФ №890 — в Приложении C его нет вовсе, хотя в закупках он стоит требованием чаще
прочих протоколов вместе взятых), **Тип включения цепей** (прямое или трансформаторное —
требование наравне с классом точности), Bluetooth, Контроль тока в нейтрали, Тип корпуса,
Комплект поставки.

Два правила добирают остаток. Уточнённая формулировка известного поля («Класс точности при
измерении активной энергии в двух направлениях») сводится к базовому полю. Название
конкретного протокола в группе протоколов («Протокол обмена Пульсар») попадает в «Прочие
протоколы» — справочник перечисляет распространённые поимённо и держит это поле как раз для
остальных.

**Результат.** Повторный разбор с расширенным справочником (41 минута): 11 088 характеристик
из документации против 9 120, 277 моделей против 253. Появились поля, которых в справочнике
не было ни у одной модели: СПОДЭС — у 113, DLMS/COSEM — у 80, IEC 61107 — у 76, Bluetooth —
у 46. Отбраковок в логе прогона осталось девять на весь справочник против сотни.

Название группы, попавшее в имя поля («Протоколы обмена» → «Протоколы обмена»), по-прежнему
отбрасывается: это заголовок раздела документа, а не характеристика.

Разбор руководств получил флаг `refresh` (`POST /manufacturers/{id}/ingest-manuals?refresh=true`):
без него повторный прогон пропускает уже разобранные документы, а после расширения справочника
их нужно перечитать — поля, которых в нём не было, в прошлый раз отброшены.


### Пустая вкладка «Требования» и ложные коды ОКПД2

Та же болезнь, что была у матрицы соответствия: анализ отрабатывал, требований выходило ноль,
и вкладка советовала запустить «Анализ документов» — кнопку, которая только что отработала
вхолостую. Теперь вкладка знает последнюю задачу анализа (`GET /jobs` получил фильтр `kind`)
и число документов с извлечённым текстом, и различает три причины: анализ не запускали;
текста нет ни из одного документа (дело в них, а не в анализе); анализ отработал и требований
к товару не нашёл.

Разбор той же закупки вскрыл два дефекта по существу:

* **Строка спецификации не считалась требованием.** У закупки у единственного поставщика
  («Приобретение счетчиков для нужд АО «Облкоммунэнерго»») вся содержательная часть — это
  «Счетчик СЕ208, 30 шт.» в спецификации договора, а промпт требовал «проверяемое условие», и
  модель такие строки отбрасывала. Ноль требований на закупке счётчиков. После явного указания
  в промпте извлекаются и модели, и количества — а `product_relevance` находит по ним нужные
  позиции каталога прямым упоминанием.
* **Ложные ОКПД2.** Код — основной фильтр релевантности (раздел 5.4 ТЗ, п.5), и на живых
  закупках в него попадали «16.08» (дата «от 16.08.2024г.»: между цифрой и кириллической
  буквой нет границы слова, и маскировка дат такую дату не видела), «16.00» (время работы
  заказчика), «12.7» (номер пункта договора), «19.28» (номер приложения), «91.05.01» (шифр
  машин и механизмов в смете).

Последний случай оказался решающим: **по форме код ОКПД2 неотличим от сметной расценки и
номера пункта**, и никакое уточнение регулярного выражения этого не меняет. Прогон по всем
тридцати закупкам с распознанными документами разделил их начисто: все настоящие коды пришли
полными и из нашей ниши (26.51.63.130, 26.51.45.190, 43.21.10.220), все ложные — из чужих
разделов, а формой от настоящих не отличались.

Поэтому правило стало таким: код из текста принимается либо **с явной меткой** («ОКПД2
26.51.63.130» — прямое указание заказчика), либо **если он попадает в нашу нишу** (Приложение
F: приборы учёта — диапазон узкий, случайный сметный шифр в него не попадает). Всё остальное
отдаётся модели, которая видит содержание закупки, а не одну лишь форму числа. Ложный код
тише отсутствующего: он молча искажает основной фильтр релевантности.

### Что дал прогон по всем закупкам с документами (05.09.2026)

Тридцать закупок, у которых документы скачаны и текст распознан, переанализированы целиком.

| | было | стало |
|---|---|---|
| закупок с извлечёнными требованиями | 5 | 23 |

| закупок с кодом ОКПД2 | 7 | 9 |

### Справочник актуальности документов (правка по итогам показа 15.09.2026)

Обход сайта и ревалидация ФГИС оставляют в справочнике ссылки на документы, но не
отвечают на вопрос, которым задаётся человек перед подачей заявки: тот ли это документ, что
мы читали, или производитель его переиздал? Руководство переиздаётся вместе с прошивкой,
«Описание типа» — приказом Росстандарта, и характеристики, снятые со старой редакции, тихо
устаревают.

Теперь у каждого документа — руководства, паспорта, «Описания типа», сертификата,
декларации — есть строка в `catalog_documents` (`app/models/catalog_document.py`) с
**актуальной датой** и её происхождением: `Last-Modified` файла на сайте, номер редакции в
ФГИС или, когда источник даты не сообщает, день, в который система зафиксировала документ
либо изменение его содержимого. Разница важна: этим датам человек доверяет по-разному, и в
интерфейсе она подписана.

**Еженедельная сверка** (`app/services/document_registry_service.py`, планировщик —
вторник 06:00, после понедельничного обхода каталогов; `DOCUMENT_REGISTRY_CHECK_*` в
`.env`). Ссылки переносятся из справочника продукции и кодов СИ (пропавшая гасит строку, а
не удаляет), затем у файлов на сайтах запрашиваются только заголовки — ETag, Last-Modified,
размер; файл читается целиком лишь если сервер не отдаёт ни одного признака. Один адрес —
один запрос за прогон (сертификат МИРТЕК общий на семейство), между запросами к сайту
пауза, `Crawl-delay` из `robots.txt` соблюдается. «Описание типа» сверяется без сети — по
редакции, которую уже обновляет ревалидация ФГИС. Первый прогон по МИРТЕК: 128 документов,
102 адреса, минута.

**Отчёт** уходит на почту тем же каналом, что и остальные уведомления, отдельным триггером
`documents_updated` (выключается в настройках), и остаётся в журнале отправок как отчёт
системы. Письмо рождается только когда есть что сказать: что переиздано (с прежней и новой
датой), что появилось, что пропало из справочника, что перестало открываться; тихая
неделя письма не рождает. Недоступность попадает в отчёт один раз — когда обнаружена.
Ручной запуск — кнопка «Проверить актуальность» в каталоге, через ту же очередь
справочника (`adapter_key=document_registry`).

## 33. Обучение по Аршину и поиск документации (15.09.2026, разделы 4.2, 4.3, 5.3 ТЗ)

Замечание заказчика: система должна учиться техническим характеристикам приборов всех
конкурентов и МИРТЕК по Аршину (ФГИС), учитывать изменения в «Описании типа» и справляться
с ситуацией, когда новый прибор уже описан в реестре, но на сайте производителя документов
о нём нет — а через поиск в Яндексе они на том же официальном сайте находятся.

### Живой пример, на котором всё проверено

НАРТИС-И100, тип 86199-22. В каталоге `nartis.ru` — исполнения W112 и W113. В карточке
Аршина 01.06.2026 приказом № 1037 вышла **редакция 2** «Описания типа», и в ней среди
«представленных на испытания» появилось исполнение
`НАРТИС-И100-W115-2-A1R1-230-5-80A-ST-RS485-P1-HKLMOQ1V3-D` — корпус W115, максимальный
ток 80 А. Ни одна страница каталога на него не ссылается, но руководство по эксплуатации
`nartis.ru/upload/iblock/5f6/nmge5xsoiskcr0avk6yrwilnnctko9rp.pdf` (121 страница, W115
описан) индексируется поисковиком и приходит первой строкой на запрос
`site:nartis.ru НАРТИС-И100 W115 руководство по эксплуатации`.

До правки система из Аршина не знала почти ничего: текст «Описания типа» был загружен у
четырёх типов из ~630, а характеристики из него извлекались по кнопке у одной модели.

### Что делает проход обучения (`app/services/catalog_learning.py`)

Пять шагов, каждый опирается на предыдущий:

1. **Карточки Аршина** (`refresh_cards`) — у типов, загруженных до правки, перечитывается
   карточка ради списка исполнений. Из `j_factorynums` и строк легенды после «На испытания
   представлены:» адаптер (`app/adapters/fgis.py`, `tested_modifications`) собирает полные
   условные обозначения; строка с несколькими исполнениями режется по началу типа с поправкой
   на омоглифы — реестр набирает «HAPTИC-P3-C-…» частично латиницей. Список хранится в
   `si_types.tested_modifications`.
2. **Исполнения → каталог** (`app/services/registry_modifications.py`). Из полного
   обозначения вычленяется короткое — тип плюс первый сегмент (`execution_designation`:
   «НАРТИС-И100-W115», «Милур 109.1», «МИРТЕК-12-РУ-D17»); дальше — набор опций, которые
   в каталоге живут характеристиками. Если модели с таким кодом нет, она заводится с
   `data_source=fgis`, полным обозначением в `products.registry_modification` и пометкой
   «требует проверки»: наименование составлено из названия типа, а не взято у производителя.
   Обозначение, не начинающееся с типа (опечатка реестра «Pl» вместо «Р1»), записи не
   порождает. Существующая модель без кода СИ привязывается к типу.
3. **«Описание типа»** (`app/services/fgis_description_ingest.py`). Документ скачивается
   (ФГИС, при отказе — зеркало), **один раз** вычитывается моделью по всем автозаполняемым
   группам полей (`fields_for_source("any")`: документ описывает не только метрологию, но и
   корпуса, интерфейсы, функции) и разносится по всем привязанным моделям. Для исполнений из
   реестра дополнительно расшифровывается **условное обозначение по легенде** из той же
   карточки — так W115 получает «Максимальный ток = 80 А», а W112 — «100 А», тогда как
   семейство — «60; 80; 100 А». Номер в Госреестре, МПИ, срок действия и ссылка на документ
   проставляются без модели. `si_types.description_type_extracted_version` помнит, из какой
   редакции характеристики разнесены.
4. **Поиск документации** (`app/adapters/yandex_search.py`,
   `app/services/document_discovery.py`). Yandex Search API живёт в том же облаке, что и
   YandexGPT, и принимает тот же API-ключ и Folder ID (проверено: ключ из «Интеграции →
   Искусственный интеллект» работает без дополнительной настройки; без роли `search-api.executor` сервис
   ответит 403, и это попадёт в журнал понятным текстом). Запрос — `site:<официальный
   домен> <код модели> руководство по эксплуатации`, при неудаче — по семейству. Принимаются
   **только документы с официального сайта** (домен из справочника производителя либо из
   профиля обхода — у Нартиса это `nartis-region.ru` и `nartis.ru`): агрегаторы документации
   хранят устаревшие редакции и чужие файлы. Балл — упоминание модели, семейства, PDF,
   слова «руководство»; ниже порога ничего не сохраняется. Найденная ссылка ложится в
   «Ссылка на руководство» с источником `web_search`.
5. **Руководства** — найденные документы разбирает тот же `product_manual_ingest`, что и
   ссылки с карточек сайта.

Проход по производителю идёт через общую очередь справочника (`adapter_key=
catalog_learning`): это минуты, и держать на нём HTTP-запрос нельзя. Планировщик ставит его
по всем производителям раз в неделю (`CATALOG_LEARNING_*`, понедельник 08:00 — через три
часа после обхода каталогов, чтобы исполнения, которых на сайте нет, заводились на фоне
свежего каталога). Кнопки в каталоге: «Обучить (в фоне)» — полный проход; «Исполнения из
реестра», «Разобрать „Описания типа“», «Найти документацию» — отдельные шаги синхронно;
у модели — «Найти документацию» (поиск + разбор одной модели). Кнопка «С сайта
производителя» теперь сначала спрашивает поисковик и только потом обходит сайт вслепую.

### Изменения в «Описании типа»

Ревалидация ФГИС (`fgis_catalog_sync._revalidate`) сравнивает не только редакцию документа,
но и список исполнений: новое исполнение попадает в отчёт задачи («новые исполнения в
реестре: …») и сразу заводится в каталог; новая редакция сбрасывает текст, ставит
`description_type_changed_at` (в интерфейсе — «описание типа изменилось <дата>», жёлтым,
пока характеристики не перечитаны) и заставляет ближайший проход обучения перечитать
документ — характеристики прежней редакции перезаписываются, кроме подтверждённых
человеком и введённых вручную.

### Новые характеристики приборов

Поле, которому не нашлось места в Приложении C, больше не выбрасывается при AI-извлечении:
значение откладывается в `products.extra_specifications` (как давно делает обход сайта) и
видно в карточке модели и в сводке «вне справочника» блока «Обучение по Аршину»
(`GET /manufacturers/{id}/unknown-fields`) — это список кандидатов на расширение
справочника, который раньше собирали руками из лога.

### Проверено живым прогоном (15.09.2026, Нартис)

Из четырёх карточек Аршина заведено пять исполнений, которых нет на сайте: НАРТИС-И100-W115
и НАРТИС-И300 в корпусах W113, SP31, W131, W135. «Описание типа» 86199-22 (редакция 2,
45 тыс. знаков) разнесено на четыре модели семейства — по 58–60 характеристик у каждой,
с верной расшифровкой тока по исполнениям. Поиском найден ровно тот PDF, что указал
заказчик; из него у W115 получено 39 характеристик руководства.

## 34. Ручные заявки: закупка, присланная заказчиком напрямую (15.09.2026, разделы 5.2, 5.4, 5.6 ТЗ)

Площадки покрывают не всё: часть заказчиков присылает проект договора или ТЗ с
характеристиками приборов письмом, минуя торги. Живой пример — проект договора АО
«Новосибирскэнергосбыт» на услугу ИСУ 2027-2036: сто страниц, техническое задание с
требованиями к приборам — приложением на 84-й. До этого такую закупку было некуда положить:
ни карточки, ни анализа требований, ни матрицы соответствия.

**Что сделано.**

- **Системный источник `manual` («Заявка»)** — новый `SourceType.MANUAL`, миграция 0041,
  запись в `app/seed/sources_data.MANUAL_SOURCE`. Одна строка на все заявки: `tenders.source_id`
  обязателен, а заводить источник на каждого заказчика значило бы плодить справочник из
  одноразовых записей. Опрос тендеров и проверка доступности его пропускают
  (`POLL_EXCLUDED_SOURCE_TYPES` в `app/models/source.py`); интерфейс не показывает его в
  «Ресурсах», настройках и счётчиках площадок, но оставляет в фильтре «Площадки» — так можно
  показать одни заявки.
- **`POST /tenders/manual`** (multipart) — `app/services/manual_request_service.py`. Поля:
  наименование (обязательно), заказчик, сумма, срок подачи, комментарий (уходит в историю
  карточки), файлы, флаг «запустить анализ». Номер заявки — `ЗАЯВКА-ГГГГММДД-XXXX`. Заявка
  сразу на этапе «на проверке» с `passed_relevance_filter=True`: её принёс человек, решение
  «эта закупка наша» уже принято; `ai_relevant` остаётся пустым — это решение модели, и
  подделывать его нельзя. Ответственный — автор заявки.
- **Загруженные файлы** — те же `tender_documents`, с `source_url` вида `upload://{id}/{имя}`
  (поле обязательное и уникальное в пределах тендера, а скачивать заново неоткуда). Текст
  извлекается сразу, в запросе: файл уже в памяти, а человек хочет видеть «текст распознан» до
  нажатия «Анализ». Дальше заявка идёт по общему конвейеру: та же фоновая задача
  `TENDER_ANALYSIS`, матрица соответствия, AI-оценка, история.
- **`POST /tenders/{id}/documents/upload`** — приложить файл к любой закупке, не только к
  заявке: уточнённое ТЗ по собранному тендеру тоже присылают письмом. Перед загрузкой
  синхронизируется комплект с площадки — иначе загруженный раньше времени файл навсегда отменил
  бы скачивание документации самой закупки (`sync_tender_documents` качает только при пустом
  списке).
- **Интерфейс**: кнопка «Новая заявка» на странице тендеров (`NewRequestModal.tsx`, поля +
  зона перетаскивания файлов); после создания карточка открывается сразу. Во вкладке
  «Документы» карточки — кнопка «Добавить файл».

**Что пришлось поправить в анализе, чтобы пример заказчика вообще разбирался.**

- **Порядок таблиц в docx** (`extract_docx_text`, `EXTRACTION_VERSION = 3`). Раньше все
  таблицы дописывались после всех абзацев: на договоре в сто страниц «Таблица 3» с количеством
  приборов уезжала на двести тысяч символов от своего заголовка, а пара «Класс точности» /
  «1,0» в столбик читалась моделью как два обрывка. Теперь тело документа обходится по
  порядку, строка таблицы — одна строка текста через « | », повторы объединённых ячеек
  схлопываются. Ранее разобранные документы переразбираются из хранилища перед следующим
  анализом (механизм `reextract_stale_documents`).
- **Отбор кусков для длинной документации** (`tender_analysis._select_chunks`). Текст договора
  — 238 тысяч символов, 18 кусков по 14 тысяч; анализ читает не больше `MAX_CHUNKS_PER_TENDER`.
  Раньше брались первые двенадцать, и ТЗ (куски 13-17) не читалось вовсе — анализ вернул бы
  требования к оплате и спорам вместо требований к счётчику. Теперь, когда кусков больше
  предела, они ранжируются по числу упоминаний прибора и его характеристик
  (`_DEVICE_TERMS_RE`), берутся самые насыщенные, первый кусок (наименование и начало
  документа) остаётся всегда, порядок среди отобранных — документный. Предел поднят с 12 до
  16: при двенадцати начало ТЗ с требованием поддержки СПОДЭС в отбор не проходило. Пока
  документация помещается в предел, ничего не меняется.

### Проверено живым прогоном (15.09.2026, договор ИСУ Новосибирскэнергосбыт)

Из docx на 6,9 МБ извлечено 40 требований: типы приборов (1-ф, 3-ф прямого и полукосвенного
включения), Госреестр СИ, ПП РФ № 890/719/878, протокол СПОДЭС, программирование на один
тариф, состав индикации дисплея и интервал смены экранов — всё это из ТЗ в конце
документа. Регион заказчика определён как Новосибирская область (СФО).

## 35. Интеграция в ПО верхнего уровня (16.09.2026, разделы 5.3, 5.5, 5.6 ТЗ)

Замечание тестировщика-специалиста по тендерам: одно из частых требований ТЗ — интеграция
прибора в ПО верхнего уровня, нередко с названием конкретного продукта («поддержка в ПК
„Энергосфера“», «внесены в перечень оборудования, поддерживаемого ПО „Пирамида-Сети“»).
Ответить на него по каталогу производителя нельзя в принципе: интегрирован прибор или нет,
знает не производитель, а разработчик ПО, и публикует это списком поддерживаемого
оборудования. Тестировщик назвал семь таких списков: Пирамида (sicon.ru), Энфорс
(nforceit.ru), ПК «Энергосфера» (prosoftsystems.ru), яЭнергетик, АльфаЦЕНТР, ПК «Некта»,
ЛЭРС УЧЁТ. До этого на такое требование матрица честно ставила `no_data` всем.

### Что показала разведка (16.09.2026) и что определило код

Единого шаблона нет — семь разметок, у каждой своя ловушка (`app/adapters/upper_software.py`):

* **Пирамида** — три таблицы `table.devlist-table`: ПО «Пирамида 2.0»/«Пирамида-Сети»,
  контроллер SM-160, СИКОН/ИВК. Производитель и тип оборудования объединены `rowspan` на
  десяток строк семейства: без раскрытия объединений (`expand_table`) производитель достался
  бы одной модели из двенадцати. Есть **номер в Госреестре** — лучший ключ сопоставления.
  Шапка свёрстана с переносами внутри слов («промежу<br>точное») — имена колонок приводятся
  по ключевому слову.
* **Энфорс** — абзацы «14. производства ООО "МИРТЕК":» и следом `ul>li`. Хвост описания
  («включая получение инициативных сообщений по каналам TCP/UDP, HDLC») снимается до
  разбиения перечисления — иначе «HDLC» становился моделью.
* **Энергосфера** — таблица `table.data-thin` **без колонки производителя**: устройства
  через запятую, номера ГРСИ (объединённые `rowspan` на группу исполнений), флаги функций
  («+ Т П У К»). Сокращённая запись «МИЛУР-104, -105, -107S» раскрывается по предыдущему
  обозначению. Секции («УСПД», «Счётчики электроэнергии СПОДЭС», «Расходомеры, тепло- и
  газосчетчики») — строки с одной ячейкой. Строка «СПОДЭС-A…D» — поддержка по протоколу.
* **яЭнергетик** — `section#tab-meters`, в строке ссылка с названием и
  `span.device-factory-title`; функции и каналы — в `data-filter` (`f:power_profile n:rs485`).
* **АльфаЦЕНТР** — новость ASP.NET с **незакрытыми `<li>`**: html.parser вкладывает каждый
  следующий пункт в предыдущий, поэтому текст пункта берётся «до первого вложенного li».
  Раздел «Все счетчики, поддерживающие протокол СПОДЭС … В том числе:» — поддержка по
  протоколу; сам пункт хранится как `is_generic`, вложенный перечень — с пометкой
  `via_protocol`.
* **Некта** — список отдаётся только AJAX-запросом `admin-ajax.php?action=filter_prod`
  порциями по 24, а без cookie `beget=begetok` сайт возвращает заглушку с перезагрузкой.
  Фильтр по типу «Счётчик электричества» (`type[]=86`): остальные четыреста устройств —
  датчики и модемы. МИРТЕК там есть (11 моделей).
* **ЛЭРС** — `h2#электросчетчики` и следом `ul.wp-block-list`, в пункте модели одного
  производителя через запятую, производитель не назван. «HEBA CT413» латиницей — ловится
  омоглифной нормализацией из `si_type_linking`.

### Хранение и связь со справочником

Семь площадок — источники типа `upper_software` (миграция 0042, `UPPER_SOFTWARE_SOURCES` в
сиде): видны и управляются в «Источниках», пингуются, опросом тендеров пропускаются
(`CATALOG_SOURCE_TYPES`). Записи — `upper_software_devices`: строка как на сайте
(`device_raw`, `manufacturer_raw`) плюс разбор (`device_names`, `si_codes`, флаги в
`details`), отпечаток строки для идемпотентности, `last_seen_at` вместо удаления пропавших
(как у моделей каталога). Связь с моделями — `upper_software_product_links`.

Производитель записи определяется тремя признаками по убыванию надёжности
(`app/services/upper_software_service.py`): **номер ГРСИ** совпал с типом СИ справочника;
**название производителя** на сайте по словарю шаблонов бренда (`_MANUFACTURER_PATTERNS`;
«Фанипольский завод … Энергомера» исключён — белорусские модели CE208BY в каталоге
energomera.ru отсутствуют); **бренд в обозначении прибора** — для Энергосферы и ЛЭРС, где
производителя нет вовсе. Модели — префиксным сравнением в двух нормализациях
`designation_keys` **с границей**: «МИРТЕК-12-РУ» покрывает «МИРТЕК-12-РУ-D1»/«-W3»/«-SP3»,

перед обозначением («Энергомера CE301-R33», «РОТЕК РТМ-03») даёт второй ключ без него.
Записи из разделов тепло-, водо- и газоучёта в сводку не идут: «Пульсар-2М» из раздела
расходомеров не подтверждает интеграцию электросчётчика.

Связь пересчитывается после каждого чтения списка и после обхода каталога сайта
(`catalog_site_sync.sync_catalog`): новая модель должна увидеть списки сразу.

### Как это попадает в матрицу соответствия

Четвёртый источник фактов `[software]` (`ComplianceSource.UPPER_SOFTWARE`) — вне трёх шагов
ТЗ и только когда в требованиях есть интеграция. Названо конкретное ПО (`detect_platforms`
по алиасам профилей: «Пирамида», «Энергосфера», «Альфа центр», …) — факты по нему; общее
требование («интегрированы в АСКУЭ», «ПО верхнего уровня»; аббревиатуры АСКУЭ/ИСУЭ/ИВК —
только рядом со словом о совместимости, «шкаф УСПД АИИС КУЭ» не в счёт) — по всем семи.

Три вида факта, и второй — главный: «в списке есть приборы производителя — МИРТЕК-12-РУ
(ГРСИ 61891-15; Пирамида 2.0; Пирамида-Сети)…», «приборов производителя «КПЗ» в списке
поддерживаемого оборудования **НЕТ**», «моделей нет, но заявлена поддержка любых счётчиков
по протоколу СПОДЭС». Промпт (правило 7) велит считать отсутствие в проверенном списке
`not_meets`, а не `no_data` — список официальный, и это ответ, а не пробел; поддержка только
по протоколу — `partial`. Проверено живым вызовом YandexGPT: КПЗ по «Некте» и «АльфаЦЕНТР»
— `not_meets, source=software, 0.7-0.8`, Нартис по тем же — `meets`, МИРТЕК по «Пирамида
2.0» — `meets`.

### «Не работает фильтр по коду ОКПД, регионы и т.д.»

Фильтры работали — фильтровать было не по чему. ОКПД2 был заполнен у 13 закупок из
17 560, регион у 1 523, тип конкурса у 38: все три поля ставил либо ИИ-анализ документации
(его запускают по единицам закупок), либо карточка с сайта ЕИС при первом открытии тендера
человеком. К списку, который никто не открывал, это не применимо.

Новый сервис `app/services/tender_gaps_service.py` заполняет эти поля без модели:

* **из уже сохранённых карточек** (`backfill_from_stored_cards`, без сети) — в базе лежало
  1 656 карточек, и у трети из них в таблице лотов стоит «Классификация по ОКПД2»; дозаполнение

  дал ОКПД2 964 закупкам;
* **из карточек с сайта** (`fetch_missing_cards`) — для открытых закупок, прошедших профиль,
  без карточки: именно они в списке по умолчанию. Порцией (`TENDER_GAPS_FETCH_LIMIT`, 100)
  с паузой 1,5 с; идёт сразу после каждого планового опроса (`_run_gaps_job`), чтобы новая
  закупка попадала под фильтры в тот же день. Руками — `oracle-t-cli fill-gaps`;
* **тип конкурса по наименованию** (`tender_type_from_title`, Приложение E): «поверка» →
  поверка, «поставка» + «монтаж/установка/работы» → комплекс, «поставка» → поставка,
  «работы/замена/монтаж» → работы; без ключевых слов — пусто, а не «прочее» («прочее» — тоже
  вердикт). Ставится при сборе новой закупки и в проходе дозаполнения (14 578 закупок разом);
  ИИ-анализ, когда его запустят, перезаписывает поле своим вердиктом по ТЗ.

После прохода: ОКПД2 у 977, регион у 1 523, тип у 14 616 закупок. Сеть на машине
разработки в момент прогона отдавала `Connection reset` от zakupki.gov.ru, так что
карточки для 49 открытых закупок без карточки дочитает первый плановый запуск на сервере.

### «Сохранять интересующие тендеры, чтобы позже вернуться»

### «Проверка реестровой записи в реестре промпродукции и действующего ЗАК Россетей»

Реальные формулировки из базы: «оборудование, включённое в Перечень оборудования,
материалов и систем, допущенных ПАО „Россети“», «в заключении аттестационной комиссии», «ПО
внесено в Единый реестр российских программ». Это **допуск**, а не характеристика: у записи
есть номер, дата и срок, после которого прибор формально перестаёт подходить. Поэтому —
отдельная таблица `product_registry_records` (миграция 0044, `app/models/registry_record.py`),
одна запись на пару «модель × реестр», три реестра (`AdmissionRegistry`): реестр промышленной
продукции ПП 719 (ГИСП), ЗАК ПАО «Россети», реестр российского ПО.

Автоматической сверки нет и построить её с этой машины было нельзя: `gisp.gov.ru` отвечает
роботам 403, `ezak.rosseti.ru` открыт только из российских сетей. Оба заведены источниками
типа `admission_registry` (в `CATALOG_SOURCE_TYPES`, опросом тендеров пропускаются) — ради
проверки доступности в мониторинге и официальной ссылки «сверить в реестре» из карточки
модели. Запись заводится руками (раздел «Реестры допуска» под характеристиками модели):
номер, даты, ссылка на карточку записи, заметка, отметка «сверено» с датой; либо явное
**«проверено: записи нет»** — это не пустое поле, а факт, и в сопоставлении он даёт
`not_meets`, тогда как незаведённая запись — `no_data`.

Цепочка проверки (`app/services/registry_records_service.py`):

* `detect_registries` — узнавание реестра в тексте требования по широким шаблонам («ПП
  719», «реестр Минпромторга», «ГИСП», «аттестационная комиссия», «допущенных ПАО Россети»,
  «реестр российских программ»); Госреестр СИ нарочно не считается допуском — им занимается
  описание типа;
* `record_state` — состояние по датам на сегодня: действует / истекает (`EXPIRING_DAYS` =
  90, квартал — столько идёт закупка до поставки) / истекла / записи нет / не проверялось;
* `registry_facts` — строки `[registry]` в карточку производителя, только по реестрам, о
  которых спрашивает закупка; правило 8 в `_SYSTEM_PROMPT` сопоставления: действует или
  истекает — `meets`, истекла или «записи нет» — `not_meets`, нет факта — `no_data`, источник
  вердикта `admission_registry`;
* `tender_overview` — блок «Допуски: реестры и аттестация» над матрицей
  (`TenderRegistryBlock.tsx`, `GET /tenders/{id}/registry-check`): требования с
  распознанными реестрами и таблица «производитель × реестр» с лучшим состоянием по
  моделям (одна действующая запись важнее десяти истёкших — в закупку предлагают её).

API: `GET /catalog/registries`, `GET /products/{id}/registry-records`,
`PUT/DELETE /products/{id}/registry-records/{registry}` (администратор). Тесты —
`tests/test_registry_records.py`: формулировки, состояния по датам, факты и сводка, API.

### Синхронизация — фоновой задачей («бесконечная синхронизация»)

Баг: после нажатия «Синхронизировать» оверлей крутился вечно, а `POST /sources/poll` в
DevTools висел без ответа. Причина — не пустой ответ, а его отсутствие: опрос девяти
площадок по журналу идёт 20–25 минут, и всё это время HTTP-запрос держался открытым.
Любой перезапуск сервера (в разработке — `uvicorn --reload` на каждое сохранение файла),
таймаут прокси или обрыв соединения гасил запрос, и интерфейс ждал ответа, который никогда
не придёт.

Теперь опрос — задача той же очереди, что и ИИ-анализ (`JobKind.SOURCES_POLL`), но без
тендера: набор площадок и итог по каждой — в новом поле `background_jobs.payload` (JSONB,
миграция 0046). `POST /sources/poll` отвечает `202` и задачей сразу; повторное нажатие,
пока опрос идёт, возвращает ту же задачу (`enqueue_standalone`). Обработчик
(`job_runner._run_sources_poll`) опрашивает площадки по очереди и после каждой пишет
прогресс в `message` («Опрос 3 из 9: Сбербанк-АСТ…»); `GET /sources/poll/current` отдаёт
последнюю задачу. Опрос идёт в своём пуле на один поток (`_poll_executor`), чтобы не
занимать половину пула ИИ-анализа; одна попытка — `poll_source` сам изолирует ошибку
каждой площадки, а повторять 25-минутный проход целиком было бы хуже честной ошибки.
`recover_interrupted_jobs` при старте помечает оборванный перезапуском опрос ошибкой — так
интерфейс не покажет «идёт» по задаче, которую никто не считает.

Во фронте оверлей поверх списка заменён полосой прогресса над ним: со списком можно
работать все двадцать минут; страница опрашивает `/sources/poll/current` раз в две секунды,
по завершении показывает итог и перечитывает список, а при входе подхватывает идущий
опрос (запущенный до перезагрузки вкладки или другим пользователем).

**Порциями по 100, а не одним куском.** Раньше адаптер возвращал всю выдачу площадки
разом (`PollOutcome.tenders`; у ЭТП ГПБ — 11 000 записей и несколько минут), и только
потом `poll_source` сохранял её в одной транзакции: пока шёл опрос, в базе не появлялось
ничего, а список ждал конца. Теперь у `SourceAdapter` есть `on_batch` и `_collect(seen,
summary)`: адаптеры кладут записи через него (одна строка на адаптер вместо
`seen[id] = summary`), и каждые `POLL_BATCH_SIZE` = 100 записей уходят подписчику.
`poll_source` подписывается, сохраняет порцию (`_upsert_tender` под точкой сохранения на
каждую запись — ошибка одной строки не откатывает порцию) и **коммитит её сразу**; остаток
меньше порции и записи, обновлённые адаптером после отправки (та же закупка по другому
слову с новыми полями), досохраняются из `outcome.tenders` после возврата — по
идентичности объектов, без повторов. Без подписчика (`on_batch is None`: CLI, тесты
адаптеров) адаптер ведёт себя как раньше. `on_progress(processed, created, updated)`
после каждой порции идёт в `message` задачи («Опрос 3 из 9: ЭТП ГПБ — сохранено 1200
(новых 16, обновлено 1184)»), а интерфейс, увидев новое сообщение, тихо перечитывает
список — без «Загрузка…» и без сброса выбранной закупки, не чаще раза в десять секунд.
Тесты — `test_poll_source_saves_in_batches`, `test_enqueue_standalone_dedupes_running_poll`.

### Знак решения «смотреть / не смотреть»

Процент AI-оценки и вердикт из трёх значений требуют чтения; в списке нужен знак,
понятный с первого взгляда, без слов «да» и «нет». В `compute_profile_score` после трёх
измерений добавлен четвёртый вызов модели (`_DECISION_PROMPT`, `DecisionAnswer`): на вход —
История, Задача и Компетенции с комментариями и обоснованиями (`_decision_context`, факты
из `*_evidence` текстом), на выход — служебная сводка `decision_summary` (хранится в
`ai_profile_scores`, но **наружу не отдаётся**: `serialize` её не включает) и двоичное
`decision`. Отдельным вызовом, а не порогом по проценту, намеренно: процент усредняет, а
решение должно ломаться об одно «нет допуска» независимо от остальных двух — правила в
промпте так и сформулированы. Без ответа модели решение остаётся `None` и порогом не
подменяется; без Задачи и Компетенций вызов не делается (миграция 0047).

`ai_decision` есть в каждой выдаче тендера (`attach_analysis_fields`), `decision` — в
`AiProfileScoreOut`. Во фронте — `DecisionMark`: зелёный круг с галочкой, красный с
крестом, серый пунктирный с чертой («не выносилось»); стоит у названия в двухпанельном
списке, таблице, на доске, в шапке карточки и в избранном меню учётной записи, а в блоке
«AI-оценка по профилю» подписан «по трём измерениям» — оттуда же человек смотрит
подробности. Оценки, посчитанные до этой правки, знака не имеют, пока их не пересчитают.

## 40. Выбор ИИ-провайдера: YandexGPT ↔ Claude через RouterAI (18.09.2026, раздел 5.4 ТЗ)

По просьбе заказчика у ИИ-модуля появился второй провайдер — Claude, подключённый через
RouterAI (OpenAI-совместимый шлюз, `https://routerai.ru/api/v1/chat/completions`). Выбор
модели — **персональный**: у каждого пользователя своя (`users.ai_provider`), один работает с
Claude, другой с YandexGPT, и смена у одного никого больше не касается. Через выбранную модель
идут **все запросы генерации** этого пользователя — разбор карточки по профилю, извлечение
требований, разделы «Дополнительно», матрица соответствия, релевантность, сводка аналитики,
экстракция характеристик — и фоновые задачи, которые он запустил. Пользователь без
собственного выбора и задачи без автора (расписание) работают через **модель по умолчанию**
(`ai_provider_settings.active_provider`), которую задаёт администратор.

- **Как вызов узнаёт пользователя** (`app/services/ai_context.py`). `run_structured` зовут из
  глубины сервисов, куда пользователь не передаётся (`_classify`, `_ask_model`,
  `read_characteristics`), и протаскивать `actor` через десяток сигнатур ради одного поля —
  много шума. Поэтому пользователь кладётся в `ContextVar` один раз на входе:
  `AiContextMiddleware` (`app/middleware/ai_context.py`) декодирует bearer-токен для
  HTTP-запроса, `run_job` в `app/core/jobs.py` ставит автора задачи. Именно middleware, а не
  зависимость FastAPI: sync-зависимость выполняется в отдельном потоке с копией контекста, и
  её `set` до обработчика не доходит (проверено на Starlette 0.41; регрессионный тест
  `test_request_context_carries_the_user_into_the_dispatcher` ходит сквозь реальный запрос).
- **`app/services/ai_client.py`** — единая точка входа: `run_structured` спрашивает
  `ai_provider_service.get_active_provider` (контекст → личный выбор → умолчание) и зовёт
  `yandex_ai_client` или `routerai_client`. Сервисы-потребители импортируют
  `run_structured`/`chunk_text` отсюда и о провайдерах не знают; контракт у обоих клиентов
  одинаков (те же аргументы, pydantic-схема ответа, три повтора с линейной задержкой). Ошибка
  «ключ не задан» у любого — `AiNotConfiguredError` (общий предок; `YandexAiNotConfiguredError`
  от него наследует), эндпоинты ловят её и отдают 400/422 с текстом.
- **`app/services/routerai_client.py`** — `httpx` без пакета `openai`: один эндпоинт, один
  формат тела, а текст ошибки шлюза (ключ, баланс, недоступная модель) нужен дословно.
  Structured output — `response_format: json_schema` со `strict: true`; схема pydantic
  перед отправкой приводится к strict-режиму (`additionalProperties: false` на каждом
  объекте, без `title`). Проверено на живом шлюзе: вложенные модели через `$defs` проходят,
  типы соблюдаются; в режиме `json_object` числа приходили строками. `max_tokens = 16 000`,
  обрыв по `finish_reason = length` считается сбоем и повторяется.
- **Хранение.** `ai_provider_settings` (миграция 0049) — синглтон: модель по умолчанию,
  `routerai_api_key`, `routerai_model` (по умолчанию `anthropic/claude-opus-5`),
  `routerai_base_url`. `users.ai_provider` (миграция 0050) — личный выбор, `NULL` = не
  выбирал. Ключ, как и у Yandex, в БД и правится из интерфейса; наружу — только
  маскированный хвост.
- **Эндпоинты.** `GET /integrations/ai-provider` (любой пользователь) — модель, действующая
  для него: `active_provider`, `source` (`user`/`default`), `default_provider`,
  `configured_providers`. `PUT /auth/me/ai-provider` — свой выбор (`null` — сброс к
  умолчанию). `PUT /integrations/ai-provider` (админ) — модель по умолчанию; личные выборы
  не трогает. `GET/PATCH /integrations/routerai`, `POST /integrations/routerai/test` (админ;
  проверка — короткий запрос к модели, отдельного «пинга» у OpenAI-совместимых шлюзов нет).
- **На ненастроенного провайдера переключиться нельзя** (400) — ни себе, ни по умолчанию:
  иначе одним щелчком все ИИ-функции разом начали бы падать, а причина была бы на другой
  странице. Если ключ очистили уже после того, как пользователь выбрал модель, он молча
  получает модель по умолчанию, а в лог уходит предупреждение (`resolve_provider`).
- **Что остаётся на Yandex независимо от выбора**: эмбеддинги для «Похожих» (у Claude нет
  модели эмбеддингов, а векторы разных моделей несравнимы), OCR-fallback для сканов и
  Яндекс-поиск при обучении справочника. Учётные данные Yandex должны быть заполнены даже
  если все работают через Claude.
- **Интерфейс.** Отдельный пункт меню «Интеграции» (`pages/Integrations.tsx`): блок
  «Искусственный интеллект» (`AiIntegrationSection`) с ключами обоих провайдеров и
  переключателем модели по умолчанию, ниже — почта и Bitrix24, вынесенные из «Настроек».
  Свою модель пользователь выбирает в «Учётной записи» (тот же `AiProviderSwitcher` в роли
  `scope="me"`) или прямо в карточке тендера: бейдж с именем модели в шапке «Разбора ИИ» —
  выпадающий список (`AiProviderPicker`, через портал, потому что блок обрезает содержимое
  ради скруглённой шапки). Блок меняет гамму под модель пользователя: розово-голубая волна и
  сфера у YandexGPT, оранжевый переливающийся градиент (`.ai-wave--claude`, `.ai-orb--claude`)
  у Claude. Статус запрашивается один раз на вкладку и кэшируется (`hooks/useAiProvider.ts`);
  смена рассылается подписчикам без перезагрузки. Смена модели не запускает пересчёт сама —
  цифры на экране получены прежней моделью, новый разбор — кнопкой. В сообщении фоновой
  задачи `ai_profile_score` есть `модель: …` — по журналу видно, чьи цифры.
- Проверено вживую 18.09.2026: администратор с личным выбором YandexGPT и системным
  умолчанием Claude — его пересчёт разбора прошёл через YandexGPT (`модель: YandexGPT` в
  сообщении задачи), второй пользователь без выбора видит Claude.

## 41. Заполнение «Моей компании» с rusprofile.ru (18.09.2026, раздел 7 ТЗ)

**Что изменилось.** До этого rusprofile был одним из двух источников автопоиска реквизитов
(раздел про ЕГРЮЛ выше) и читался анонимно по ссылке на карточку. Заказчик дал учётную
запись сайта, и под ней открывается всё, что анонимно замаскировано символами «░»: полный
список госзакупок компании с исходом каждой, лицензии, среднесписочная численность, финансы,
учредители, контакты. Это закрывает главный пробел раздела «Моя компания»: допуски,
реализованные проекты и историю участий больше не вводят руками.

**Почему это важнее, чем кажется.** Реестр контрактов ЕИС (раздел 23) знает только о победах,
поэтому История отказывалась считать долю побед по такой выборке. Раздел «Госзакупки» на
rusprofile показывает и закупки со статусом «Не выиграно» — это единственный найденный
открытый источник проигрышей. Источник `rusprofile` намеренно не входит в
`WINS_ONLY_SOURCES`, и после первой синхронизации win-rate становится осмысленным.

**Как устроен сайт** (проверено 18.09.2026, `app/adapters/rusprofile.py`):

- поиск по ИНН — `GET /ajax.php?query=<ИНН>&action=search` → JSON со ссылкой `/id/<номер>`
  (ИНН в ответе обёрнут маркерами подсветки `!~~…~~!`). Прежний вывод «поиск по ИНН
  недоступен» относился к HTML-странице `/search`; ajax-эндпоинт из референсного
  `rusprofile-wrapper` работает и без входа;
- вход — `POST /auth.php?action=login`, поля `login`/`password`, ответ JSON
  `{success, code, message}`; код 255 — сайт просит капчу (после серии неудачных попыток),
  лечится разовым входом в браузере. Перед входом читается `/` ради cookie и CSRF-токена;
- разделы карточки: `/gz/<id>/supplier` (закупки, 20 на страницу, ссылка «дальше» в
  `.filters-pagination__nav.--next`), `/licenses/<id>` (404 = лицензий нет), `/finance/<id>`;
- строки закупок и лицензий свёрстаны одинаково — блок `.snippet` с парами
  «`.snippet__row-key` → `.snippet__row-value`», контракт закупки — соседний `.snippet.sub`.
  Разбор общий (`parse_snippets`), поверх него `parse_purchases` и `parse_licenses`;
- замаскированное значение считается **отсутствующим**, а не пустой строкой; досье помнит
  `data_hidden`, и итог синхронизации предупреждает об этом — иначе «0 проигрышей» при
  истёкшей подписке выглядело бы как факт.

**Данные.** `rusprofile_settings` (синглтон, миграция 0051): логин, пароль, итог последней
синхронизации. `company_profile`: `rusprofile_card_id` (после первого поиска по ИНН не
ищем повторно), `rusprofile_data` (досье целиком, JSONB), `rusprofile_synced_at`. У лицензий
и проектов появилось поле `source`: записи с `rusprofile` ведёт синхронизация, без него —
человек. В `field_sources` — новый источник `rusprofile` с `verified_by_user: false`.

**Правила синхронизации** (`app/services/rusprofile_service.py`):

1. Реквизиты — только в пустые поля и в поля, ранее взятые с сайта. Подтверждённое человеком
   значение важнее сайта: оно подаётся в evidence оценки как факт.
2. Лицензии и проекты сайта заменяются целиком при каждом запуске, ручные остаются.
   Проектами становятся только выигранные закупки (объект закупки, заказчик, цена контракта,
   год, номер закупки и контракта в описании).
3. История участий — только у основной компании (таблица привязана к «нашему»
   производителю). Ключ дедупликации — номер закупки, общий с выгрузкой из ЕИС: одна
   закупка из двух источников остаётся одной записью, исход берётся с сайта, источник
   записи ЕИС не меняется, `lessons_learned_md` не трогается.
4. Досье попадает в промпт AI-оценки через `company_profile_service.rusprofile_fields`
   (ключи `rusprofile:*` в evidence) — «Компетенции» сверяют с ним требования к участнику,
   которых из реквизитов не видно: выручка, численность, статус МСП, исполнительные
   производства. Факты того же снимка кладутся в `company_profile_snapshot`.

**Измерение History после rusprofile.** История по ИНН приходит за годы до появления
системы и ни к какому нашему тендеру не привязана, а имена заказчиков на сайте короткие
(«ПАО "Россети…"») против полных в ЕИС — прежний отбор «по похожим тендерам или подстроке
заказчика» её не видел, и History оставалась «нет данных». Теперь
`_relevant_participations` сравнивает ядро названия заказчика без организационно-правовой
формы и кавычек, ищет участия со схожим предметом закупки (общие основы значимых слов,
порог 0,5 от меньшего набора и минимум две общие основы), а когда прямых совпадений нет —
третий уровень: общая доля побед по всей истории с известным исходом, с комментарием, что
она общая, а не по нише. Правило «выборка из одних побед не даёт долю» действует на всех
уровнях.

**Интерфейс.** «Интеграции → Rusprofile» (`RusprofileSection`): логин, пароль (наружу не
отдаётся), «Проверить вход», итог последней синхронизации. «Моя компания → Профили
компаний»: кнопка «Обновить из rusprofile» у каждой строки (нужен ИНН или сохранённый номер
карточки). Карточка компании перерисована 18.09.2026 под дашборд-референсы: свёрнутая —
шапка с аватаром и ряд ключевых цифр (стаж, допуски, проекты, победы/проигрыши, выручка),
раскрытая — четыре блока в своих оттенках (реквизиты, допуски, проекты, досье rusprofile
с плитками численности/прибыли/капитала и чипами заказчиков); у допусков и проектов с
сайта — пометка `rusprofile`. Синхронизация основной компании перечитывает вкладку «История
участий».

**Ограничения.** Синхронизация синхронная (карточка + до 60 страниц закупок с паузой 0,7 с +
лицензии), как и выгрузка из ЕИС. Один вход на запуск: частые входы сайт считает
подозрительными. Пагинация закупок и лицензий анонимно недоступна — без действующей
подписки придёт только первая страница, и итог об этом скажет.

**Блок «Разбор ИИ» в карточке тендера** (`TenderAiScorePanel.tsx`, 18.09.2026): шкалы
измерений двух состояний, по образцу индикатора усилия в Claude Code. Выше 50% —
зелёная сетка точек 4×64 (`.dotbar` в `index.css`), заполненная до доли процента и
переливающаяся бегущей волной: интерфейс прямо сигнализирует «можем участвовать». 50% и
ниже — без точек, сплошная красная полоса с медленным переливом градиента (`.solidbar`).
Без данных — пустая полоса. Разделы под шкалами — отдельные карточки с иконками: резюме,
слабые места (иконка и чип веса у каждого пункта), стратегия тремя плитками (вердикт,
цена, первый шаг), сноска об источниках «Истории».

## 42. Три ответа на один вопрос, слепое пятно анализа и «Разобрать закупку» (18.09.2026, разделы 5.4, 5.5, 5.5.1 ТЗ)

Замечание по карточке «Обслуживание систем АИИС КУЭ … Хохловского месторождения» (Фабрикант
3214995): «Подобрано ИИ», 34 % и вопрос «зачем система рекомендует тендер, в котором
компания проиграет?». Разбор показал три разные проблемы.

### Вердикт выводится, а не спрашивается

На одной карточке стояли красный крест (решение «не смотреть»), 34 % и вердикт «ИДТИ С
ОГОВОРКАМИ». Причина: вердикт выбирала модель в промпте «Резюме» свободно, без оглядки ни
на процент, ни на решение из отдельного вызова; `_fallback_verdict` с порогами применялся
только при сбое модели. Теперь `_verdict(decision, overall)` в `ai_profile_service`:
решение `False` → `no_go` при любом проценте; иначе порог 80/50, как у цветного бейджа
списка; при решении `True` и проценте ниже 50 — `go_with_reservations`, а не отказ (решение
уже вынесено в пользу просмотра, окончательное — за человеком). Из `ResumeAnswer` поле
`verdict` убрано, промпту «Резюме» передаётся решение с пометкой «не пересматривай». Тест —
`test_verdict_follows_decision_and_threshold`.

### «Подобрано ИИ» → «Наша тематика»

Метка `ai_relevant` отвечает только «это про счётчики электроэнергии?», а читалась как «ИИ
рекомендует участвовать». Переименована; подсказка прямо говорит, что за рекомендацию
отвечает знак решения слева. Значение и поле не менялись.

### Анализ извлекал только требования к товару

Обе кнопки работали, но давали «требований сохранено: 0» на ТЗ в 27 тысяч знаков: промпт
извлекал характеристики прибора, а требования к работам и участнику велел пропускать.
Закупка на обслуживание — профильная по `COMPANY_CONTEXT` отбора, но для анализа была
невидима; AI-оценка после этого считалась «только по карточке, точность ниже». Введён
`RequirementKind` (`requirements.kind`, миграция 0052): `product`, `service`,
`participant`. Промпт описывает все три вида и явно допускает закупки без товара; в
ранжирование кусков документации добавлены слова о работах (`обслуживани|ремонт|монтаж|
аискуэ|…`), иначе ТЗ на обслуживание проигрывало проекту договора. Матрица соответствия
(`compliance_service.evaluate_tender`, `analysis_service.get_compliance_matrix`) строится
только по `product`: сравнивать модель счётчика с «группой допуска персонала» бессмысленно,
а «нет данных» по таким строкам обнулило бы процент; закупке без товара матрица сообщает об
этом прямо. В контекст AI-оценки вид требования идёт пометкой рядом с критичностью —
измерение «Компетенции» теперь видит требования к участнику, которых раньше не было вовсе.
Группа характеристик у `service`/`participant` не ставится, даже если модель её подставила.
На той же закупке после правки: 29 требований (27 к услугам, 2 к участнику), оценка 18 %,
крест, «НЕ ИДТИ» — согласованно. Тесты —
`test_service_and_participant_requirements_are_saved_with_kind`,
`test_matrix_is_built_only_from_product_requirements`.

### Одна кнопка и автозапуск

«Анализ документов» и «Расчёт соответствия» заменены одной «Разобрать закупку» —
`POST /tenders/{id}/review`, `JobKind.TENDER_FULL_REVIEW`, обработчик уровня задачи
`_run_full_review`: анализ → матрица (если есть требования к товару, иначе шаг пропускается
с пояснением) → AI-оценка. Между шагами в `message` пишется «Шаг N из 3: …», карточка
показывает это в строке хода; итог каждого шага — в `payload` (`analysis`, `evaluation`,
`score`), по `payload.analysis` вкладка «Требования» объясняет пустоту. Сбой одного шага не
отменяет остальных; задача считается неудавшейся, только если не удались и анализ, и
оценка. Раздельные `/analyze`, `/evaluate`, `/ai-score` остались для интеграций и точечного
пересчёта («Обновить разбор» в блоке оценки — только оценка). `GET /jobs?kind=` принимает
несколько видов через запятую: последний анализ — это либо `tender_analysis`, либо
`tender_full_review`. Автозапуск при открытии карточки без оценки: полный разбор, если
`requirements_count == 0`, иначе только оценка — так 34 % «по карточке без ТЗ» больше не
появляются. Тесты — `test_full_review_runs_steps_and_skips_matrix_without_product_requirements`,
`test_full_review_fails_only_when_both_analysis_and_score_fail`.
