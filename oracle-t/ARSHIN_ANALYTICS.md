# ТЗ: блок «Аналитика» — рынок счётчиков электроэнергии по поверкам ФГИС «Аршин»

Записано 29.10.2026. Источники ТЗ:
- созвон с Ксенией Мурашовой 29.10.2026 (видео Compass);
- файлы, которые она прислала после созвона;
- её ответы на вопросы в тот же день.

Раздел «Аналитика» перестраивается под этот отчёт. Документ — единственный источник
требований: материалы созвона во временных папках не сохраняются.

## 1. Зачем

Ксения раз в квартал вручную собирает для руководства отчёт о рынке счётчиков
электроэнергии (ПУ) по данным поверок из ФГИС «Аршин». Цепочка сейчас такая: программа
Чернова → Excel → Power BI. На отчёт уходит очень много времени. Задача от Романа — чтобы
Сова собирала его сама. За Ксенией остаются разметка новых модификаций и проверка
локализации.

## 2. Как сейчас (путь Ксении)

1. **Загрузка поверок.** Программа Чернова (`data_downloader.py`) по манифесту ФГИС качает
   ежедневные пакеты поверок в их Postgres во внутренней сети.
2. **Подсчёт.** Excel-форма `multipage_table_data.xlsm` (`get_tables_db.py`) по номеру типа
   СИ и периоду выдаёт `COUNT(*)` с группировкой по поверителю, наименованию, модификации,
   номеру ГРСИ и обозначению типа. Фильтр — `ILIKE '%…%'`. Считает 1–2 минуты, Excel в это
   время висит.
3. **Разбор модификаций.** По каждому описанию типа (около 109–140, только интеллектуальные
   счётчики по ПП 890, «простейшие» не нужны) модификации разбираются вручную. Поверители
   пишут их по-разному: латиница вместо кириллицы, 0 вместо О, лишние пробелы. На сайте
   Аршина видно только 100 записей на страницу.
4. **Новые описания типа** Ксения отслеживает сама по официальным источникам.
5. **Справочник модификаций** (Excel, лист «2021-2026 интерфейсы», рабочий файл
   «Счетчики 3Q на 01.10.26»). Для каждой модификации проставляется:
   - производитель, номер ГРСИ, срок свидетельства;
   - тип ПУ (1ф/3ф), исполнение, интерфейс, межповерочный интервал (МПИ);
   - локализация: есть ли в реестре российской промышленной продукции (РПП), требованиям
     какого года соответствует, сколько баллов по ПП 719 (смотрит в XLSX реестра на ГИСП,
     в том числе по окончанию наименования, например «/2»);
   - свой комментарий.

   Справочник растёт строками за период. Строки без выпуска она удаляет вручную.
6. **Отчёт.** Итог собирается в Power BI на четырёх страницах (раздел 8).

## 3. Согласованные правила подсчёта

| # | Правило | Статус |
|---|---|---|
| 1 | «Производитель» — **владелец описания типа** (по номеру ГРСИ), а не организация-поверитель | Ксения, 29.10 |
| 2 | Поверки с пригодностью «нет» (`applicability` ≠ 1) **исключаются** | Ксения, 29.10 |
| 3 | «Соответствие требованиям года» определяется **по порогу баллов** ПП 719 (см. ниже) | Ксения, 29.10 |
| 4 | Поверки модификации до даты её внесения в РПП **не считаются локализованными** | Ксения, 29.10 |
| 5 | Поверка относится к периоду по **дате поверки** (`verification_date`) | по умолчанию, не возражали |
| 6 | Учитываются только описания типа, включённые в список отчёта | со слов на созвоне |
| 7 | Аннулированные записи не учитываются, у исправленной берётся актуальная версия | инструкция ФГИС |
| 8 | Первичную поверку от периодической **не отделяем**, считаем все пригодные поверки типа | предложено, ждём подтверждения (раздел 11) |

**Пороги баллов.** В файле за 3 кв. 2026:
- 94, 95, 105 баллов → требования **2024**;
- 113–120 баллов → требования **2025**.

Значит, правило такое: ≥ 113 → 2025, иначе ≥ 94 (уточнить нижнюю границу) → 2024. Пороги
хранить настройкой «год → минимум баллов», а не константой. Порог на 2026 год пока
неизвестен. 113 уже используется в Сове как `PP719_MIN_SCORE` (раздел 77 ARCHITECTURE.md).

## 4. Источник данных — сервис выгрузки поверок ФГИС

Инструкция: страница <https://fgis.gost.ru/fundmetrology/cm/docs>, документ «Инструкция по
использованию выгрузки сведений о результатах поверки СИ».

- Манифест: `https://fgis.gost.ru/fundmetrology/exporter/poverki/manifest.json`, файлы
  лежат по `relativeUri` рядом с ним.
- **Слепок.** `poverki.snapshot.YYYYMMDD.csv.zip` раз в месяц, около 11,8 ГБ в zip. Это
  все средства измерений страны, не только счётчики.
- **Изменения.** `poverki.delta.<prevId>--<id>.csv.zip` каждый день, 0,3–15 МБ. Публикация
  около 01:00 МСК. Следующее обновление — в поле `nextUpdate`, раньше этого времени
  обращаться к сервису не нужно.
- В манифесте лежат 2 последних слепка и изменения примерно за 2 месяца.
- Цепочку строим по парам `id`/`prevId` от известного нам состояния до `currentId`.
  Каждый файл сверяем по md5.
- Формат CSV: разделитель `;`, кодировка UTF-8, один CSV внутри zip.
- Поля: `global_id, org_title, mit_number, mit_title, mit_notation, mi_modification,
  mi_number, verification_date, valid_date, result_docnum, applicability, ver_date_start,
  ver_date_end, ver_id_prev, ver_id_next, reason`.
- **Аннулирование.** Прежняя запись не меняется: приходит новая со ссылкой на предыдущую
  (`ver_id_prev`) и причиной (`reason`). Поэтому `global_id` неуникален. Внутри файла
  изменений сначала идут аннулированные, затем действующие записи.
- **Тип поверки** (первичная/периодическая) в выгрузке **отсутствует**: он есть только в
  карточке поверки на сайте. Для электроэнергии он не нужен (раздел 10).
- **Даты.** У Чернова встречался разнобой форматов (`dd.mm.yyyy`, ISO, с временем и без),
  разбирать надо устойчиво.

Справочно: код Чернова лежит в `~/Downloads/Аршин.zip`. В `settings.py` и
`data_downloader.py` оттуда открытым текстом записан пароль к их внутренней базе — в
репозиторий эти файлы не класть и пароль не переносить. Их база (192.168.1.121) из Совы
недоступна, данные Сова грузит сама.

## 5. Хранение и загрузка

- **Что сохраняем.** Поверки только по счётчикам электроэнергии, а не всю выгрузку.
  Объём — порядка 27 млн записей за 2021–2026 (в отчёте групп у Ксении 26,7 млн).
  Рекомендация: брать **все** типы счётчиков электроэнергии (по `mit_title`/реестру типов),
  а не только включённые в отчёт. Тогда включение нового типа — это флаг в справочнике, а
  не повторный проход по слепку на 11,8 ГБ.
- **Хранимые поля:** `global_id`, ссылка на тип, сырое `mi_modification`, `org_title`,
  `mi_number`, `verification_date`, `valid_date`, `applicability`, признак
  актуальности/аннулирования.
- Отчёты строить по **помесячным сводным таблицам** («тип × модификация × месяц →
  количество»), которые пересчитываются после загрузки изменений. Окончательную схему
  выбирает разработчик, обоснование — новым разделом ARCHITECTURE.md.
- **Первичная загрузка.** Скачать последний слепок, читать CSV потоком прямо из zip, не
  распаковывая на диск, и отбрасывать всё, что не счётчики электроэнергии. Затем применить
  цепочку изменений. Учесть место на сервере и время: слепок качается долго, загрузка
  должна продолжаться после обрыва.
- **Ежедневно.** Задание планировщика (`core/scheduler.py`) после `nextUpdate`, примерно
  в 01:15. Статус и ошибки — в журнал и в «Источники», как у других источников
  справочника (раздел 28 ARCHITECTURE.md).
- **История с 2021 года** нужна: отчёты показывают годы 2021–2026. Проверить, что слепок
  содержит историю, а не только действующие поверки.

## 6. Справочники (правит Ксения, по умолчанию также администратор)

### 6.1 Описания типа (ГРСИ)

- Поля: номер ГРСИ, наименование, обозначение, **производитель (владелец типа)**, срок
  свидетельства, МПИ, флаг «в отчёте».
- Стартовый список — из файла Ксении (109 номеров ГРСИ в выгрузке за 3 кв.).
- Новые описания типа счётчиков электроэнергии Сова находит сама через реестр утверждённых
  типов ФГИС: адаптер `adapters/fgis.py`, `mit24/list`. Такие типы попадают в очередь «на
  решение»: включать в отчёт или нет. Решение — за Ксенией: интеллектуальный ли счётчик по
  ПП 890, определяет человек.

### 6.2 Модификации

- Поля:
  - каноническое название, тип ГРСИ;
  - тип ПУ: 1ф или 3ф;
  - исполнение: шкафное, сплит, DIN-рейка, н/д;
  - интерфейс (единый перечень, см. ниже);
  - МПИ;
  - «Дополнительно» — комментарий Ксении, в отчёт не идёт;
  - локализация: в РПП да/нет, баллы, год требований (вычисляется по порогу), дата
    внесения в РПП, источник значения (ГИСП или вручную).
- **Стартовые данные** — `~/Downloads/3 кв 2026.xlsx`, лист «Лист1». Значимых строк 1 194
  (остальные пустые до 1 038 697-й), около 1 000 модификаций, 36 производителей. Колонки:

  > Производитель, Регистрационный номер типа СИ, Срок свидетельства, Тип ПУ, Исполнение,
  > Период, Количество, Интерфейс, Межповерочный интервал, Наименование типа СИ,
  > Модификация СИ, Дополнительно, В Реестре российской промышленной продукции,
  > Соответствие требованиям года, Кол-во баллов

  Данные грязные:
  - «шкафное» и «Шкафное»;
  - « да» с пробелом;
  - «Срок свидетельства» то датой, то строкой;
  - табуляции в названиях;
  - «н/д» в числовых полях.

  Полный рабочий файл за 2021–2026 (около 11 тыс. строк) нужно запросить у Ксении
  (раздел 11).
- **Интерфейсы.** В файле 69 вариантов. Свести к единому перечню без дублей вида «GSM»,
  «GSM » и «LoRaWan»/«LoRaWAN»; составные значения («RF и RS», «GSM, ZigBee, Bluetooth»)
  — как в отчёте Ксении. Основа отчёта — колонка «Интерфейс», «Дополнительно» —
  комментарий.

### 6.3 Варианты написания модификации

- Сырое `mi_modification` (вместе с типом) привязывается к канонической модификации.
- **Автоматическое сведение** — нормализация ключа:
  - латиница и кириллица одного начертания (A/А, B/В, C/С, E/Е, H/Н, K/К, M/М, O/О, P/Р,
    T/Т, X/Х, y/у) приводятся к одному виду;
  - 0 и О тоже;
  - регистр, пробелы, лишняя пунктуация и табуляции убираются.
- Не сведённое автоматически попадает в очередь **«Разметить»**: сырое написание, тип,
  количество поверок, примеры заводских номеров и поверителей. Ксения привязывает его к
  существующей модификации или заводит новую.
- Пока вариант не размечен, его поверки в отчёте видны строкой «не размечено», а не
  пропадают. Иначе итоги молча разойдутся с ФГИС.
- Для каждой модификации видно, как её записывали и сколько поверок у каждого варианта.
  Ксения хотела этого от формы Чернова: «чтобы я видела все варианты модификации».

### 6.5 Локализация из ГИСП

- Сова уже загружает реестр ГИСП (ПП 719) по ОКПД2 26.51.63: `product_registry_records`
  с полями `score`, `issued_at` (дата внесения), `valid_to`; раздел 77 ARCHITECTURE.md,
  `registry_polling`.
- Эти записи привязаны к продуктам каталога (`product_id`), а не к модификациям из
  поверок. Нужна связь «модификация отчёта ↔ запись ГИСП»: автоматическое сопоставление
  по наименованию с учётом окончаний вроде «/2» плюс ручное подтверждение Ксенией.
  Ручное значение не затирается автоматическим.
- **Точка отсчёта** — дата внесения исполнения в РПП. Поверки раньше неё в отчёт о
  локализации не попадают (правило 4).

## 10. Вне рамок первой версии

- Счётчики газа, воды и тепла. Схема та же, другой список типов.
- **Тип поверки (первичная/периодическая) из карточки поверки.** В выгрузке его нет,
  а открывать карточку каждой поверки — это миллионы запросов. Для будущих отчётов по газу
  и воде делать отдельно и только по нужным типам.
- Связь с тендерами (доли конкурентов в «Конкуренции», в расчёте шансов) — после того,
  как отчёт сойдётся.
- Баг профиля отбора «Счетчики газа», найденный на том же созвоне, — отдельная задача.

## 11. Открытые вопросы к Ксении

1. **Первичная поверка.** Ксения переспросила, зачем нужен список «своих» поверителей.
   Он нужен был, только чтобы отделять выпуск (поверку на заводе) от периодических
   поверок. Раз производитель — владелец типа, предлагаем считать все пригодные поверки
   типа. Для интеллектуальных счётчиков с МПИ 16 лет периодических поверок в 2021–2026
   почти нет. Ждём подтверждения: так ли она считает сейчас.
2. Нижняя граница баллов для требований 2024 года и порог на 2026 год.
3. Полный рабочий файл справочника за 2021–2026 (лист «2021-2026 интерфейсы») и
   PBIX-файл отчёта.
4. Кто кроме Ксении правит справочник.
5. Исполнение «н/д» — оставляем отдельной категорией, как в Power BI (предположение).
