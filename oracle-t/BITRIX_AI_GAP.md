# Дополнительный перечень данных от ИИ для Bitrix24 — сопоставление с кодом (05.11.2026)

Источник: «Что еще нужно от ИИ.docx» (специалист Битрикса), 94 пункта в 8 разделах.
Статусы: **есть** — извлекается в нужном виде; **частично** — данные есть, но не в требуемой
структуре (нет цитаты/пункта/связи с лотом/прежнего значения); **нет** — не реализовано.
Оценка по просмотру кода, не построчный аудит.

## Что уже есть (опора)

- **Канал в Bitrix24** — `services/bitrix_ai_service.py` (раздел 66 ARCHITECTURE.md): подписанный
  JSON, `schema_version 2`, шесть разделов (`tz_nomenclature`, `preparation`, `contract`,
  `participants_prices`, `fas`, сопоставление), постоянные ключи строк, `full_snapshot`, журнал
  `bitrix_ai_requests`, повтор с теми же байтами.
- **Требования** — `tender_analysis` (виды `product/service/participant/supply`, критичность),
  матрица `compliance_service`, позиции `tender_positions`, выжимка `tender_key_facts`.
- **Условия закупки** — `tender_insights` («Дополнительно», 9 разделов), но это **списки коротких
  строк без цитаты, пункта и страницы**.
- **Даты** — `eis_card_dates`: подача, окончание, итоги, аукцион, переторжка, пояс «МСК+N» (только ЕИС).
- **Заточенность ТЗ** — `detect_brand_lock` (п. 36).
- **Итог** — `TenderOutcome`: победитель, цена, URL протокола; `company_participation` — история участий.
- **Журнал** — `tender_history` (`field_change`), но пишется только при ручной правке
  (`tender_edit_service`); мониторинга изменений площадок с «было → стало» не нашёл.

## Сквозные требования, которых сейчас нет нигде

1. **Доказательность факта**: документ + пункт/страница + цитата для *каждого* извлечённого значения.
2. **Различение «не указано / документ недоступен / недостаточно данных / подтверждённо нет»**
   вместо пустого списка.
3. **Лот как сущность** и привязка к нему документов, позиций, требований, результатов.
4. **Версионность**: хранение прошлой версии документов/полей и сравнение «было → стало».
5. **Часовой пояс** во всех датах (сейчас только ЕИС).
6. **Структурные поля вместо списков строк** для условий договора (вид дней, событие-основание,
   база расчёта, периодичность).

## Предлагаемые этапы

0. **Уточнить у заказчика (блокирует остальное):** формат обмена и версия схемы (поля вне
   `schema_version 2`), справочник событий 8.5.1, коды событий `*_CHANGED` / `*_SCHEDULED`,
   справочник возможностей компании (п. 11), недостающие п. 8 и 68, регламент 7.x/8.x.
1. **Фундамент:** сущность «лот»; формат факта (значение + источник + цитата + статус
   «не указано/недоступно/…» + уверенность); хранение версий документов.
2. **Структурный разбор договора (пп. 14–29, 30–31):** один проход модели по проекту договора →
   типизированные поля; раздел `contract` пакета. Самый заметный результат для менеджера.
3. **Мониторинг изменений (пп. 48–67):** сравнение версий, события, дедупликация. Самое большое
   по объёму; зависит от этапов 0–1.
4. **Протоколы и итоги (пп. 69–87):** участники, ИНН, цены, лоты, причины отклонения; расширение
   `TenderOutcome` (миграция).
5. **Квалификация и разъяснения (пп. 9–13, 33–35).**
6. **ФАС и после победы (пп. 37–47, 88–94).**
7. **Лоты, комиссия, грузополучатели, история заказчика (пп. 1, 4–7).**

Каждый этап — новый раздел в ARCHITECTURE.md, миграции Alembic, запись в `changelog.ts` при
видимых изменениях.
